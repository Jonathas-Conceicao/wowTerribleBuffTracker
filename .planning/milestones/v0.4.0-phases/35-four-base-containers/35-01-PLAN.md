# Phase 35 — Plan 01: Container Registry & Schema v4

**Created:** 2026-09-21
**Requirements:** CONT-01, CONT-03

## Approach

Everything downstream in this phase is a loop over one table, so that table comes first. `ns.CONTAINERS`
is an ordered list of container definitions living at the top of `Core.lua` — the first file in the TOC,
so it is in scope for `BuffEngine.lua`, `EditModeFrames.lua`, `Display.lua` and `CDMTab.lua` at both load
and run time.

**The four keys are fixed here and never chosen again:**

| key | title | frame name | kind | CDM viewer global | default x, y |
|---|---|---|---|---|---|
| `buffs` | `Tracked Buffs` | `TBTBuffContainer` | `icon` | `BuffIconCooldownViewer` | `300, -80` |
| `bars` | `Tracked Bars` | `TBTBarContainer` | `bar` | `BuffBarCooldownViewer` | `300, 0` |
| `essential` | `Essential Cooldowns` | `TBTEssentialContainer` | `icon` | `EssentialCooldownViewer` | `300, -160` |
| `utility` | `Utility Cooldowns` | `TBTUtilityContainer` | `icon` | `UtilityCooldownViewer` | `300, -240` |

`bars` and `buffs` keep the keys v0.3.0 already wrote into `entry.section`, so **no tracker is ever
re-sectioned** — the riskiest half of `CONT-03` is a no-op by construction. `essential` and `utility` are
new, deliberately id-shaped rather than label-shaped, and are the mapping target Phase 40's steal mode
will use against `Enum.CooldownViewerCategory.Essential` / `.Utility`.

**One key space.** After this phase `entry.section`, `ns.db.containerSettings[k]`,
`ns.db.editModePositions[k]`, `ns.containers[k]` and the CDM tab section key are all the same four
strings. Today `editModePositions` uses `icons` where the section is `buffs`; that asymmetry is retired
by the migration rather than duplicated into the two new entries.

**List order is the user's, from `35-CONTEXT.md`:** Tracked Buffs, Tracked Bars, Essential Cooldowns,
Utility Cooldowns. This reorders the CDM tab, which today shows Tracked Bars before Tracked Buffs. That
is an intended, visible change. Default positions are per-key facts and are unaffected by list order —
`bars` stays at `300, 0` and `buffs` at `300, -80`, exactly the values `ApplyEditModePositions` and
`SaveEditModePositions` already use, so no existing user's layout moves.

**Split of responsibility for the two kinds of database work.** The `icons` → `buffs` rename must happen
exactly once and destroys the old key, so it is version-gated in `BuffEngine.lua` beside the existing
three migrations. Seeding a *missing* key with a default is idempotent, so it stays where the data is
read (`containerSettings` in `Core.lua`'s existing backfill loop; `editModePositions` in Plan 02's
`ApplyEditModePositions`). Do not version-gate the seeding — an upgraded and a fresh database must reach
the same end state.

## Tasks

1. **`Core.lua` — add the registry.**
   *Read first:* `Core.lua`, `TerribleBuffTracker.toc` (confirm `Core.lua` loads first).
   Define `ns.CONTAINERS` at the top of the file, immediately after `local addonName, ns = ...` and
   before `ns.activeTimers`, as an ordered array of tables with fields exactly
   `key`, `title`, `frameName`, `kind`, `cdmViewerGlobal`, `defaultX`, `defaultY`, populated from the
   table above in that row order. `kind` is the string `"bar"` or `"icon"` and is what every consumer
   branches on — no consumer may branch on a key string.
   Immediately after, build `ns.CONTAINER_BY_KEY` as a `key -> def` map by iterating `ns.CONTAINERS`.
   Add a short comment stating that `bars`/`buffs` are the v0.3.0 section keys and must never change,
   and that `essential`/`utility` are Phase 40's steal-mode mapping target.
   *Acceptance:* `grep -c 'ns\.CONTAINERS' Core.lua` ≥ 2. All four of
   `"buffs"`, `"bars"`, `"essential"`, `"utility"` appear as `key =` values.
   `grep -n 'TBTBuffContainer\|TBTBarContainer' Core.lua` shows both legacy frame names unchanged.
   `ns.CONTAINER_BY_KEY` is defined in `Core.lua`.

2. **`Core.lua` — drive `containerSettings` from the registry.**
   *Read first:* `Core.lua` lines 35-83 (the `containerSettings` literal and the backfill loop),
   `EditModeFrames.lua` `ns:ShowSettingsPopup` (the setting keys each kind reads).
   Replace the two-key literal and the `for _, key in ipairs({ "bars", "buffs" })` backfill with a single
   registry-driven pass that runs on every load:
   - Ensure `ns.db.containerSettings` is a table.
   - For each `def` in `ns.CONTAINERS`, if `ns.db.containerSettings[def.key]` is nil, create it from the
     kind's default set: **icon kind** = `orientation = 0`, `growthDirection = 0`, `scale = 100`,
     `padding = 5`, `opacity = 100`, `visibility = 0`, `hideWhenInactive = true`, `showTimer = true`,
     `showTooltips = true`; **bar kind** = the same plus `barWidth = 100` and `displayMode = 0`, and with
     `orientation = 1` (bars stack vertically) — these are today's literal values for `buffs` and `bars`
     respectively, copied verbatim, not re-derived.
   - Keep the existing per-field backfill for tables that already exist (`hideWhenInactive`, `showTimer`,
     `showTooltips`, `opacity`, and `displayMode` for bar-kind), now keyed off `def.kind` rather than
     `key == "bars"`.
   Write fresh tables per container — never share one table between two containers, or Phase 36's
   per-container settings would alias.
   *Acceptance:* `grep -n 'ipairs({ "bars", "buffs" })' Core.lua` returns nothing.
   `grep -n 'ipairs(ns.CONTAINERS)' Core.lua` returns at least one hit.
   `grep -n 'containerSettings = {' Core.lua` no longer shows a literal containing `buffs = {`.
   Reading the file shows `barWidth` and `displayMode` are added only under the bar-kind branch.

3. **`BuffEngine.lua` — schema v3 → v4 migration.**
   *Read first:* `BuffEngine.lua` lines 70-122 (`ns:InitBuffEngine` and the three existing migrations),
   `EditModeFrames.lua` lines 9-48 (`ApplyEditModePositions`, the current shape of
   `editModePositions.bars` / `.icons`).
   Set `CURRENT_SCHEMA_VERSION = 4` and replace its stale "v3 is terminal" comment with a one-paragraph
   note that v4 renames the Tracked Buffs position key. Append a fourth block in the same shape as the
   existing three:
   - `if ver < 4 then`
   - if `ns.db.editModePositions` exists: when `.icons` is present and `.buffs` is not, copy `.icons` to
     `.buffs`; then set `.icons = nil` unconditionally.
   - `ns.db.schemaVersion = 4`
   Touch nothing else — `trackedBuffs` entries are not rewritten, because `bars` and `buffs` are already
   the correct section keys. Do **not** seed `essential`/`utility` positions here; Plan 02 seeds any
   missing key idempotently when positions are applied. No `print` (v2 and v3 are silent; only v1 prints).
   *Acceptance:* `grep -n 'CURRENT_SCHEMA_VERSION = 4' BuffEngine.lua` matches.
   `grep -n 'ns.db.schemaVersion = 4' BuffEngine.lua` matches.
   `grep -n 'if ver < 4 then' BuffEngine.lua` matches.
   `grep -c 'editModePositions' BuffEngine.lua` ≥ 1.
   `grep -n 'trackedBuffs' BuffEngine.lua` shows no new occurrence inside the `ver < 4` block.

4. **Format and syntax-check.**
   Run `stylua` from the repo root with no flags, then confirm both edited files parse:
   `luac -p Core.lua BuffEngine.lua` if `luac` is on PATH, otherwise `stylua --check Core.lua BuffEngine.lua`.
   *Acceptance:* `stylua --check .` exits 0 from the repo root, and `git diff --stat` lists only

## Verification

  order buffs, bars, essential, utility.
- `grep -rn '"icons"\|\.icons' Core.lua BuffEngine.lua` — the only hit is inside the `ver < 4` migration.
- `stylua --check .` exits 0.
- No in-game check in this plan. The registry has no user-visible effect until Plan 02 builds frames from
  it.

## Risks

- **A v0.3.0 user who never entered Edit Mode has no `editModePositions` at all.** The migration is
  nil-guarded and becomes a no-op; Plan 02's idempotent seeding gives them all four defaults. Verified by
  reading `ApplyEditModePositions`, which already treats `editModePositions == nil` as the fresh-install
  path.
- **Reordering the registry reorders the CDM tab.** Accepted and intended — the order is the user's, from
  `35-CONTEXT.md`. Default positions are keyed, not ordinal, so no layout moves.
- **`CURRENT_SCHEMA_VERSION` is currently declared and never read.** Leave it that way; updating its value
  keeps it honest. Removing it would be a refactor of pre-existing code, which `PROJECT.md` forbids outside
  a cleanup phase.
