# Phase 35 — Plan 02: Four Edit Mode Containers

**Created:** 2026-09-21
**Requirements:** CONT-01, CONT-02, CONT-03

## Approach

`EditModeFrames.lua` currently names its two containers in fourteen places — creation, positions, save,
handles, selection, lifecycle wiring, the hit test and the visibility checkbox. Every one of those becomes
a loop over `ns.CONTAINERS`. Nothing about *how* a container behaves changes; only the count does.

**New accessors, replacing the six paired fields:**

| old | new |
|---|---|
| `ns.barContainer`, `ns.iconContainer` | `ns.containers[key]` |
| `ns.barOverlay`, `ns.iconOverlay` | `ns.containerOverlays[key]` |
| `ns.barSelectedOverlay`, `ns.iconSelectedOverlay` | `ns.containerSelectedOverlays[key]` |

`Display.lua` still reads `ns.barContainer` and `ns.iconContainer` and is not touched until Plan 04, so
this plan leaves those two names behind as aliases pointing at `ns.containers.bars` / `ns.containers.buffs`.
That keeps the addon loadable and deployable between waves. Plan 04 deletes them.

**Edit Mode labels carry a `TBT ` prefix** — `"TBT " .. def.title`, giving *TBT Tracked Buffs*, *TBT
Tracked Bars*, *TBT Essential Cooldowns*, *TBT Utility Cooldowns*. Blizzard's own CDM systems use exactly
the four unprefixed names in the same Edit Mode screen, so an unprefixed TBT overlay would be
indistinguishable from Blizzard's. This replaces today's `TBT Bars` / `TBT Buffs`. The bare `def.title` is
what the CDM tab uses (Plan 03) — there is no ambiguity there.

**`CONT-01`'s "cannot be renamed or deleted" is satisfied by absence.** This plan adds no rename or delete
affordance and none exists today. Do not add one, and do not add a per-container enable checkbox — the
Edit Mode panel's single `TerribleBuffTracker` checkbox stays addon-wide and continues to govern all four.

**Do not add an example-icon placeholder to the empty icon containers.** `35-CONTEXT.md` lists it under
Deferred Ideas. Empty icon containers already size to 40x40 in `Display.lua`, which is clickable and
therefore draggable; only the *bar* container had the 1px-tall bug that `EXAMPLE_BAR_SLOT` solved in
Phase 34.

## Tasks

1. **Create the four containers and their overlays from the registry.**
   *Read first:* `EditModeFrames.lua` lines 98-140 (`CreateEditModeOverlay`, `CreateSelectedOverlay`) and
   lines 755-786 (`ns:InitEditModeFrames`); `Core.lua` (`ns.CONTAINERS` from Plan 01).
   In `ns:InitEditModeFrames`, initialise `ns.containers`, `ns.containerOverlays` and
   `ns.containerSelectedOverlays` as empty tables, then loop `ipairs(ns.CONTAINERS)`:
   - `CreateFrame("Frame", def.frameName, UIParent)`; `SetFrameStrata("MEDIUM")`;
     `SetClampedToScreen(true)`.
   - Initial size by kind: `bar` → `SetSize(220, 1)`; `icon` → `SetSize(40, 40)`. These are today's
     literals for `TBTBarContainer` and `TBTBuffContainer`, unchanged.
   - `ns.containerOverlays[def.key] = CreateEditModeOverlay(frame, "TBT " .. def.title)`.
   - `ns.containerSelectedOverlays[def.key] = CreateSelectedOverlay(frame)`.
   After the loop add the two temporary aliases `ns.barContainer = ns.containers.bars` and
   `ns.iconContainer = ns.containers.buffs`, with a comment naming Plan 04 as their removal point.
   Leave `ApplyEditModePositions()` and the two `EventRegistry` callbacks where they are.
   *Acceptance:* `grep -n 'CreateFrame("Frame", def.frameName' EditModeFrames.lua` matches.
   `grep -c 'ns.containerOverlays\[' EditModeFrames.lua` ≥ 1.
   `grep -n 'TBTEssentialContainer\|TBTUtilityContainer' EditModeFrames.lua` returns nothing (the names
   come from the registry, not from this file).
   `grep -n 'ns.barSelectedOverlay\|ns.iconSelectedOverlay\|ns.barOverlay\|ns.iconOverlay' EditModeFrames.lua`
   returns nothing.

2. **Apply and save positions per registry key.**
   *Read first:* `EditModeFrames.lua` lines 9-48 (`ApplyEditModePositions`) and 517-535
   (`ns:SaveEditModePositions`).
   Rewrite `ApplyEditModePositions` as: ensure `ns.db.editModePositions` is a table; then for each `def`
   in `ns.CONTAINERS`, if `ns.db.editModePositions[def.key]` is nil, write
   `{ point = "CENTER", relativeTo = "UIParent", relativePoint = "CENTER", x = def.defaultX, y = def.defaultY }`;
   then `ClearAllPoints()` and `SetPoint(...)` from that table. This seeding is idempotent and
   unconditional — it is what gives an upgraded v0.3.0 database its `essential` and `utility` entries
   (Plan 01's migration deliberately does not seed them). Keep the `ns.db.tbtVisible ~= false` block,
   showing or hiding all four in the same loop.
   Rewrite `ns:SaveEditModePositions` to keep its local `ReadPoint` helper unchanged and write
   `ns.db.editModePositions[def.key] = ReadPoint(ns.containers[def.key], def.defaultX, def.defaultY)`
   for each registry def.
   *Acceptance:* `grep -n 'editModePositions.icons\|editModePositions\.bars =' EditModeFrames.lua` returns
   nothing. `grep -c 'editModePositions\[def.key\]' EditModeFrames.lua` ≥ 3.
   `grep -n 'def.defaultX' EditModeFrames.lua` matches in both functions.
   `grep -n '300, 0\|300, -80' EditModeFrames.lua` returns nothing — defaults live only in the registry.

3. **Generalise selection, handles, lifecycle and the hit test.**
   *Read first:* `EditModeFrames.lua` lines 145-184 (selection state), 471-511 (`ShowEditModeHandles` /
   `HideEditModeHandles`), 541-559 (`WireSelectableDrag`), 588-650 (the Edit Mode panel checkbox),
   673-749 (click detector and `OnEditModeEnter` / `OnEditModeExit`).
   - `ns:SelectContainer` / `ns:DeselectContainer`: replace the
     `which == "bars" and ns.barSelectedOverlay or ns.iconSelectedOverlay` ternary with
     `ns.containerSelectedOverlays[which]`, guarding on nil so an unknown key is a silent no-op rather
     than an error. Keep the idempotence guard and the `pcall(EditModeManagerFrame.ClearSelectedSystem…)`
     call exactly as they are — both are Phase 34 behaviour that must not regress. Update the
     `-- "bars" | "buffs" | nil` comment on `selectedContainer` to say it holds any `ns.CONTAINERS` key.
   - `ns:ShowEditModeHandles`: loop the registry. For `bar` kind keep today's floors — height ≥ 30, width ≥
     `ns.db.containerSettings[def.key].barWidth` defaulting to 220. For `icon` kind keep height ≥ 40 and
     width ≥ 40. Then `Show()` the container and its overlay. `HideEditModeHandles` hides all four
     overlays and, when `ns.db.tbtVisible == false`, hides all four containers.
   - `IsMouseOverTBTFrame`: loop `ns.containerOverlays`, keeping the settings-popup check.
   - `OnEditModeEnter` / `OnEditModeExit` and the panel checkbox's on/off branches: replace each pair of
     hardcoded calls with a loop over the registry doing `SetMovable`, `WireSelectableDrag(overlay,
     container, def.key)` on enable, and `SetMovable(false)` plus clearing `OnMouseDown`/`OnMouseUp` on
     disable. `WireSelectableDrag` itself is already per-key and must not change.
   *Acceptance:* a filtered grep finds no legacy field references —
   `grep -v '^\s*--' EditModeFrames.lua | grep -c 'ns\.barOverlay\|ns\.iconOverlay\|ns\.barSelectedOverlay\|ns\.iconSelectedOverlay'`
   returns `0`.
   `grep -c 'ipairs(ns.CONTAINERS)' EditModeFrames.lua` ≥ 5.
   `grep -n 'ns:SelectContainer(containerKey)' EditModeFrames.lua` still matches (Phase 34's mouse-down
   selection intact).
   `grep -n 'DRAG_THRESHOLD\|dragStartX' EditModeFrames.lua` returns nothing.

     *TBT Essential Cooldowns*, *TBT Utility Cooldowns*, with the two new ones stacked below the existing

## Risks

- **`Display.lua` will size only two of the four containers until Plan 04 runs.** Expected: `essential`
  and `utility` keep their 40x40 creation size, which is clickable and draggable, so `CONT-02` is already
  demonstrable at the end of this plan. The two aliases keep the bar and buff render paths working
  meanwhile.
- **`ShowEditModeHandles` floors can be overwritten by the next `UpdateDisplay`** — the Phase 34 lesson
  (`34-01-SUMMARY.md`). It bit the bar container only, whose empty height was 1px; the icon path's empty
  case is `SetSize(40, 40)`. Plan 04 preserves that.
- **`_G[def.cdmViewerGlobal]` may be nil on Forever.** The existing guard prints a message and returns;
  no error. This is a capability check, not a flavour check — no flavour token enters this file.
