# Phase 38 — Plan 02: Cooldown Slot Rendering and the CDM Charge Count

**Created:** 2026-09-21
**Requirements:** CD-02, CD-03, CD-04, CD-05

## Approach

### The render model: a slot, not a timer

Plan 01 established that a cooldown never enters `ns.activeTimers`. `RenderIconContainer` already
collects its slots by walking `ns.db.trackedBuffs` for entries whose `section` matches the container, so
**a cooldown tracker is already in the slot list** — it just currently falls into the placeholder branch
and gets hidden when `hideWhenInactive` is on. This plan gives it its own branch, placed **between** the
timer branch and the placeholder branch:

```
if timer then            -- unchanged; also the PREVIEW path for a cooldown entry
elseif entry.trackerType == "cooldown" then   -- new
elseif not settings.hideWhenInactive or ns.configOpen or iconEditing then  -- unchanged
else icon:Hide()
```

Order matters twice. Before the placeholder branch, so a cooldown icon is **always shown** regardless of
`hideWhenInactive` — the behaviour Blizzard's Essential and Utility viewers have, and the only behaviour
that makes sense for a slot that produces no timers. After the timer branch, so that in preview mode the
synthetic proc Plan 01 now creates for cooldown entries wins and drives
`icon.cooldown:SetCooldown(startedAt, duration)` — a correct demo sweep, with zero type branching, which
is all `CD-05` needs.

### Where the duration handle is set, and how often

In `ApplyCooldownSlot`, behind a two-field guard:

```
if icon._cdGen ~= ns.cooldownGeneration or icon._cdKey ~= entry.key then
```

`ns.cooldownGeneration` advances on `SPELL_UPDATE_COOLDOWN`, `SPELL_UPDATE_CHARGES`, `SPELLS_CHANGED`,
`PLAYER_ENTERING_WORLD`, `PLAYER_REGEN_ENABLED` and a tracked cooldown cast (Plan 01). So
`C_Spell.GetSpellCooldownDuration` is called **on those events only** — roughly once per GCD at worst,
not 20 times a second, and not at all on an idle screen. Between fetches the engine animates the handle
itself. `_cdKey` covers pool reuse: a pooled frame that changes which slot it draws re-fetches even if
no event fired.

Re-setting on every `SPELL_UPDATE_COOLDOWN` rather than once at cooldown start is what delivers
`CD-02`'s live-CDR half. The research records the handle as tracking reduction live on its own, but
`SPELL_UPDATE_COOLDOWN` is precisely the event Blizzard's own `CooldownViewer` re-reads on
(`CooldownViewer.lua:2147`, `:2170`), and re-handing the widget a fresh handle on that event costs one
API call per tracked cooldown per GCD. That is the belt-and-braces the roadmap's "the sweep jumps live,
in combat, with no `/reload`" criterion is worth.

**Nothing is read.** The handle goes straight from `C_Spell.GetSpellCooldownDuration` into
`Cooldown:SetCooldownFromDurationObject`. It is never compared, never concatenated, never indexed, and
no method is called on it. `C_Spell.GetSpellCooldownDuration` is `AllowedWhenTainted` with no secrecy
flag and returns a `LuaDurationObject` — a userdata handle, not a secret value — so the
`SecretArguments` tier never applies to passing it back into a widget setter. Measured on Forever
2026-09-20 in genuinely restricted open-world combat: `Cooldown:SetCooldownFromDurationObject` with a
secret-bearing handle, **ACCEPTED**.

`C_Spell.GetSpellCooldownDuration` is CDM-independent — it takes a spell identifier, has no
`cooldownID` parameter, never touches `C_CooldownViewer` and never consults the CDM's spell table. That
is what makes `CD-04` work: a spell the CDM does not support has no CDM frame, and this call does not
need one.

### Charges, taken from Blizzard's source

`Interface/AddOns/Blizzard_CooldownViewer/CooldownViewer.xml` carries the same charge/stack font string
in three item templates. TBT's `CreateTimerIcon` is already a faithful copy of
**`CooldownViewerBuffIconItemTemplate`** (lines 158-206: `Size 40x40`, `UI-HUD-CoolDownManager-Mask`,
overlay at `-8, 7` / `8, -7`, `reverse="true"`, swipe colour `0,0,0,0.7` — every one of which TBT
already matches), and that template's count font string is:

```xml
<Frame parentKey="Applications" setAllPoints="true">
  <Layer level="OVERLAY">
    <FontString parentKey="Applications" inherits="NumberFontNormal">
      <Anchor point="BOTTOMRIGHT" x="-2" y="2"/>
```

`CooldownViewerEssentialItemTemplate` (lines 54-59) uses the identical construction for its
`ChargeCount.Current`: a `setAllPoints` child **Frame**, an `OVERLAY` `FontString` inheriting
**`NumberFontNormal`**, anchored **`BOTTOMRIGHT, x = -2, y = 2`**. Only the 30x30
`CooldownViewerUtilityItemTemplate` (line 126) differs, using `NumberFontNormalSmall` for its smaller
icon. **TBT's icon is 40x40, the BuffIcon size, so `NumberFontNormal` at `BOTTOMRIGHT (-2, 2)` is the
matching pair** — and it is also what a stolen Essential cooldown will carry when Phase 40 puts one
beside a TBT cooldown in the same container.

The child frame is not decoration: Blizzard creates it **after** the `Cooldown` frame in the same
`<Frames>` block so it draws above the swipe. TBT must create `frame.chargeCount` after `frame.cooldown`
for the same reason, and an `OVERLAY` font string parented directly to the icon frame would be wrong.

**Reading the count safely.** `C_Spell.GetSpellCharges` is `SecretWhenCooldownsRestricted`
(`SpellDocumentation.lua:250-254` — the research doc's table omits this flag; the generated docs are
the ground truth). So in restricted combat the returned struct is readable field by field but every
field is a `SECRET(number)`. Two consequences:

- **The decision of whether to show the count at all is never taken from a secret.** Blizzard's
  `CacheChargeValues` tests `spellChargeInfo.maxCharges > 1`; that comparison throws for a tainted
  caller on a secret. TBT instead keeps a sticky module-level `chargeCapable[spellID]` cache, written
  **only** when `issecretvalue(maxCharges)` is false. Until the answer is readable once — which
  `PLAYER_REGEN_ENABLED`, `PLAYER_ENTERING_WORLD` and `SPELLS_CHANGED` all provide — the count is
  hidden. This is a data-absence check, not a flavour check.
- **The value itself is piped, never inspected.** `chargeCount.Current:SetText(chargeInfo.currentCharges)`
  passes the possibly-secret number straight through, exactly as Blizzard's
  `Current:SetText(self.cooldownChargesCount)` does. `FontString:SetText` is documented
  `SecretArguments = "AllowedWhenTainted"` with `SecretArgumentsAddAspect = { Enum.SecretAspect.Text }`
  (`SimpleFontStringAPIDocumentation.lua:664-673`), and the S2 Forever run measured
  `FontString:SetText` accepting a genuinely secret value. The call is nonetheless wrapped in `pcall`,
  because the measured sample was a secret *string* rather than a secret *number*, and a raise inside
  the render path would take down every container's render, not just one icon. The `pcall` runs only on
  a generation change, never per frame.

Per `38-CONTEXT.md` the count is shown whenever the spell **has** charges (`maxCharges > 1`), and is not
conditionally hidden at one charge.

### `hideWhenInactive` without a per-frame walk

`RenderIconContainer` currently computes `hasActiveIcons = #timers > 0` and hides the whole container
before it ever walks `ns.db.trackedBuffs`. A container holding only cooldown trackers would therefore
hide forever, since cooldowns produce no timers. Moving the slot walk above the visibility test would
fix it — and would also add a full `pairs(ns.db.trackedBuffs)` walk per container per 0.05s tick on the
**hidden** path, which is the common path. That is the regression `CLAUDE.md`'s hot-path mandate exists
to catch.

Instead: a module-level `cooldownSlotCounts` table, rebuilt in one pass only when `ns.trackerGeneration`
(Plan 01) differs from the stamp taken at the last rebuild. `ns:UpdateDisplay` calls the refresher once
per tick, before the container loop; on an unchanged generation that call is a single integer compare
and an immediate return. `hasActiveIcons` then becomes
`#timers > 0 or (cooldownSlotCounts[def.key] or 0) > 0`.

### The three render-path functions still allocate nothing new

`ns:UpdateDisplay`, `RenderBarContainer` and `RenderIconContainer` gain **zero** new table constructors.
`cooldownSlotCounts` is constructed once at module scope and `wipe()`d in place on rebuild, matching the
`pools` / `slots` / `activeByKey` convention already in the file. `chargeCapable` is likewise
module-level. The cooldown branch assigns `icon.proc = entry` — the `ns.db.trackedBuffs` entry itself,
which already carries the numeric `spellID` and `label` that `ns:ShowBuffTooltip` reads — instead of
building the `{ spellID, label, key }` table the placeholder branch builds. The new helper functions are
module-level locals, so calling them allocates no closure.

### Bar containers skip cooldowns

"Cooldowns are icons, never bars" is a locked user decision. `RenderBarContainer`'s placeholder slot
walk gets `and entry.trackerType ~= "cooldown"` added to its `entry.section == def.key` test, so a
cooldown tracker misfiled into a bar container is skipped rather than drawn as a permanently-empty bar.
One extra field comparison per entry, no allocation.

## Risks

- **`FontString:SetText` with a secret *number* is inferred, not measured.** The S2 Forever run measured
  a secret *string* accepted. The generated docs mark `SetText` `AllowedWhenTainted` with
  `SecretArgumentsAddAspect = { Enum.SecretAspect.Text }`, which is exactly the mechanism for piping a
  secret into text, and Blizzard's own `CooldownViewer` passes the raw number. The `pcall` bounds the
  downside to "the charge count stops updating in combat" instead of "every container stops rendering".
  In-game check 4 plus check 7 settle it on Forever; check 4's multi-charge half is also on Phase 44's
  retail list, because the test character on Forever may not have a charge spell — the same gap that
  left `T1.5` unmeasured in the research run.
- **`entry.spellID` could be absent on an entry written before it was stored.** Every entry
  `ns:AddTrackedBuff` has ever written carries `spellID`, and cooldown entries can only come from Phase
  37's dialog, so this cannot occur in practice; the `type(spellID) == "number"` screen in
  `ApplyCooldownSlot` makes it a blank icon with no sweep rather than an error if it somehow does.
- **A cooldown slot is always shown, so a container of cooldowns never auto-hides.** This is the
  intended behaviour and matches Blizzard's Essential/Utility viewers, but it is a visible change for a
  user who expects `hideWhenInactive` to apply to everything. The per-container Visibility setting
  (`Never Show`) still hides it outright, so the user has an out.
- **`SPELL_UPDATE_COOLDOWN` fires for every spell, not just tracked ones.** Each firing invalidates every
  tracked cooldown icon, so the cost scales with the number of cooldown trackers times the GCD rate —
  a handful of `C_Spell.GetSpellCooldownDuration` calls per second at realistic tracker counts. If Phase
  43's hot-path audit finds this material, the fix is a per-spellID stamp rather than a global one; it is
  deliberately not built now, because a global counter has no bookkeeping to get wrong.
