# Phase 38 — Plan 01: Cooldown State, Events and the Two Phase 37 Seams

**Created:** 2026-09-21
**Requirements:** CD-01, CD-04, CD-05, CD-06

## Approach

### How a cooldown is represented, and why it is not a timer

**A cooldown is never a real timer.** No cooldown proc is ever written to `ns.activeTimers`, and
`ns:GetActiveTimers` is not touched by this phase. A cooldown tracker is a **slot** — the
`ns.db.trackedBuffs` entry itself — rendered whenever its container renders, with its sweep driven by a
`LuaDurationObject` handed to the widget. Three reasons, and the first is decisive:

1. **`ns:GetActiveTimers` is built entirely on `proc.expiresAt` being a plain number.** It expires
   entries with `proc.expiresAt <= now` and sorts the flattened list with `a.expiresAt < b.expiresAt`.
   A cooldown's remaining time is a **secret value** in restricted combat — measured 2026-09-20 on
   Forever, every method on the duration handle returned `SECRET(...)`. There is no honest number to put
   in `expiresAt`, and any number we invented would be a lie that the sort and the expiry sweep would
   then act on. The nominal duration the user typed is exactly such a lie: it is blind to cooldown
   reduction, which is the thing `CD-02` exists to get right.
2. **There is nothing for a timer list to add.** A cooldown slot is rendered by Plan 02 whenever its
   container is rendered, running or not — the same behaviour Blizzard's Essential/Utility viewers have.
   A timer entry would only duplicate a slot that is already on screen.
3. **`ScanActiveTimersForCancellation` iterates `ns.activeTimers` and nothing else.** Keeping cooldowns
   out of that table satisfies "do not route cooldowns through the cancellation scan" **by
   construction**, with no guard to add, no guard to forget, and no coupling to
   `C_Secrets.ShouldAurasBeSecret()`.

**The one exception is preview, and it is deliberate.** `ns:StartAllPreviewTimers` writes to
`ns.previewTimers`, which is a separate table full of synthetic demo procs built from data the addon
already owns (`entry.duration`, a number the user typed). No secret is involved, nothing is read from
the game, and the existing `RenderIconContainer` timer branch already turns such a proc into
`icon.cooldown:SetCooldown(startedAt, duration)` — a correct demo sweep for a cooldown icon, for free.
So a cooldown entry takes part in preview like any other entry, and `CD-05` needs no special case at
all beyond deleting the skip.

### The two seams, by name

- **`UserSpellProviderMixin:OnTrigger` (`Providers.lua`)** — the block
  `if entry.trackerType == "cooldown" then return nil end` and its "Phase 38 ... owns cooldown
  rendering" comment. Replaced by a `ns:MarkCooldownsDirty()` call followed by `return nil`: still no
  proc, but the cast now advances the generation counter so the icon re-reads its handle on the very
  next render tick rather than waiting on `SPELL_UPDATE_COOLDOWN`.
- **`ns:StartAllPreviewTimers` (`BuffEngine.lua`)** — the `and entry.trackerType ~= "cooldown"` clause
  and its matching comment. Simply deleted; a cooldown entry now previews like a buff entry.

### Two counters, not one

Plan 02 needs two different invalidations at two different rates, so they get two counters. Merging
them would make the cheap one pay the expensive one's rate.

| Counter | Advanced by | Consumed by (Plan 02) |
|---|---|---|
| `ns.cooldownGeneration` | `SPELL_UPDATE_COOLDOWN`, `SPELL_UPDATE_CHARGES`, `SPELLS_CHANGED`, `PLAYER_ENTERING_WORLD`, `PLAYER_REGEN_ENABLED`, a tracked cooldown cast | per-widget re-fetch of the duration handle and the charge count |
| `ns.trackerGeneration` | `ns:AddTrackedBuff`, `ns:RemoveTrackedBuff`, `ns:SetBuffSection` | rebuild of the per-container cooldown-slot count |

`SPELL_UPDATE_COOLDOWN` fires roughly per GCD in combat. Advancing `ns.trackerGeneration` at that rate
would make Plan 02 walk `ns.db.trackedBuffs` once per container per GCD for a set that only changes when
the user edits their trackers. `PLAYER_REGEN_ENABLED` is on the cooldown list on purpose: it is the
first moment after combat when a charge count that was secret becomes readable again, which is where
Plan 02's sticky charge-capability cache gets its chance to populate.

The three tracker mutation functions are the only choke points that matter — `CDMTab.lua`'s seven
drag-and-drop, context-menu and delete call sites all route through `ns:SetBuffSection` or
`ns:RemoveTrackedBuff`, and `Core.lua`'s `ns:DeleteUserContainer` routes through `ns:SetBuffSection`.
No `CDMTab.lua` edit is needed and none is made.

### Migration (CD-06): nothing to migrate

`entry.trackerType` has been written by `ns:AddTrackedBuff` since Phase 37 and is read in exactly one
shape — `entry.trackerType == "cooldown"`. On an entry written before Phase 37 the field is `nil`, the
comparison is false, and the entry behaves as a buff. That is the whole migration. **`schemaVersion`
stays at 4** and no `ver < 5` block is added, following Phases 35.1, 36 and 37, which all added fields
without a bump; Phase 35 bumped only because it destroyed a key. Task 4 makes this an explicit,
checkable assertion rather than an assumption.

### Add dialog: deliberately untouched

`38-CONTEXT.md` puts the add dialog in Phase 37's scope, not this one. `CDMTab.lua`'s Add button still
requires a Duration for a cooldown tracker, and that number is now the **preview sweep length** — it
drives nothing at runtime, because the game owns the real cooldown. This is a known wart, recorded in
Risks, not fixed here.

## Notes carried in from plan review

- **`CD-01` is inherited, not delivered here.** The add dialog’s buff-vs-cooldown choice shipped in
  Phase 37 (`37-03`); this plan deliberately does not touch `CDMTab.lua`. It is listed in
  `requirements` because this phase is what makes a registered cooldown tracker mean anything, but no
  task here closes it on its own.
- **`SPELL_UPDATE_CHARGES` is a deliberate divergence from Blizzard.** `CooldownViewerCooldownMixin`
  refreshes charge info on `SPELL_UPDATE_USES`, not `SPELL_UPDATE_CHARGES`. Both are real and
  `Blizzard_ActionBar` uses the latter for the same purpose, so this is valid — but add one comment
  line acknowledging the divergence, since this milestone otherwise behaviour-matches the CDM.
- **Do not overstate what `PLAYER_REGEN_ENABLED` buys.** Leaving combat is not reliably “the first
  moment a secret charge count can be read again”: `C_Secrets.ShouldCooldownsBeSecret()` stacks
  encounter, challenge-mode and restricted-map restrictions on top of combat. A player who reloads
  mid-M+ may get no readable moment for the whole run, which keeps the charge text hidden — safe, not a
  crash. Word the comment that way, and flag it for Phase 44’s retail M+ pass.

## Risks

- **`SPELL_UPDATE_CHARGES` may not exist on the Forever client.** Both events appear in Blizzard's
  12.1 source (`Blizzard_ActionBar/Shared/ActionButton.lua:248` for charges, `CooldownViewer.lua:2147`
  for cooldown), but Forever declares interface `16001` and an engine-side symbol present on Midnight
  is explicitly not guaranteed there — `GetScaledCursorPositionForFrame` threw 53 errors in one drag
  session for exactly this reason. `TryRegisterEvent`'s `pcall` makes a missing event a silent
  degradation: `SPELL_UPDATE_COOLDOWN` alone still drives the sweep, and the charge count simply
  refreshes less often.
- **`ns:MarkCooldownsDirty()` is reachable at GCD rate.** It is a single integer increment on a table
  field and allocates nothing, so the cost is a rounding error against the `UNIT_SPELLCAST_SUCCEEDED`
  handler that already runs on the same cast.
- **The add dialog still demands a Duration for a cooldown tracker.** That number now means "preview
  sweep length" and drives nothing at runtime. Left alone deliberately: `38-CONTEXT.md` scopes the add
  dialog to Phase 37. Worth raising with the user before Phase 43 rather than silently redefining a
  field the user believes is the cooldown length.
- **A cooldown tracker assigned to a bar container renders nothing.** The add dialog's container menu
  offers all four containers for either tracker type. Plan 02 makes bar containers skip cooldown
  entries, because "cooldowns are icons, never bars" is a locked decision and drawing a fake bar would
  be worse than drawing nothing. The silence is the accepted cost of honouring that decision.
