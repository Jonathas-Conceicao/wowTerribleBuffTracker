## The three structures that must not be "simplified" (42-CONTEXT.md D5)

This plan touches `Display.lua`'s render path, which is where two of the three live:

1. **`ns:GridSlotPlacement` is the single source of grid arithmetic**, used by both `Display.lua`
   and `MergeMode.lua`. The two drifted three separate times when they each derived it — first by
   padding, then by scale, then by origin. Nothing in this plan may inline, duplicate or
   "specialise" it, and `CenteredSlotPlacement` beside it is not touched either.
2. **`entry.cdmShown` is stamped from Blizzard's own CDM item frames.** It looks like it duplicates
   an aura lookup and does not: the aura APIs are secret in combat and the engine's own visible
   count is unreadable, so the CDM's `IsShown()` is the one plain boolean available. It reaches
   this file as the filter behind `ns.mergeShownSlots`; do not replace a read of that with
   `ns.mergeSlots` or with an aura query.
3. **One aura container per merged entry per unit** (`MergeMode.lua`). Not reachable from this plan,
   but `ns:PlaceMergeAura` is called from `RenderIconContainer`'s engine-draws branch — leave that
   call, its arguments and its `if anchor then` guard exactly as they are.
</constraints>

Three blocks are character-identical between the two render functions. Extract each as a
module-level local above `RenderBarContainer`.

**(a) `MergedSlotsFor(def)` — returns `merged, mergedCount`.**

Both functions open with:

    local merged = ns.mergeShownSlots and ns.mergeShownSlots[def.key]
    local mergedCount = merged and #merged or 0

Return both values (two returns, no table — this runs once per container per tick and must not
allocate). Both call sites keep their two locals and their existing position, immediately before
the visibility gate that reads `mergedCount`.

Move `RenderIconContainer`'s long comment onto the helper: the mirror is built by `MergeMode.lua`'s
event-driven refresh and never rebuilt here, Merge Mode being off leaves it empty so it costs one
index and one `#` with no branch on merge-mode state, and — load-bearing — it is
**`ns.mergeShownSlots`, NOT `ns.mergeSlots`**: the latter is everything the player's CDM has
*configured*, the former only what the CDM currently has *on screen*. Reading the configured set
here is what once put a tracked debuff in TBT permanently instead of only while it was on the
target. `RenderBarContainer`'s shorter "same mirror read as RenderIconContainer" comment is
replaced by a one-line pointer.

**(b) `BuildActiveByKey(timers)` — wipes and fills the module-level `activeByKey`.**

Both functions contain:

    wipe(activeByKey)
    for _, timer in ipairs(timers) do
        activeByKey[timer.key] = timer
    end

Call it at each function's **existing** position — before the slot build in `RenderBarContainer`,
after the slot build and mirror append in `RenderIconContainer`. Do not align them.

Keep the reasoning comment on the helper: the index is the stable provider key, THE slot identity
(string for meta trackers, numeric for user spells), populated by every provider at `OnTrigger`
time.

**(c) `AppendMergedSlots(merged, mergedCount)` — appends into the module-level `slots`.**

Both functions contain:

    if merged then
        for i = 1, mergedCount do
            table.insert(slots, merged[i])
        end
    end

Call it at each existing position: in `RenderBarContainer` after the `showPlaceholders` if/else and
before the `EXAMPLE_BAR_SLOT` check; in `RenderIconContainer` after `table.sort(slots,
ByLayoutOrder)`.

Keep on the helper the contract both call sites currently state: mirrored slots are appended
**after** the sort, never sorted into it, which preserves both the user's own `layoutOrder` and the
CDM's configured order with no `layoutOrder` value to invent for a mirror entry. Leave at the bar
call site its own extra sentence — that the append happens *before* the example-slot check so a
container holding mirrored bars never shows the "Example Buff Name" placeholder. That reason is
specific to the bar path and does not belong on the helper.

Nothing else in either function changes in this task.

| Block | Why it stays split |
|-------|--------------------|
| The visibility gate (`ShouldShow` → `container:Hide()` → `return` → `container:Show()`) | The `hasActive` expression differs substantially: the bar path is `#timers > 0 or mergedCount > 0`; the icon path adds `cooldownSlotCounts[def.key]` (a cooldown slot produces no timer, so a cooldowns-only container would hide forever) and `engineDrawsHere` (aura frames are children of the container, and TBT may not ask how many are visible). It is also an early return, which a helper cannot perform for its caller. |
| The slot build | The bar path branches on `showPlaceholders`, excludes `trackerType == "cooldown"` because "cooldowns are icons, never bars" is locked, and falls back to iterating `timers`. The icon path always walks `ns.db.trackedBuffs` and excludes nothing. Different shape, different predicate. |
| The timer branch of each | The bar branch drives `statusBar` min/max, `SetValue`, `GetBarColor`, `fillTexture`, `pip` and a formatted countdown; the icon branch drives `icon.cooldown:SetCooldown`, `chargeCount`, desaturation and `mergedTime`. Almost nothing in common beyond reading `timer`. |
| The container sizing tail | The bar path computes a 1-D height plus `barWidth`; the icon path computes a 2-D grid with `majorCount` / `minorCount` and an orientation swap. Different arithmetic. |
| The pool-hide tail (`for i = n + 1, #pool do pool[i]:Hide() end`) | Three lines, identical, but it has never drifted and extracting it would add a function call per container per tick in a 20 Hz loop for no drift protection. `ns:UpdateDisplay`'s superficially similar `for i = 1, #pool` loop is a different operation — hide *everything* this container last rendered, not just the tail — and is not a fourth copy. |
| `RenderIconContainer`'s timer-branch icon cache block | See Task 2. Lacks the `cachedIcon == nil` test and the `134400` fallback. Equivalence would rest on a reachability argument rather than on the text, and nothing can test it before Phase 43. |

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| game engine → render path | Aura, cooldown and CDM bar values may be Secret Values under restriction. The render path relays them into setters and must never compare, concatenate or do arithmetic on one. |
| Blizzard CDM frames → TBT | `ns.mergeShownSlots` and `ns.mergeItemFrames` carry data mirrored off Blizzard-owned frames. TBT reads them; it never writes to a CDM frame or calls a CDM mixin method (locked taint decision). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-10 | Tampering | secret values in extracted helpers | mitigate | None of the four helpers compares or computes on an engine value. `MergedSlotsFor` does a table index and a `#`; `BuildActiveByKey` and `AppendMergedSlots` move TBT-owned tables; `ApplyCachedIcon` compares a TBT-resolved numeric `spellID` against TBT's own cache field. `RelayMergedBar`'s relay-only discipline and `bar._lastDuration = nil` are untouched by this plan. |
| T-42-11 | Elevation of Privilege | CDM frame taint | accept | No task adds a call against a Blizzard CDM frame or mixin. `ns:PlaceMergeAura` and its `if anchor then` guard are explicitly out of bounds. |
| T-42-12 | Denial of Service | 20 Hz render loop | mitigate | Helpers are called once per container per tick, never per widget. | T-42-SC | Tampering | npm/pip/cargo installs | accept | No package manager runs in this phase. |
