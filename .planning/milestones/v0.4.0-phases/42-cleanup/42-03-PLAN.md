<task type="auto">
  <name>Task 2: Extract the exclusive-pair wiring into one helper</name>
  <files>CDMTab.lua</files>
  <action>
Four `OnClick` handlers implement the same rule: check yourself, uncheck your partner, so a pair can
never both be off and clicking an already-checked box re-checks it rather than clearing it. The
Buffs/Cooldowns pair additionally calls `ApplyCategory(false)` and `ApplyCategory(true)`
respectively.

Add a module-level local helper above the dialog builder:

    local function WireExclusivePair(first, second, onSelect)

which sets `first`'s `OnClick` to check itself, uncheck `second`, then call `onSelect(false)` if
`onSelect` is non-nil; and `second`'s `OnClick` to check itself, uncheck `first`, then call
`onSelect(true)` if `onSelect` is non-nil.

The boolean argument is chosen so `ApplyCategory` can be passed **directly**, with no wrapper
closure: today `buffsCheck` calls `ApplyCategory(false)` and `spellsCheck` calls
`ApplyCategory(true)`, so `first = buffsCheck`, `second = spellsCheck`, `onSelect = ApplyCategory`
reproduces both calls exactly. This is the reason for the parameter's polarity — do not flip it.

Replace the two wiring blocks **in place**, each where its own `SetScript` pair currently sits:

- Where `iconsCheck:SetScript("OnClick", ...)` / `barsCheck:SetScript("OnClick", ...)` are today:
  `WireExclusivePair(iconsCheck, barsCheck)`.
- Where `buffsCheck:SetScript("OnClick", ...)` / `spellsCheck:SetScript("OnClick", ...)` are today,
  **below** `ApplyCategory`'s definition: `WireExclusivePair(buffsCheck, spellsCheck,
  ApplyCategory)`.

Do not move either call. The Icons/Bars wiring currently sits *above* `ApplyCategory` and must stay
there — `WireExclusivePair` is a module-level local, so it is in scope at both points, and
preserving the textual order keeps the diff reviewable and rules out any question about upvalue
capture.

`ApplyCategory` itself is unchanged. `dialog.ResetChoices` is unchanged — it sets all four boxes
directly and calls `ApplyCategory(false)`, which is correct and is not part of this idiom.
  </action>
  <verify>
    <automated>test "$(grep -c 'local function WireExclusivePair' CDMTab.lua)" -eq 1 && test "$(grep -c 'WireExclusivePair(' CDMTab.lua)" -eq 3 && test "$(grep -c 'WireExclusivePair(buffsCheck, spellsCheck, ApplyCategory)' CDMTab.lua)" -eq 1 && stylua --check .</automated>
One definition and two call sites, with the Buffs/Cooldowns call passing `ApplyCategory` by name
rather than a wrapper.

Then the behaviour argument, which must be made by reading and written into the summary — walk all
five reachable states of the dialog and confirm each is unchanged:

1. Open: Buffs checked, Cooldowns unchecked, Icons checked, Bars unchecked and **enabled**.
2. Click Cooldowns: Cooldowns checked, Buffs unchecked, `ApplyCategory(true)` runs → Icons forced
   checked, Bars unchecked, disabled, label greyed to `0.5, 0.5, 0.5`.
3. Click Buffs: Buffs checked, Cooldowns unchecked, `ApplyCategory(false)` runs → Bars re-enabled,
   label back to `1, 1, 1`. Icons/Bars checked state is deliberately left as it was, exactly as
   today.
4. Click an already-checked box in either pair: it re-checks itself and unchecks its partner — the
   pair can still never both be off.
5. Reopen after a Cooldowns container: `dialog.ResetChoices` restores Buffs + Icons and calls
   `ApplyCategory(false)`, so Bars is enabled again.

Finally confirm `createBtn`'s reads still work: `barsCheck:GetChecked() and "bar" or "icon"` and
`spellsCheck:GetChecked() and "spells" or "buffs"` are untouched, and the persisted category key is
still the literal `"spells"` — renaming it is explicitly deferred (42-CONTEXT.md Deferred Ideas).
  </verify>
