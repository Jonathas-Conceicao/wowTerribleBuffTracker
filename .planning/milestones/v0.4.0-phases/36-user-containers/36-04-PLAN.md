# Phase 36 — Plan 04: CDM-Tab Sections and the Create/Delete UI

**Created:** 2026-09-21
**Requirements:** CONT-04, CONT-05, CONT-07

## Approach

Two jobs, both in `CDMTab.lua`, and they are here together because they are the same file and the second
is meaningless without the first.

**1 — the section lists become rebuildable.** `SECTION_DEFS` and `VALID_DROP_SECTIONS` are built in two
file-scope loops that run at Lua load, before Plan 01 rehydrates user containers. Both are walked every
frame during a drag (`SectionHitTest`, `OnDragUpdate`) and `#SECTION_DEFS` is read by
`ns:UpdateScrollChildHeight`, so they must be **wiped and refilled in place, never reassigned** — the
hot loops hold upvalues to those exact tables. `ns.RebuildContainerSectionDefs()` does that; it is
called once at file scope (replacing both loops) and again from Plan 01's attach/detach dispatch. Its
`{ key, title }` constructors allocate only on rebuild — create, delete and load — never per frame.

Once `VALID_DROP_SECTIONS` includes user keys, **CONT-07 is delivered by machinery that already
exists**: the ghost frame, drop-zone hit test, reorder marker and `layoutOrder` renumbering are
untouched, and the right-click "Move to …" menu already loops `ns.CONTAINERS`.

**2 — create and delete live in the config panel.** Phase 35.1 left `ns.tbtConfigContainerSection`
hidden, empty, terminal in `CreateConfigPanel`, with nothing anchored below it. This plan fills it and
calls `:Show()`. Nothing goes beside the tab's `+` button and nothing goes into Edit Mode — that
placement is a locked user decision.

**There is no rename control.** Not a button, not a double-click handler, not an editable label. A
container's title is set once, in the create dialog, because a section header and an Edit Mode overlay
need something to say. Renaming was explicitly never requested and is not to be added speculatively.

**Base containers provably cannot be deleted, by two independent mechanisms.** The delete rows are
generated from `ns.db.userContainers`, which contains no base record, so no Delete button for a base
container can ever be drawn. And Plan 01's `ns:DeleteUserContainer` rejects any def without
`isUser`, which only `ns:RegisterContainerDef` ever sets. Either alone would be sufficient.

**The confirm dialog names the count first.** A `StaticPopupDialogs` entry whose `text` is exactly
`"%s"`, with the whole message built at show time and passed as the first substitution argument. Two
reasons: it lets one dialog carry both the "N trackers move to Not Displayed" and the "it is empty"
wording, and it keeps the user-supplied container title out of a `format` **format string**, where a
`%` in a title would otherwise throw.

**Section teardown must not truncate the refresh loop.** `ns:RefreshTBTSections` currently does
`if not section then break end`, which would stop the whole loop — silently skipping Not Displayed and
Suggested — the moment a section is missing. Deletion removes sections at runtime, so that `break`
becomes a guarded skip.

## Risks

- **A section removed while a drag is in flight.** `SectionHitTest` and `OnDragUpdate` both already test
  `ns.tbtSections[key]` for existence before use, and `VALID_DROP_SECTIONS` is refilled in the same
  frame the section is removed, so the removed key stops being a candidate immediately.
- **`RelayoutTBTSections` running before the scroll child has a width.** The existing
  `ns.tbtPanel` `OnShow` hook already re-refreshes on `C_Timer.After(0, ...)` for exactly this reason,
  and `RelayoutTBTSections` only sets anchor points, which do not depend on the child's width.
- **A grep-based acceptance criterion invalidated by its own comment.** Phase 35.1 lost two executors to
  this. Every negative gate here is anchored on code shape — a `sed`-scoped function body, a bare
  indented `break`, a call-site pattern — rather than on a bare word that prose could contain. Do not
  write the forbidden token into an explanatory comment; explain the rule without quoting it.
- **`DELETE` / `CANCEL` globals.** Both are FrameXML constants present on retail and on Forever, and the
  `or "Delete"` / `or "Cancel"` fallbacks make the dialog degrade to English rather than to a nil
  button label if a client ever lacks one. This is a capability check, not a flavour check.
