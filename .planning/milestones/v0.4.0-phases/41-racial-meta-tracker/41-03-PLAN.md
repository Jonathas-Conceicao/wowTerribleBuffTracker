# Phase 41 — Plan 03: Racial Tile Presentation & the Add-Flow Escape Hatch

**Created:** 2026-09-21
**Requirements:** RACE-01, RACE-04, RACE-05

## Approach

Plan 01 put `"racial"` in `ns.SUGGESTED_KEYS` and `racial = RacialProvider` in `keyToProvider`, so the
tile already renders through the existing Suggested loop with no new branch — `RACE-01` is mostly
satisfied by registration alone. What this plan adds is the two presentation affordances `RACE-04`
names, and both are written **provider-agnostically**: the CDM tab reads two new optional fields on the
display-info table and never mentions a race, a racial, or a key string.

| field | type | meaning | consumer |
|---|---|---|---|
| `info.unsupported` | `true` / absent | this tile is a known-but-unimplemented thing | desaturation |
| `info.descriptionLines` | array of strings, or absent | tooltip body, provider-owned constant | `extraLines` |

That shape matters: `META_DESCRIPTIONS` is a static CDMTab-local table keyed by the suggested key, which
cannot express "explain yourself differently depending on what resolved". Making the provider the
authority keeps the render path dumb, and matches the established rule that providers self-govern their
own preview safety while the dispatcher stays uniform.

**Desaturation is set on every Suggested tile, not only the unsupported one.** The item frames come from
`section.itemPool`, so a frame that drew the greyed racial tile can be reacquired for Lust on the next
`ns:RefreshTBTSections`. Writing the flag unconditionally makes the render path idempotent; writing it
only on the unsupported branch would leave grey tiles behind after a re-render. The tracked-items branch
clears it for the same reason.

**`RACE-05` needs no new code, and proving that is the deliverable.** `ns:AddTrackedBuff` takes a number
and a duration and files a plain buff tracker; the add dialog passes the typed number straight through;
and Phase 26's `TOOL-01` tooltip post-call already prints `Spell ID: N` on any spell tooltip, so a player
can read their own racial's ID off its spellbook tooltip and type it in. The unsupported tile's tooltip
(Plan 01's `RACIAL_UNSUPPORTED_LINES`) points at exactly that route. Task 3 is an audit that asserts no
racial special case leaked into the add path — which is what would actually break this requirement.

## Risks

- **`SetDesaturated` is a texture method, not a frame method.** It is called on `item.Icon`, which is a
  `CreateTexture` result in `CreateIconFrame`. Calling it on the frame would error.
- **A greyed tile is still draggable and addable.** Deliberate, and consistent with Phase 27's decision
  that an unresolved Trinket/Pot tile stays draggable rather than becoming permanently un-addable. The
  resulting tracker is inert, which is exactly what `RACE-04` asks for.
- **An unsupported racial tracker is stored under the key `"racial"`.** If that character later plays on a
  client or patch where the racial becomes supported, the same key resolves to a working tracker with no
  migration — the entry stores no spell ID, exactly like `"lust"`. No `schemaVersion` bump is needed or
  wanted.
