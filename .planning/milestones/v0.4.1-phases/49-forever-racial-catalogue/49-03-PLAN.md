<objective>
Make the per-racial model visible and usable: per-race Suggested tiles that drop out once tracked,
tracker creation from a racial key, race-gating on every render path, and the migration that moves
existing `racial` / `racial2` entries onto the new keys without losing a placement.

Purpose: this is the rest of **RACE-10** and all of **RACE-08**. 49-01 built the addressing layer
and 49-02 filled the data; nothing is on screen until this plan runs. Three of the phase's eight
success criteria — a player sees their own racials under both tabs, sees no other race's anywhere,
and keeps their existing placements — close here.

Output: one new Suggested loop, one widened `AddSuggestedTracker`, four render-path gates, and a
schema v7 migration.

Locked decisions implemented here, all from **D-4**:

| Aspect | Decision |
|--------|----------|
| Visibility | Only the owning race sees a racial — in Suggested **and** in any container |
| Gating point | Render time, not only Suggested. Gating Suggested alone leaves another race's racials sitting in a container |
| Placement | Account-wide and per racial, which falls out of the existing account-wide DB |
| Drop-out | A tracked racial leaves Suggested, exactly as an `item:` key already does (ITEM-02) |
| Migration | Required, or players lose their placements |

Claude's discretion exercised, per 49-CONTEXT.md: race-gating is implemented as a single predicate
(`ns:IsRacialKeyVisible`, built in 49-01) applied at each of the four walks over
`ns.db.trackedBuffs` that can put something on screen, rather than at DB read. The migration runs
from `ns:InitBuffEngine` and again from `PLAYER_ENTERING_WORLD`, for the reason given in task 3.
</objective>
