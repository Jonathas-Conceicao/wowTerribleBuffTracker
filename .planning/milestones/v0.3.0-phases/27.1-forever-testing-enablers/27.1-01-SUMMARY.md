# Phase 27.1 Plan 01: Forever Testing Enablers (TOOL-01 + PAR-02) Summary

**Registered a shared, existence-guarded spell-tooltip post-call that appends `Spell ID: <n>` to every spell tooltip, and gated `ns:ShowBuffTooltip`'s `SetSpellByID` call on `C_Spell.GetSpellInfo` resolution so unresolvable spells (e.g. Bloodlust on Forever) fall through to a readable label instead of an empty tooltip.**

## Performance

- **Duration:** ~20 min
- **Completed:** 2026-09-18T21:25:46Z
- **Tasks:** 2 completed
- **Files modified:** 2 (`Core.lua`, `Display.lua`)

## Accomplishments

- TOOL-01: a single top-level existence-guarded `if` in `Core.lua` registers one spell-only `TooltipDataProcessor.AddTooltipPostCall` handler that reads `tooltipData.id` directly (no API round-trip) and appends a grey `Spell ID: <n>` line — this is what the user needs to discover Forever spell IDs to type into TBT's Add dialog.
- PAR-02: `ns:ShowBuffTooltip` now probes `C_Spell.GetSpellInfo(spellID)` exactly once and only takes the `SetSpellByID` branch when it resolves; otherwise it falls through to the pre-existing `SetText(proc.label)` path. This fixes the empty Lust tile tooltip found on Forever (`2825` does not resolve there) without touching `LustProviderMixin`.
- Resolved the one non-obvious interaction the planner flagged: `SetSpellByID` now also fires the new post-call, which would have produced two identical `Spell ID:` lines on every CDM grid tile whose spell resolves. TBT's own line is now conditional on `not spellResolves`.

## Files Created/Modified

## Planner Findings — Confirmed

All four planner findings were confirmed by direct source reading before implementation, with no contradictions found:

1. **Post-call handler signature is `function(tooltip, tooltipData)`.** Confirmed in `wow-ui-source/.../TooltipDataHandler.lua`: `ProcessTooltipPostCalls(tooltipType, self, tooltipData)` → `ProcessSecureCalls(tbl, canTerminate, keyType, ...)` strips `keyType` → `MakeSecureCalls` calls `func(...)`, i.e. `func(self, tooltipData)`. `tooltipData.id` confirmed as the correct field via `TooltipUtil.GetDisplayedSpell` (`TooltipUtil.lua:25-31`), which reads `tooltipData.id` directly.
2. **No manual `tooltip:Show()` needed.** Confirmed: `ProcessInfo` (`TooltipDataHandler.lua:280-302`) calls `ProcessTooltipPostCalls(...)` then `self:Show()` on the next line.
3. **TOOL-01 would duplicate TBT's own `Spell ID:` line without de-duplication.** Confirmed: both `CDMTab.lua` `ShowBuffTooltip` call sites pass `showSpellID = true`/`showSpellID = type(info.spellID) == "number"`; bar and icon `OnEnter` handlers pass no `opts` at all and were never at risk. Resolved per the plan's specified approach (see Decisions).
4. **`C_Spell.GetSpellInfo` is the correct resolution probe.** Confirmed `LustProviderMixin:GetDisplayInfo` (`Providers.lua:573-589`) already calls `C_Spell.GetSpellInfo(lustSpellID)` and defaults `spellID` to `2825` when the class map misses — the exact code path PAR-02 guards. `C_Spell.DoesSpellExist` was not used, per the plan's explicit instruction (its Forever behavior is unverified).

## Decisions Made

- **De-duplication split (Claude's discretion, not a locked CONTEXT.md decision):** TBT's own `Spell ID:` line fires only when `not spellResolves`, letting the global post-call own the line whenever `SetSpellByID` actually renders the spell natively. The user may want to revisit this split later — for example, always showing TBT's line regardless of the post-call, if the visual duplication turns out to be acceptable or even useful for confirming both mechanisms agree.
- Spacer bookkeeping now follows `addedIDLine` (a runtime fact) rather than `opts.showSpellID` (a request), since the two can now diverge when a spell resolves but the caller requested `showSpellID`.
