<objective>
META-01: hide a Suggested meta tile when none of the spells in that provider's catalog resolve on the current client. Data-driven, with no flavor detection of any kind — the user was offered an explicit flavor guard and chose this instead, and `REQUIREMENTS.md`'s Out of Scope table bars the flavor branch outright.

The load-bearing distinction (D-09): the test is **"does any spell in this catalog resolve?"**, not **"is anything equipped or bagged?"**. On retail, `TRINKET_SPELLS`, `POT_SPELLS` and the lust buff family all resolve through `C_Spell.GetSpellInfo` even on a naked fresh alt, so all three tiles stay visible and draggable and Phase 27's D-04 (both tiles must remain addable) is preserved exactly. On Forever, where the live session proved `C_Spell.GetSpellInfo(2825)` returns nil, none resolve and all three tiles disappear from the Suggested section.

Purpose: the three meta tiles can never carry a value on a client that has none of their spells, and the user asked for them gone rather than carrying a permanent question mark. Framing it as *unresolvable* rather than *Forever* means a future Forever build that ships lust spells makes the lust tile return by itself, with no code change (D-12) — which is precisely why this beats a flavor guard.
Output: two single-file commits (`Providers.lua`, then `CDMTab.lua`), both stylua-clean with CRLF preserved, proven by static gates only.
</objective>

<planner_findings>
Established by direct code reading during planning. Confirm each in the task that depends on it and carry all six into the SUMMARY.

1. **There is exactly one place the Suggested tiles are rendered: `CDMTab.lua:714-728`,** inside `ns:RefreshTBTSections`'s `if def.key == "suggested"` branch. The two other `ns.SUGGESTED_KEYS` readers (`CDMTab.lua:135` and `CDMTab.lua:516`) are the add-from-Suggested paths — the right-click context menu and the drag-drop handler — and both are only reachable *from a rendered tile*. They therefore need no gate, and adding one there would be both dead code and a risk: it could block a user who already holds that key in `trackedBuffs` from moving their own entry between sections. Gate the render site only; leave both add paths byte-unchanged.

2. **`ns:StartAllPreviewTimers` (`BuffEngine.lua:268`) iterates `ns.db.trackedBuffs`, not `ns.SUGGESTED_KEYS`.** So hiding a tile has no effect on preview timers, and a hidden-but-tracked key still previews exactly as it does today. That is consistent with D-11 (user data untouched) and means this plan needs no `BuffEngine.lua` change.

3. **The one-shot memo cannot mis-fire early.** The first call to the resolver happens when the Suggested section first renders, which is inside `ns:RefreshTBTSections` — reached only from `StartPreview` on CDM open, or from a user drag/menu action. Both are long past `PLAYER_ENTERING_WORLD` and are user-triggered, so the client's spell database is fully available by then. A sticky one-shot cache is therefore safe and no invalidation hook is needed; adding one would be unreferenced code that Phase 30's dead-code sweep would immediately flag.

4. **`SHARED_LUST_BUFFS_LOCAL` (`Providers.lua:223-229`) is already the lust catalog** — it maps each primary lust buff to its shared-`Sated` family variants, covering `32182`, `1243972`, `2825`, `264667`, `466904`, `80353` and `390386`. That is a strict superset of the spells `LustProviderMixin:GetDisplayInfo` can name (the `CLASS_LUST_SPELL` map plus both `GetHunterLustSpell` returns). Use it; do not invent a fourth data table and do not hardcode a new ID list. It is declared at file scope above the mixins, so a method defined near line 570 closes over it fine.

5. **`CDMTab.lua` currently references no spell API and no catalog table at all** — `grep -cE 'C_Spell|TRINKET_SPELLS|POT_SPELLS' CDMTab.lua` is 0 today, because Phase 23 routed every icon/label/tooltip resolution through `ns:GetDisplayInfoForKey`. That makes "still zero" a meaningful, non-vacuous gate that the catalog walk did not leak into the UI layer, and it is why the new accessor belongs in `Providers.lua` beside `ns:GetDisplayInfoForKey` rather than in `CDMTab.lua`. Related: `item.suggestedIndex` is set at `CDMTab.lua:725` and read nowhere — it is a D-13 artifact. Keep setting it to the `ns.SUGGESTED_KEYS` index `i` and leave it for Phase 30 to judge; do not repoint it at the new layout counter and do not delete it in this plan.

6. **Line endings never reach the commit, and `CDMTab.lua` is LF on disk today — both verified empirically during planning.** `core.autocrlf=true` with no `.gitattributes`, so `git ls-files --eol` reports `i/lf` for every Lua file and git normalises the working tree to LF before hashing: converting a file's endings produces a literally empty `git diff` (tested by converting `CDMTab.lua` and observing an empty `--numstat`, then restoring it). Two consequences. First, the numstat gates in this plan are bounds on the size of the *content* change; they cannot detect a line-ending reflow, so passing `--line-endings Windows` is a discipline the executor must keep, not something a gate polices. Second, `Providers.lua` is `w/crlf` on disk but `CDMTab.lua` is `w/lf` — a bare `stylua` was run on it at some point — so `--line-endings Windows` will additionally convert `CDMTab.lua` to CRLF, bringing it in line with the rest of the tree at zero cost to the commit. That is expected and correct; do not try to avoid it, and do not `--line-endings Unix` it to preserve the anomaly. `EditModeFrames.lua` is `w/lf` for the same reason and is out of scope for this phase — leave it alone.
</planner_findings>
