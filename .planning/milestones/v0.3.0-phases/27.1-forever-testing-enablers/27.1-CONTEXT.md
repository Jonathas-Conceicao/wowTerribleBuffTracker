<decisions>
## Implementation Decisions

### TOOL-01 — spell ID in game tooltips

- **D-01:** Implement via `TooltipDataProcessor.AddTooltipPostCall(Enum.TooltipDataType.Spell, handler)`. **Verified present on Forever** at `Interface/AddOns/Blizzard_SharedXMLGame/Tooltip/TooltipDataHandler.lua:199` on the `forever-beta` branch, and on retail 12.1 in the local clone at the same path. One shared implementation, both flavors, **no flavor branch** — the cross-flavor constraint holds.
- **D-02:** Scope is spell tooltips only. Do **not** add item, aura, or unit tooltip handlers — the user's need is discovering castable spell IDs for the Add dialog.
- **D-03:** Append a line in TBT's existing tooltip style: `Spell ID: <n>` in grey `0.8, 0.8, 0.8`, matching `ns:ShowBuffTooltip`'s existing formatting at `Display.lua:83`. Consistency over novelty.
- **D-04:** Read the spell ID from the tooltip data the post-call handler receives, not from a separate API round-trip. `TooltipUtil.GetDisplayedSpell(tooltip)` exists on Forever if a helper is preferred.
- **D-05:** Guard the whole registration behind an existence check (`if TooltipDataProcessor and TooltipDataProcessor.AddTooltipPostCall then`). Cheap, and it means a future flavor lacking the API degrades to no-op instead of a load error. This is a capability check, **not** a flavor check — permitted.
- **D-06:** Always on, not debug-gated. The user chose "add to v0.3 as a testing enabler" over the debug-gated option. It is a small, genuinely useful feature that many buff addons ship.
- **D-07:** New file vs existing: put it in `Core.lua` if it is a handful of lines near init, or a small dedicated section. Do **not** create a new Lua file — that would mean touching both TOCs, and the drift guard treats TOC file lists as required-identical. Adding a file is allowed but must update both TOCs; prefer avoiding it.

### META-01 — data-driven meta tile hiding

- **D-08:** **No flavor detection.** `REQUIREMENTS.md`'s Out of Scope table bars `WOW_PROJECT_ID` branching and `PROJECT.md`'s constraints bar flavor-forked source. The user was offered an explicit flavor guard and chose the data-driven route instead.
- **D-09:** The test is **"does any spell in this provider's catalog resolve on this client?"** — not "is anything equipped/bagged". That distinction is load-bearing:
  - On **retail**, `TRINKET_SPELLS` / `POT_SPELLS` / the lust spells resolve via `C_Spell.GetSpellInfo` **even when the player has nothing equipped**, so all three tiles stay visible and draggable. Phase 27's D-04 is preserved.
  - On **Forever**, none resolve, so all three hide.
- **D-10:** Resolve the catalog check **once and cache it**, not per-render. The Suggested section redraws on every CDM open; iterating three spell catalogs per redraw is needless work in a UI path. A one-shot check at first use, or alongside the existing `RefreshAtRest` combat-gated refresh, is right.
- **D-11:** Hiding means the tile is **not rendered in the Suggested section**. It does not mean deleting user data — if a user somehow has a meta key in `trackedBuffs`, that entry is left alone. This phase touches the Suggested catalog display only.
- **D-12:** Keep the mechanism honest in naming and comments: this hides *unresolvable* tiles, and Forever is merely the case where that currently happens. A future Forever build that ships lust spells would make the lust tile reappear automatically, which is the desired behaviour and the reason this beats a flavor guard.

### PAR-02 — lust empty tooltip

- **D-13:** Root cause, traced: `LustProviderMixin:GetDisplayInfo` (`Providers.lua:~573`) always returns a numeric `spellID`, defaulting to `2825` (Bloodlust) when the class map misses. `ns:ShowBuffTooltip` (`Display.lua:75-79`) therefore takes the `GameTooltip:SetSpellByID(2825)` branch. On Forever that spell does not exist, `SetSpellByID` populates nothing, and `GameTooltip:Show()` renders an empty tooltip.
- **D-14:** Fix in `ns:ShowBuffTooltip`, not in `LustProvider`. Verify the spell resolves before taking the `SetSpellByID` branch; otherwise fall through to the existing `SetText(proc.label)` path, which already produces a readable tooltip. One narrow defensive read at a single site, benefiting every caller.
- **D-15:** Do **not** change `LustProviderMixin:GetDisplayInfo` to return a nil `spellID`. It is correct for it to name its class-appropriate lust spell; the display layer is the right place to cope with a spell the client cannot resolve. Changing the provider would also break retail's lust tooltip, which works today.
- **D-16:** With META-01 in place the lust tile will be hidden on Forever anyway — but fix this regardless. The same code path is reachable on retail for any spell the client cannot resolve, and a defensive read at a shared handler is cheap insurance.

### Cross-cutting

- **D-17:** `stylua --line-endings Windows <file>` after edits. A bare `stylua` reflows the whole file to LF (tree is CRLF, `core.autocrlf=true`, no `stylua.toml`).
- **D-18:** Zero flavor-detection tokens introduced. A grep gate for `WOW_PROJECT_ID|GetBuildInfo|IsTestBuild` must stay at zero matches.
- **D-19:** If a new Lua file is added (discouraged, D-07), **both** TOCs must be updated identically or `scripts/check-toc.ps1` will fail the next release.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ns:ShowBuffTooltip` already implements the exact `Spell ID: <n>` line TOOL-01 should match (`Display.lua:83`), including the grey colour. Reuse the format string style, not the function — that one is for TBT's own tiles.
- `134400` is the established question-mark fallback (`BuffEngine.lua:126`, `:132`; `CDMTab.lua:409`).
- `ns.SUGGESTED_KEYS` is the ordered list driving the Suggested section; META-01's filter hooks its readers rather than inventing a parallel list.

### Established Patterns
- **Capability checks, not flavor checks.** The codebase already guards secret-value APIs behind `C_Secrets` existence/behaviour rather than flavor identity. D-05 follows that precedent.
- **Combat-gated refresh:** `ns:RefreshProvidersAtRest` wraps provider `RefreshAtRest` with an `InCombatLockdown()` gate. META-01's cached catalog check can ride alongside it (D-10).
- **No per-render allocation in UI paths** — CLAUDE.md's standing hot-path rule, and the reason D-10 requires caching.
- Providers stay UI-agnostic; Display derives presentation. D-15 respects that boundary by fixing the display layer.

### Integration Points
- TOOL-01 is additive and touches nothing existing — a registration plus a handler.
- META-01 filters at the Suggested-section render sites in `CDMTab.lua`; it must not alter `trackedBuffs` (D-11).
- PAR-02's fix is one conditional inside `ns:ShowBuffTooltip`, benefiting bars, icons, and CDM tiles at once.

</code_context>
