<planner_findings>
Established by direct source reading during planning — from the local read-only `wow-ui-source` clone and from this repo. Confirm each in the task that depends on it; carry all five into the SUMMARY.

1. **The post-call handler signature is `function(tooltip, tooltipData)`.** `TooltipDataHandler.lua:298` calls `ProcessTooltipPostCalls(tooltipType, self, tooltipData)`; `ProcessSecureCalls(tbl, canTerminate, keyType, ...)` strips `keyType` and `MakeSecureCalls` forwards the remainder as `func(...)`. So the handler receives the tooltip frame first and the tooltip data table second. The spell ID is `tooltipData.id` — the same field `TooltipUtil.GetDisplayedSpell` reads at `TooltipUtil.lua:25-31`. Reading it directly satisfies D-04 with no round-trip; `GetDisplayedSpell` would additionally call `C_Spell.GetSpellName`, which is pointless work and, on Forever, an extra call on a data set we know is different.

2. **No manual `tooltip:Show()` is needed.** `TooltipDataHandlerMixin:ProcessInfo` calls `self:Show()` on the line immediately *after* `ProcessTooltipPostCalls` (`TooltipDataHandler.lua:298-300`), so a line added inside the post-call is included when the tooltip sizes itself. Do not add a `Show()` call — it would be redundant work on every spell hover.

3. **TOOL-01 will duplicate TBT's own `Spell ID:` line unless PAR-02's task de-duplicates it. This is the one non-obvious interaction in the plan.** `GameTooltip:SetSpellByID` is a `SharedTooltipDataMixin` setter wired to `GetSpellByID` (`TooltipDataHandler.lua:560`), so it routes through `ProcessInfo` and fires the new post-call. `CDMTab.lua:89` and `CDMTab.lua:112` both call `ns:ShowBuffTooltip` with `showSpellID = true`, and `Display.lua:83-84` then adds its own `Spell ID: <n>` line — producing two identical lines on every CDM grid tile whose spell resolves. Resolution (Claude's discretion; `27.1-CONTEXT.md` does not cover it): Task 2 makes TBT's own line conditional on the spell *not* resolving, so the post-call owns the line for resolvable spells and TBT owns it for unresolvable ones. Exactly one line in both cases, and the unresolvable case — a Forever lust tile showing `Spell ID: 2825` next to a readable label — is strictly more useful than today's empty tooltip. Bars and buff icons (`Display.lua:193`, `:242`) pass no `opts` at all, so they gain the line from the post-call and were never at risk of duplication.

4. **`C_Spell.GetSpellInfo` is the right resolution probe, and it is already proven on Forever.** `BuffEngine.lua:124-133` (`ns:GetSpellIcon`) and `Providers.lua:583` both use it, and the live session's question-mark icon on all three meta tiles is the evidence that `C_Spell.GetSpellInfo(2825)` returns nil on Forever — that nil is precisely the discriminator PAR-02 needs. Do **not** reach for `C_Spell.DoesSpellExist`: its presence and behaviour on Forever are unverified, whereas `GetSpellInfo`'s nil-on-Forever behaviour is established by observation.

5. **Line endings never reach the commit — verified empirically during planning, and the reason the numstat gates are size bounds, not line-ending detectors.** `core.autocrlf=true` with no `.gitattributes`, so `git ls-files --eol` reports `i/lf` for every Lua file: git normalises the working tree to LF when hashing, and converting a file's endings produces a literally empty `git diff`. `Core.lua` and `Display.lua` are both `w/crlf` on disk today, so `--line-endings Windows` is a no-op for them and simply keeps them that way (D-17). Two related facts to know but not act on: `CDMTab.lua` and `EditModeFrames.lua` are `w/lf` on disk right now, evidence that a bare `stylua` was run on them at some point — `CDMTab.lua` belongs to plan `27.1-02`, `EditModeFrames.lua` belongs to nothing in this phase, and neither may be touched here.
</planner_findings>

| Boundary | Description |

| Blizzard tooltip data → TBT's post-call handler | `tooltipData` arrives from the game's tooltip pipeline. TBT does not control its shape, and on Forever the pipeline is a different build of the same code. Every field read must be existence- and type-checked before use. |
| a numeric spellID in TBT's own data → the client's spell database | TBT stores and passes spell IDs as plain numbers (from `UNIT_SPELLCAST_SUCCEEDED`, from static catalogs, from user input in the Add dialog). A number being present is not evidence the client can resolve it. This is exactly the boundary PAR-02 was crossing unguarded. |
| TBT's registered handler → every spell tooltip in the game UI | The post-call runs on tooltips TBT does not own, including Blizzard frames and other addons' anchored tooltips. A handler error here surfaces as a Lua error attributed to TBT on an unrelated hover. |
| a Forever client's API surface → this shared source set | Forever runs a different build. Any symbol TBT calls unguarded that is absent there is a load-time or hover-time error, with no flavor branch permitted as a workaround. |
