<upstream_facts>
Facts established by reading `BigWigsMods/packager`'s `release.sh` at `master` during
planning. Cited line numbers are from that file. **Read this block before touching
`release.yml` — it contains the one correction this plan makes to CONTEXT.md.**

1. **`-m <file>` sets the pkgmeta file** (`release.sh:348`). **`-n <template>` sets the
   zip name template**; `{game-type}` is substituted with the shell variable `game_type`
   verbatim (`release.sh:166`).

2. **The `ignore` list only governs what gets copied into the zip.** `parse_ignore`
   feeds `copy_directory_tree`'s `_cdt_ignored_patterns`, which sets `_cdt_skip_copy`
   per file (`release.sh:1157`, `1852-1861`). It has **no effect on TOC discovery**.

3. **TOC discovery globs the source checkout unconditionally.** The loops at
   `release.sh:1401` and `1419` iterate `$topdir/$package{_Mainline,_Camelot,…}.toc` and
   append every file that exists to `toc_paths`. Both flavor TOCs are always found.

4. **Each TOC's own `## Interface:` becomes its root interface** (`release.sh:1217`):
   `_Mainline.toc` → `120100`, `_Camelot.toc` → `16001`.

5. **`set_build_version` aggregates across all of `toc_paths`** into the associative
   array `game_type_version` (`release.sh:1339-1367`). `toc_to_type` maps `120100`→
   `retail` and `16001`→`forever` (`release.sh:211-219`). So `game_type_version` ends up
   with **two** keys.

6. **`game_type` is auto-derived only when exactly one game version was found**
   (`release.sh:1380-1383`): `if [[ -z $game_type && ${#game_type_version[@]} -eq 1 ]]`.
   With two keys, that guard fails and **`game_type` stays empty**.

7. **`-g` accepts the flavor names directly** (`release.sh:293-296`): `-g mainline` →
   `game_type=retail`, `-g camelot` → `game_type=forever`. With `game_type` set,
   `set_build_version`'s filter at `release.sh:1336` narrows `game_version` to that one
   flavor — which is what produces a correct per-upload game-version tag.

8. **`-g` does not remove the other flavor's TOC from the zip.** It only adds *content*
   filters to TOC/XML files (`release.sh:1930-1950`). Flavor purity of the zip comes
   from the `ignore` entry and nothing else.

9. **Dotfiles are pruned from the copy tree before the ignore list is consulted**
   (`release.sh:1829`: `\( -name ".*" -a ! -name "." \) -prune`). So `.pkgmeta*` and
   `.gitignore` never ship regardless of whether they are listed under `ignore`; those
   entries are hygiene, not behavior.

### The correction: D-04 is inverted, and `-g` must be passed

CONTEXT.md D-04 says *"because each build then sees exactly one TOC, the packager derives
that build's game version from it — `-g` is unnecessary and must not be passed."*

Facts 2, 3 and 5 show the premise is false. Each build's **zip** sees one TOC; each
build's **metadata pass** sees both, because the metadata pass reads the checkout, not
the staged copy. Concretely, with `-g` omitted:

- `game_type` is empty (fact 6), so `{game-type}` expands to the empty string (fact 1),
  so **both jobs emit an identically-named `TerribleBuffTracker-<version>-.zip`** — the
  two assets collide on one release. `max-parallel: 1` does not help: the collision is
  in the *name*, not the timing. That is DIST-03 and DIST-05 failing.
- `game_version` is `12.1.0,1.60.1`, so **each upload would be tagged for both game
  versions** (fact 5 vs. fact 7). That is DIST-06 failing.

So `-g` is not "a redundant second source of truth for the same fact." It is the *only*
source of truth for `game_type`, which the `ignore` list provably cannot reach. The two
mechanisms are orthogonal and both are required:

| Mechanism | What it buys | Requirement |
|---|---|---|
| `ignore: the other flavor's TOC` | the zip contains only its own TOC | DIST-04 |
| `-g mainline` / `-g camelot` | correct `{game-type}` in the zip name, and a single correct game-version tag per upload | DIST-03, DIST-06 |

**This plan therefore passes `-g`, overriding D-04 as literally written.** This is
flagged, not silent: it is Deferred Question 1 in `<deferred_verification>`, and
reverting it is a single-token deletion in one line of `release.yml`. It is called out
because honoring D-04's literal text would ship a release that provably clobbers one of
its own two assets — the exact outcome D-07 was reasoning about.
</upstream_facts>
