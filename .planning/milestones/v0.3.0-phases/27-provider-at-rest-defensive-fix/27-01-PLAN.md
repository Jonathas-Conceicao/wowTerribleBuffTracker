<objective>

Output: One `Providers.lua` commit, stylua-clean, plus a grep-gated static proof that all four sites are gone and that none of the phase's invariants were violated.

<planner_findings>
These were established by direct code reading during planning. They correct or extend `27-CONTEXT.md`; the executor should confirm each in Task 1 before implementing and carry all three into the SUMMARY.

1. **`27-CONTEXT.md` D-08 is wrong that "consumers already tolerate" a nil `duration`.** `BuffEngine.lua:281-286` does `if info then` … `expiresAt = now + info.duration`. A nil `duration` there is an arithmetic error on a nil value, thrown whenever the config window opens with a "trinket" or "pot" entry tracked. The placeholder therefore uses `duration = 0`, not `duration = nil`. This honors D-08's actual intent ("keep the shape identical so no consumer needs changing") — `nil` would have forced a second-file change, `0` does not. `0` is already this codebase's unresolved-duration sentinel: `UserSpellProviderMixin:GetDisplayInfo`'s no-entry branch returns `{ icon = 134400, label = ..., duration = 0, spellID = key }`, and `CDMTab.lua:98` already tests `info.duration and info.duration > 0`. With `duration = 0` the preview timer is inserted at `expiresAt = now` and filtered out one line later by `GetActiveTimers`'s `proc.expiresAt > now` check — the tile shows nothing, which is exactly PAR-01's intent.
2. **`27-CONTEXT.md` D-10's rationale does not hold for the trinket array.** `POT_FALLBACK_ORDER` really is the iteration order of the real bag scan (`Providers.lua:387`). `TRINKET_FALLBACK_ORDER` is not: the trinket scan iterates `INVSLOT_TRINKET1`/`INVSLOT_TRINKET2` and tests set membership in `TRINKET_ITEM_IDS`. Its only two references today are the two sites this plan deletes (lines 299 and 313), so after the fix it is an unreferenced module-local. D-10 is locked and says do not delete it — so keep it, mark it, and hand it to Phase 30's dead-code sweep. Do not delete it in this plan.
3. **`27-CONTEXT.md` D-01's four-site count is confirmed.** Lines 299, 313, 394, 406, all matching `FALLBACK_ORDER[1]`, currently four occurrences. `FindSpellByItemID` resolves them against the same table they came from, so the lookup is guaranteed to succeed — this is why the tile shows a real-looking wrong item rather than failing.
</planner_findings>
