<planner_findings>
Established by direct reading of this repo on 2026-09-18. These are the hypotheses the audit must confirm or refute — do not copy them into the SUMMARY as conclusions without re-deriving them, and do refute any that turn out wrong. Line numbers are as of planning time and will have shifted by −5 in `Providers.lua` after plan 30-01.

1. **The ghost `OnUpdate` looks clean, and the reason is `topLevel` being an upvalue.** `CDMTab.lua:232-245`: the handler body is `local scale = topLevel:GetScale()`, `local x, y = GetCursorPosition()`, `x, y = x / scale, y / scale`, `self:ClearAllPoints()`, `self:SetPoint("TOPLEFT", topLevel, "BOTTOMLEFT", x, y)`. No table constructor, no string work, no closure creation, no varargs. `GetCursorPosition()` returns two numbers (Lua numbers are values, not heap objects) and `GetScale()` is a cheap C accessor. Crucially `topLevel` is captured once inside `GetOrCreateGhostFrame`, which runs only on the first drag of the session — so `GetAppropriateTopLevelParent()` is **not** called per frame. Confirm that capture, because it is the difference between a clean handler and one that calls a resolver 60+ times a second. One honest caveat to record: the capture also means a ghost created in one UI-parent context keeps that parent for the session. That is a correctness observation about the Phase 27.1 fix, not a performance one, and it is **not** to be fixed here.

2. **`ns:IsSuggestedKeyResolvable` does memoise, and it handles the `false` case correctly.** `Providers.lua:689-701`: `local cached = catalogResolvable[key]; if cached ~= nil then return cached end` — the `~= nil` test rather than a truthiness test is what makes a cached `false` stick instead of re-walking the catalog on every redraw, which is exactly the regression D-18 is worried about. The walk itself (`AnyCatalogSpellResolves`, or `LustProviderMixin:HasResolvableCatalog`'s two-level loop over `SHARED_LUST_BUFFS_LOCAL`) runs at most once per key per session. Also confirm the render path is clean: `grep HasResolvableCatalog CDMTab.lua` should find **nothing** — the render loop at `CDMTab.lua:738` goes through the memoised accessor only. Note the one asymmetry: when `keyToProvider[key]` is nil the function returns `true` **without** writing the cache; that is harmless (no walk happens on that branch) but it is a real difference from the cached branch and belongs in the record.

3. **The `RelatedID` closure is created per tooltip hover, and the early-out ordering is what keeps that bounded.** `Core.lua:190-199` defines `RelatedID` *inside* the post-call handler, so one closure is allocated per handled tooltip. Two things make this acceptable under D-17 and both must be verified rather than assumed: the handler is registered for `TooltipDataProcessor.AllTypes` (`Core.lua:165`) but returns at `Core.lua:172-174` when the tooltip is neither spell nor aura — **before** the closure is created — so item, unit and currency tooltips cost three table lookups and zero allocation; and tooltips fire on hover, not per frame. Verify the ordering by line number, not by eye. D-17 wants this said out loud, so say it: one closure plus up to two `pcall`s per spell/aura hover, on a user-paced path, is acceptable, and the `pcall`s are load-bearing because `C_Spell.GetBaseSpell` / `GetOverrideSpell` can reject an ID the client does not fully know.

4. **`UnresolvedDisplayInfo` allocates one small table per call and that is its whole cost.** `Providers.lua:223` returns a fresh four-field literal. Called from `TrinketProviderMixin:GetDisplayInfo` and `PotProviderMixin:GetDisplayInfo` only, on the unpopulated-cache branch — i.e. per Suggested tile per `ns:RefreshTBTSections`, not per frame. On Forever it is not reached at all, since META-01 hides those tiles before `GetDisplayInfo` is called. A shared module-level table would remove the allocation but hand callers a mutable alias, which is a behaviour change and out of scope. Quantify it and accept it; do not change it.

5. **`ShowBuffTooltip` calls `C_Spell.GetSpellInfo` exactly once per invocation.** `Display.lua:83`: the result is stored in `spellResolves` and reused by the `opts.showSpellID` branch rather than probed twice. Its three call sites are the bar `OnEnter`, the icon `OnEnter` (`Display.lua:205`, `:254`) and the CDM settings grid — all hover-driven. Confirm no `OnUpdate` anywhere reaches it.
</planner_findings>
