<planner_findings>
Established by direct reading of this repo on 2026-09-18, before Phase 29 landed. Confirm each against the actual post-Phase-29 state; carry all five into the SUMMARY, marked confirmed or refuted.

1. **`.pkgmeta`'s shared content is very likely irreducible, and the audit's job is to prove that rather than assume it.** The pre-Phase-29 `.pkgmeta` is 18 lines: a three-line comment about CI-generated `RELEASE_NOTES.md`, `package-as`, a `manual-changelog` block, and a nine-entry `ignore` list. Phase 29's plan (`29-CONTEXT.md` D-02, D-05) is for both flavor files to carry all of that identically plus one extra `ignore` line each. The BigWigs packager's pkgmeta format has no include, inherit, merge or extends directive as far as the planner is aware — its accepted keys are `package-as`, `externals`, `ignore`, `plain-copy`, `move-folders`, `required-dependencies`, `optional-dependencies`, `embedded-libraries`, `tools-used`, `manual-changelog`, `license-output`, `enable-nolib-creation` and `enable-toc-creation`. **Verify that against the pinned source** (`29-CONTEXT.md` references `https://raw.githubusercontent.com/BigWigsMods/packager/master/release.sh`) rather than taking the planner's word for it, because the whole conclusion turns on it. If no include mechanism exists, the duplication is structural: unifying it would require generating the two files from a template at release time, which is a new tool and new behaviour. Record the directive list as the evidence and accept the duplication. What *is* worth noting: `check-toc.ps1`'s assertion 3 guards only the cross-ignore lines, so the *shared* `ignore` list can drift between the two files with nothing catching it — `29-CONTEXT.md` itself calls that "the same class of bug as TOC drift". That gap is a todo, not a Phase 30 fix.

2. **`install.bat` is already unified, and the criterion is likely satisfied as-built.** Phase 26 rewrote it as: one `FILES` variable holding the ten-file list, one `FLAVORS` variable holding seven client folder names, one preflight loop over `FILES`, one outer loop over `FLAVORS` containing one inner copy loop, and an `INSTALLED` counter driving the zero-clients error. There is no per-client or per-flavor branch anywhere — no `if retail`, no duplicated copy block. So ROADMAP criterion 2's `install.bat` half is satisfied by construction and the honest audit outcome is "no change needed", recorded with the loop structure as evidence. Do not restructure it to look more unified. The one genuine redundancy is cross-file: the shared runtime file set is listed three times — in `install.bat`'s `FILES`, in `TerribleBuffTracker_Mainline.toc`, and in `TerribleBuffTracker_Camelot.toc`. Removing that would mean `install.bat` parsing a TOC at runtime, which is new behaviour. Todo, not fix. (`check-toc.ps1` assertion 2 already guards the two TOCs against each other; nothing guards `install.bat`'s copy against either.)

3. **`stylua.toml` will ship inside the release zips unless both pkgmeta files ignore it.** Plan 30-01 adds `stylua.toml` at the repo root. The packager includes everything not listed under `ignore`, and the existing list already excludes exactly this class of file — `.gitignore`, the pkgmeta file itself, `CLAUDE.md`, `README.md`, `CHANGELOG.md`, `LICENSE`, `scripts`, `*.png`, `RELEASE_NOTES.md`. Adding `stylua.toml` preserves the existing property that release zips contain only runtime files; it is a correctness follow-on from 30-01, not a new capability. Note `.luarc.json` is untracked so it cannot be packaged, and `TerribleBuffTracker.zip` plus the `#...#` Emacs backups are covered by `.gitignore`.

4. **Two things in `release.bat` will look wrong and only one of them is.** The guard ordering is correct: `check-toc.ps1` is invoked at line 17, its `if errorlevel 1` aborts at 18–21, and `git tag` is at 23 — so a drifted TOC cannot be tagged. Verify that by line number, not by eye. The genuinely questionable part is line 29: `git push origin main "%TAG%"`. The tag is created on whatever `HEAD` the script is run from, but the push targets `main` — so running it from the milestone branch would tag the branch tip and push `main` in the same breath. The project's own release rule (squash-merge to `main` first, never tag from the milestone branch) makes the script correct *when used correctly*, but nothing in the script enforces it. Report that as a finding and a todo. **Do not add the guard** — that is new behaviour, and the current milestone is sitting on exactly the branch where a mistake would hurt.

5. **`release.yml` was still single-job at planning time and Phase 29 is supposed to have changed that.** Pre-Phase-29 it is one `release` job: checkout with `fetch-depth: 0`, an `awk` step extracting the first `##` section of `CHANGELOG.md` into `RELEASE_NOTES.md`, then `BigWigsMods/packager@v2` with no arguments. Phase 29's `DIST-02` (`29-CONTEXT.md` D-06) adds a two-flavor matrix, each job passing `-m .pkgmeta-<flavor>` and `-n` with a `{game-type}` token. Review whatever is actually there against that spec, and pay attention to the `RELEASE_NOTES.md` step: it must run inside each matrix job, since each job checks out fresh and the packager needs the file present. Also note `CF_API_KEY` and `WAGO_API_TOKEN` are commented out in `env:` — that is deliberate (`FTOOL-01` defers re-enabling them) and must **not** be "fixed".
