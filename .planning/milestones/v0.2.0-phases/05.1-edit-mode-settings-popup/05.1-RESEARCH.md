## Summary

Phase 5.1 adds a selection system to TBT's Edit Mode overlays and a settings popup that mirrors Blizzard's `EditModeSystemSettingsDialog`. Because TBT cannot use `EditModeSystemMixin` (requires a server-backed `Enum.EditModeSystem` entry), all of this must be implemented as addon-owned frames.

The key insight from reading Blizzard source is that the `EditModeSystemSettingsDialog` is a **singleton global frame** — it is reused across all system frames and re-populated when a new system is selected. TBT builds its own equivalent popup (a `ResizeLayoutFrame` with `DialogBorderTranslucentTemplate`) that is also a singleton and re-populated when a container is selected. The popup uses the same three Blizzard control templates: `EditModeSettingDropdownTemplate`, `EditModeSettingSliderTemplate`, and `EditModeSettingCheckboxTemplate`.

The selected-state NineSlice uses `editmode-actionbar-selected` as the `textureKit` (filling `%s` in the layout's `atlas` format string). The highlight state uses `editmode-actionbar-highlight`. TBT already has the highlight NineSlice on both overlays; phase 5.1 adds the selected-state overlay (or switches the atlas on click). The popup listens to overlay `OnMouseUp` to detect click-vs-drag, shows the popup for the selected container, and hides it on `EditMode.Exit`.

**Primary recommendation:** Build TBT's own `TBTSettingsPopup` singleton frame (not hooking `EditModeSystemSettingsDialog`), use Blizzard's `EditModeSettingDropdownTemplate`, `EditModeSettingSliderTemplate`, and `EditModeSettingCheckboxTemplate` pools to populate it, and wire `OnMouseUp` on overlays with a drag-threshold guard to differentiate click-vs-drag.

## Architecture Patterns

### Recommended Project Structure

No new files required. All new code goes into `EditModeFrames.lua` (selection logic + popup) and `Display.lua` (reads from DB instead of hardcoded tables). `Core.lua` gains DB init for `containerSettings`.

```
EditModeFrames.lua     -- gains: selection state, selected NineSlice, click-vs-drag detection,
                       --        TBTSettingsPopup singleton frame, pool, populate/hide logic
Display.lua            -- gains: reads cachedBarSettings/cachedIconSettings from
                       --        ns.db.containerSettings instead of module-level hardcoded tables
Core.lua               -- gains: ns.db.containerSettings default init in ADDON_LOADED
```

### Pattern 1: Selected-State NineSlice Atlas

**What:** Blizzard uses a parameterized `EditModeSystemSelectionLayout` where each atlas string has `%s` filled by a `textureKit`. The highlight kit is `editmode-actionbar-highlight`; the selected kit is `editmode-actionbar-selected`. The layout keys match TBT's existing `NINESLICE_LAYOUT` in `EditModeFrames.lua` exactly.

**When to use:** On `OnMouseUp` (non-drag) to switch the overlay to the selected visual.

**Source:** `EditModeSystemTemplates.lua:3062-3113`, `EditModeSystemTemplates.xml:14-15`

```lua
-- Confirmed atlas kit values from EditModeSystemTemplates.xml KeyValues:
--   highlightTextureKit = "editmode-actionbar-highlight"
--   selectedTextureKit  = "editmode-actionbar-selected"

-- NineSlice layout (parameterized) — same structure as TBT's NINESLICE_LAYOUT
-- but uses string.format("%s-NineSlice-Corner", textureKit) etc.
-- TBT can define two static layouts or pass the kit string to a shared apply function.

local SELECTED_NINESLICE_LAYOUT = {
    ["TopRightCorner"]  = { atlas = "editmode-actionbar-selected-NineSlice-Corner",  mirrorLayout = true, x=8,  y=8  },
    ["TopLeftCorner"]   = { atlas = "editmode-actionbar-selected-NineSlice-Corner",  mirrorLayout = true, x=-8, y=8  },
    ["BottomLeftCorner"]= { atlas = "editmode-actionbar-selected-NineSlice-Corner",  mirrorLayout = true, x=-8, y=-8 },
    ["BottomRightCorner"]={ atlas = "editmode-actionbar-selected-NineSlice-Corner",  mirrorLayout = true, x=8,  y=-8 },
    ["TopEdge"]         = { atlas = "_editmode-actionbar-selected-NineSlice-EdgeTop" },
    ["BottomEdge"]      = { atlas = "_editmode-actionbar-selected-NineSlice-EdgeBottom" },
    ["LeftEdge"]        = { atlas = "!editmode-actionbar-selected-NineSlice-EdgeLeft" },
    ["RightEdge"]       = { atlas = "!editmode-actionbar-selected-NineSlice-EdgeRight" },
    ["Center"]          = { atlas = "editmode-actionbar-selected-NineSlice-Center", x=-8, y=8, x1=8, y1=-8 },
}
-- Apply with: NineSliceUtil.ApplyLayout(overlay, SELECTED_NINESLICE_LAYOUT)
```

### Pattern 2: Click-vs-Drag Detection on Overlay

**What:** `OnMouseDown` starts a potential drag. `OnMouseUp` completes it. The trick is distinguishing "clicked" from "dragged" without overcomplicating. Two viable approaches:

**Option A (position threshold — Claude's discretion):** Record `GetCursorPosition()` in `OnMouseDown`. In `OnMouseUp`, compare. If delta < 4 pixels → click. This is simple and reliable.

**Option B (time threshold — Claude's discretion):** Record `GetTime()` in `OnMouseDown`. In `OnMouseUp`, if elapsed < 0.2s → click. Less reliable on slow machines.

Recommendation: **Option A (position threshold)**. Blizzard uses a similar approach in drag systems.

```lua
-- In CreateEditModeOverlay (or new SelectableOverlay creator)
local dragStartX, dragStartY
local DRAG_THRESHOLD = 4  -- pixels

overlay:SetScript("OnMouseDown", function(self, button)
    if button == "LeftButton" then
        dragStartX, dragStartY = GetCursorPosition()
        ns.barContainer:StartMoving()  -- or iconContainer
    end
end)

overlay:SetScript("OnMouseUp", function(self, button)
    if button == "LeftButton" then
        ns.barContainer:StopMovingOrSizing()
        local curX, curY = GetCursorPosition()
        local dx = math.abs(curX - (dragStartX or curX))
        local dy = math.abs(curY - (dragStartY or curY))
        if dx < DRAG_THRESHOLD and dy < DRAG_THRESHOLD then
            -- It was a click — select this container
            ns:SelectContainer("bars")  -- or "buffs"
        end
    end
end)
```

### Pattern 3: TBTSettingsPopup — Singleton Frame with Control Pools

**What:** Mirror `EditModeSystemSettingsDialog` exactly. One singleton popup, re-populated each time a container is selected. Use `CreateFramePoolCollection` with the three Blizzard template pools.

**Source:** `EditModeDialogs.lua:480-686`, `EditModeDialogs.xml:251-327`

```lua
-- In EditModeFrames.lua — module-level singleton
local tbtSettingsPopup = nil

local function CreateSettingsPopup()
    local popup = CreateFrame("Frame", "TBTSettingsPopup", UIParent, "ResizeLayoutFrame")
    popup:SetFrameStrata("DIALOG")
    popup:SetFrameLevel(200)
    popup:SetClampedToScreen(true)
    popup:SetMovable(true)
    popup:RegisterForDrag("LeftButton")
    popup:SetScript("OnDragStart", function(self) self:StartMoving() end)
    popup:SetScript("OnDragStop", function(self) self:StopMovingOrSizing() end)
    popup:Hide()

    -- Translucent border (same as EditModeSystemSettingsDialog)
    local border = CreateFrame("Frame", nil, popup, "DialogBorderTranslucentTemplate")
    -- ignoreInLayout so ResizeLayoutFrame doesn't count it
    border.ignoreInLayout = true

    -- Title
    local title = popup:CreateFontString(nil, "ARTWORK", "GameFontHighlightLarge")
    title:SetPoint("TOP", 0, -15)
    popup.Title = title

    -- Settings container (VerticalLayoutFrame with spacing=2)
    local settings = CreateFrame("Frame", nil, popup, "VerticalLayoutFrame")
    settings:SetSize(1, 1)
    settings:SetPoint("TOP", title, "BOTTOM", 0, -12)
    -- KeyValue spacing=2 must be set programmatically:
    settings.spacing = 2
    popup.Settings = settings

    -- Pool collection — same templates as EditModeSystemSettingsDialog
    popup.pools = CreateFramePoolCollection()
    popup.pools:CreatePool("FRAME", settings, "EditModeSettingDropdownTemplate")
    popup.pools:CreatePool("FRAME", settings, "EditModeSettingSliderTemplate")
    -- Checkbox omitted if not needed for this phase's settings

    tbtSettingsPopup = popup
    return popup
end
```

### Pattern 4: Populating the Popup

**What:** `EditModeSettingDropdownMixin:SetupSetting` and `EditModeSettingSliderMixin:SetupSetting` take a `settingData` table:

```lua
settingData = {
    displayInfo = {
        setting   = <key>,         -- arbitrary key string (not Enum.EditModeSetting)
        type      = "dropdown" | "slider",
        options   = { { text=..., value=... }, ... },  -- for dropdown
        minValue  = <n>,            -- for slider
        maxValue  = <n>,            -- for slider
        stepSize  = <n>,            -- for slider
        formatter = <formatter>,    -- optional; CreateMinimalSliderFormatter
    },
    currentValue  = <value>,
    settingName   = <string>,       -- label text
}
```

**Critical difference from Blizzard:** Blizzard's `SetupSetting` calls `EditModeSystemSettingsDialog:OnSettingValueChanged(self.setting, value)` — this is the global singleton. TBT cannot reuse this callback routing because `EditModeSystemSettingsDialog` is not TBT's popup. TBT must either:

1. **Subclass/override the mixin** — create frames that inherit the template but override the `OnSettingValueChanged` call, OR
2. **Build simpler custom controls** that look identical but wire directly to `ns.db.containerSettings`.

**Recommendation (simpler):** Build custom wrapper functions that create `EditModeSettingDropdownTemplate` and `EditModeSettingSliderTemplate` frames but replace the `OnSettingValueChanged` callback with a TBT-specific closure. The templates provide the visual widgets; TBT provides the callback routing.

```lua
-- After acquiring a dropdown from the pool:
local dropdownFrame = popup.pools:GetPool("EditModeSettingDropdownTemplate"):Acquire()
dropdownFrame.Label:SetText("Orientation")
dropdownFrame.setting = "orientation"
dropdownFrame.layoutIndex = 1

dropdownFrame.Dropdown:SetupMenu(function(dd, rootDesc)
    rootDesc:CreateRadio("Vertical",   function() return currentValue == 0 end,
        function() ns:OnContainerSettingChanged(containerKey, "orientation", 0) end, 0)
    rootDesc:CreateRadio("Horizontal", function() return currentValue == 1 end,
        function() ns:OnContainerSettingChanged(containerKey, "orientation", 1) end, 1)
end)
dropdownFrame:Show()
```

### Pattern 5: Popup Positioning Relative to Container

**What:** Blizzard uses `AnchorUtil.CreateAnchor` and calls `anchor:SetPoint(dialog, clearAllPoints)`. TBT can use a simpler approach: `SetPoint("LEFT", container, "RIGHT", 10, 0)` or `SetPoint("TOP", container, "BOTTOM", 0, -10)` depending on available screen space.

**Recommendation (Claude's discretion):** Anchor to the right of the container (matching typical CDM behavior). If the popup would go off-screen to the right, anchor below instead. Simple screen-edge check using `UIParent:GetWidth()`.

### Pattern 6: Deselection on Click Outside

**What:** Blizzard's `EditModeSystemMixin:OnSystemHide` calls `EditModeManagerFrame:ClearSelectedSystem()` which hides the dialog. For TBT, there is no system manager to call. Instead:

- `EditMode.Exit` → deselect and hide popup (already handled by `ns:OnEditModeExit`).
- Click on the other container → deselect first, select new.
- Click outside both → trickier. Blizzard handles this via `EditModeManagerFrame:SelectSystem(frame)` which replaces the previous selection.

**TBT approach:** Use a single `ns.selectedContainer` variable. When `SelectContainer("bars")` is called, deselect any previously selected container, switch that overlay back to highlight atlas, and select the new one. For click-outside: in `OnMouseUp` only select when `ns.editModeActive` is true and the click was on an overlay. Clicking elsewhere does not call `SelectContainer` so the popup stays open (acceptable, matching Blizzard CDM behavior where the dialog stays until you close it or select a different system).

### Anti-Patterns to Avoid

- **Calling `EditModeSystemSettingsDialog:AttachToSystemFrame(self)`** — requires `self.system`, `self.settingMap`, and other `EditModeSystemMixin` internals. Will crash.
- **Hooking `EditModeSystemSettingsDialog:UpdateDialog`** — this updates Blizzard's own popup when any registered system is selected, not TBT's popup. Hooking it will fire on every CDM element selection.
- **Using `EditModeManagerFrame:SelectSystem(frame)`** — requires the frame to be registered via `RegisterSystemFrame`. TBT containers are not registered. Will crash or silently fail.
- **`SetupSetting` pointing at `EditModeSystemSettingsDialog`** — the acquired dropdown/slider frames call `EditModeSystemSettingsDialog:OnSettingValueChanged` in their `SetupSetting`. If TBT calls the stock `SetupSetting`, it will attempt to route changes through Blizzard's dialog. Always wire callbacks manually after acquiring from the pool.

## Common Pitfalls

### Pitfall 1: Using Stock `SetupSetting` Routes to Wrong Dialog

**What goes wrong:** Acquiring a frame from `EditModeSettingDropdownTemplate` pool and calling `SetupSetting` as defined in `EditModeSettingDropdownMixin`. The mixin's `SetSelected` closure calls `EditModeSystemSettingsDialog:OnSettingValueChanged(self.setting, value)` — which routes to Blizzard's dialog, not TBT's.

**Why it happens:** The mixin is tightly coupled to `EditModeSystemSettingsDialog` (the global). TBT has a separate popup.

**How to avoid:** After acquiring from the pool, set up the `Dropdown:SetupMenu` manually instead of calling `SetupSetting`. The label, dropdown widget, and layout infrastructure are still correct — only the callback changes.

**Warning signs:** Settings appear to have no effect, or Blizzard's CDM selection popup reacts to TBT control interactions.

### Pitfall 2: ResizeLayoutFrame Not Resizing

**What goes wrong:** Popup appears as a tiny dot or wrong size after adding settings frames.

**Why it happens:** `ResizeLayoutFrame` only resizes when children have `layoutIndex` set AND `frame:Layout()` is called after adding them.

**How to avoid:** Assign `layoutIndex = N` (1, 2, 3...) to each settings frame acquired from the pool. Call `popup.Settings:Layout()` and then `popup:Layout()` after populating all controls.

**Warning signs:** Popup has zero/minimal height; settings controls are invisible or clipped.

### Pitfall 3: NineSlice Selected Atlas Missing

**What goes wrong:** The "selected" yellow overlay shows wrong texture or renders white boxes.

**Why it happens:** The `editmode-actionbar-selected` atlas tiles may need `useAtlasSize = false` for stretching edges. The existing `NINESLICE_LAYOUT` in `EditModeFrames.lua` already has the correct structure for `editmode-actionbar-highlight`; `editmode-actionbar-selected` follows the same naming pattern — verify by checking that atlas tiles exist.

**How to avoid:** Apply `SELECTED_NINESLICE_LAYOUT` to a second overlay on top of (or instead of) the highlight overlay. Test in-game before continuing.

**Warning signs:** Yellow border shows incomplete corners or white boxes instead of the atlas art.

### Pitfall 4: Popup Frame Level Too Low

**What goes wrong:** Popup appears under the EditModeManagerFrame or other DIALOG-strata frames.

**Why it happens:** `EditModeSystemSettingsDialog` uses `frameLevel=200` inside `DIALOG` strata. TBT's popup needs a similar level.

**How to avoid:** Set `popup:SetFrameStrata("DIALOG")` and `popup:SetFrameLevel(200)` (or at minimum higher than the EditModeManagerFrame).

**Warning signs:** Popup visible but clicking on it seems to click through to frames behind it; popup disappears behind the Edit Mode UI.

### Pitfall 5: Drag vs Click Ambiguity With StopMovingOrSizing

**What goes wrong:** Every click registers as a drag (no selection), or every drag also selects.

**Why it happens:** `StopMovingOrSizing` in `OnMouseUp` does not know whether actual movement occurred. The cursor position check must happen before `StopMovingOrSizing`, or the test frame's position must be compared before/after.

**How to avoid:** Record `GetCursorPosition()` in `OnMouseDown` and compare in `OnMouseUp` BEFORE calling `StopMovingOrSizing`. Use a module-level `dragStartX, dragStartY` per overlay (since only one can be dragging at a time).

### Pitfall 6: VerticalLayoutFrame `spacing` Is a KeyValue, Not a Method

**What goes wrong:** Setting `frame.spacing = 2` in Lua has no effect on layout.

**Why it happens:** `VerticalLayoutFrame` reads `spacing` as an XML KeyValue, not a runtime Lua field. The Lua field name is `spacing` but it must be set as `frame.spacing` before the first `Layout()` call — this does work for KeyValues that map to simple table fields.

**How to avoid:** After `CreateFrame("Frame", nil, parent, "VerticalLayoutFrame")`, set `settings.spacing = 2` before calling `settings:Layout()` for the first time. This works because Lua-set fields on the frame table are read at layout time.

### Wiring Click-vs-Drag on an Overlay

```lua
-- Source: Pattern derived from CDM drag system in CooldownViewerSettings.lua
-- and Blizzard's own drag detection approach

local function WireSelectableDrag(overlay, container, containerKey)
    local dragStartX, dragStartY
    local DRAG_THRESHOLD = 4

    overlay:SetScript("OnMouseDown", function(self, button)
        if button == "LeftButton" and ns.editModeActive then
            dragStartX, dragStartY = GetCursorPosition()
            container:StartMoving()
        end
    end)

    overlay:SetScript("OnMouseUp", function(self, button)
        if button == "LeftButton" and ns.editModeActive then
            container:StopMovingOrSizing()
            local curX, curY = GetCursorPosition()
            local moved = math.abs(curX - (dragStartX or curX)) >= DRAG_THRESHOLD
                       or math.abs(curY - (dragStartY or curY)) >= DRAG_THRESHOLD
            if not moved then
                -- It was a click — toggle selection
                if selectedContainer == containerKey then
                    ns:ClearSelection()
                else
                    ns:SelectContainer(containerKey)
                end
            end
            dragStartX, dragStartY = nil, nil
        end
    end)
end
```

## Open Questions

1. **Scale slider units — 1.0 vs 100**
   - What we know: DB could store `1.0` (raw) or `100` (percentage). Slider min/max would differ. Display.lua uses `iconScale` as a raw 0–2 float.
   - What's unclear: Which unit is more user-friendly; whether the slider formatter should show "%" suffix.
   - Recommendation: Store as integer percentage (50–200) in DB for slider ease; divide by 100 when reading into `GetBarSettings()`. Use a formatter that appends "%".

2. **Real-time preview vs. on-close apply**
   - What we know: D-04/CONTEXT Specifics suggest real-time preview is desired. The code examples above call `ns:UpdateDisplay()` immediately on each control change.
   - What's unclear: Whether this is fast enough without frame drops (sliders fire on every thumb drag tick).
   - Recommendation: Implement real-time preview. `UpdateDisplay` already runs on `UPDATE_INTERVAL` (0.05s) so the slider's `OnValueChanged` just writes to DB; the next `OnUpdate` tick picks it up naturally. No extra `UpdateDisplay()` call needed if the DB write is immediate.

3. **Slider `OnValueChanged` direct wiring vs. MinimalSliderWithSteppersMixin callback**
   - What we know: The mixin uses `CallbackRegistryMixin` events (`OnValueChanged`, `OnInteractStart`, `OnInteractEnd`) rather than direct `SetScript("OnValueChanged")`.
   - What's unclear: Whether `SetScript("OnValueChanged")` on `frame.Slider.Slider` (the inner `MinimalSliderTemplate`) bypasses the mixin events.
   - Recommendation: Use `self.cbrHandles:RegisterCallback(frame.Slider, MinimalSliderWithSteppersMixin.Event.OnValueChanged, handler, context)` — same pattern as `EditModeSettingSliderMixin:OnLoad`. This is the correct path.
