## v0.4.1 Requirements

### ITEM — Generic item tracking (both flavours)

Built on two probe runs against Forever 1.60.1 on 2026-09-24. The measured findings and the settled
design are recorded in `.planning/ROADMAP.md` backlog entry 999.6 — read it before planning.
**Spell categories are not used:** a per-item `C_Item.GetItemCooldown(itemID)` read already reflects
a shared cooldown, so tracking items individually gets cooldown sharing for free.

- [x] **ITEM-01**: Opening the Cooldown Manager produces a catalogue of the usable consumables in the
      player's bags, keyed by itemID rather than by bag and slot
- [x] **ITEM-02**: Every catalogued consumable that is not already tracked is offered in the Suggested
      section of the Cooldowns tab
- [x] **ITEM-03**: A Suggested consumable tile shows the item's own icon and the number the player
      currently holds
- [x] **ITEM-04**: Dragging a Suggested consumable into a container creates an ordinary cooldown
      tracker for that item
- [x] **ITEM-05**: Using any item refreshes the displayed cooldown of every tracked item, so an item
      that shares a cooldown with the one used shows it too
- [x] **ITEM-06**: A tracked item's count decreases only when a use actually lands, never when a press
      is refused by the game
- [x] **ITEM-07**: A tracked item's count is reconciled against the bags when the player leaves combat,
      so drift from looting or multi-item consumption self-corrects
- [x] **ITEM-08**: Quest items, recipes, keys, trade goods and bandages are absent from the catalogue
- [x] **ITEM-09**: A tracked item keeps its tile and its running cooldown after the stack reaches zero
      and the item leaves the player's bags
- [x] **ITEM-10**: The consumables catalogue is offered on **both** retail and Forever. Changed from a
      Forever-only offer by user decision, 2026-09-24 — unlike the racial tiles, this is not a
      duplicate of anything retail's CDM already provides for items the player chooses to track
**MEASURED — Forever 1.60.1, 2026-09-24.** The catalogue produces the player's relevant consumables,
and **ITEM-05 is confirmed**: one HP potion fired the cooldown on all three potions sharing it, and
the quantity decremented correctly. That is the design bet of this whole feature paying off — the
kickoff decision was that a per-item `C_Item.GetItemCooldown(itemID)` read already reflects a shared
cooldown, so tracking items individually gets cooldown sharing *for free* and no spell-category
table is needed. It does, and it did.

**Campfire items are in the catalogue, and stay there by user decision, 2026-09-24.** The user would
mildly prefer them out, judged it not worth excluding, and noted other players may want them.
Recorded rather than acted on — and it does **not** breach ITEM-08: the catalogue filter admits only
`classID == 0` (Consumable), so a quest item, recipe, key or trade good cannot reach it whatever it
is called. Those campfire entries are therefore Consumables by construction, which ITEM-08 never
excluded. The one part of ITEM-08 still unobserved is a bandage being filtered by the
`subClassID ~= 7` test.

**The Trinket and Pot meta-trackers stay as-is.** Retiring the combat potion meta-tracker was raised
and then withdrawn at kickoff, 2026-09-24: it tracks the potion's *buff* from a hand-maintained
duration table, while generic item tracking tracks the item's *cooldown*, so replacing one with the
other would quietly hand players a different kind of tracking than they configured. PROJECT.md's
"Trinket and Pot meta-trackers stay as-is" Key Decision is unchanged.

### RACE — Forever racial catalogue

`RACE-07` is carried verbatim from v0.4.0, where it was written and deferred. Each racial is an
individually-specified special case whose values the user supplies; the data shape is the
`RACIAL_SPELLS` table at `Providers.lua:794`.

**Built last among this milestone's feature work, immediately before the two closing review passes.**
User decision, 2026-09-24 (revised same day): a game update landing later that day may make the
feature obsolete, so the work is deliberately built after item tracking and the pandemic highlight to
avoid building something that gets dropped, and is followed by a Forever review pass and then a
retail review pass rather than more feature work. The user supplies the racial specs at the start of
the corresponding phase, not now.

- [x] **RACE-07**: Every Forever racial is implemented as its own specified special case
- [x] **RACE-08**: A player of any Forever race sees their own racial resolve in the Suggested section
      rather than a "not yet supported" tile
- [ ] ~~**RACE-09**: The "not yet supported" tooltip names the races that are actually supported,
      instead of the hardcoded "Orc, gnome and troll" line it carries today
      (`RACIAL_UNSUPPORTED_LINES`, `Providers.lua:815`)~~
      **OBSOLETE, closed by user decision 2026-09-24.** RACE-10 replaces the generic two-slot racial
      tile with one entry per racial, each visible only to its own race — so there is no longer a
      tile for a "not yet supported" message to occupy. The requirement is not descoped; its subject
      stops existing. `RACIAL_SUPPORTED_LINES` and `RACIAL_UNSUPPORTED_LINES`
      (`Providers.lua:814-819`) become dead code. Accepted consequence: a future Forever race sees
      no racial tile and no explanation, consistent with the rest of the addon.

- [x] **RACE-10**: Every racial is its own tracker entry, visible only to its own race. Added by user
      decision 2026-09-24, replacing the two generic `racial`/`racial2` slots. A troll sees their two
      racials in Suggested under both Buffs and Cooldowns; an orc sees the orc racials and no trace
      of the troll ones, in Suggested or in any container. Placement is account-wide and persists per
      racial, so a second troll finds them where the first one put them. A tracked racial leaves
      Suggested, exactly as an `item:` key already does (ITEM-02). Existing `racial`/`racial2`
      database entries migrate to the new keys so no placement is lost.

### PAND — Pandemic highlight in Merge Mode

Researched 2026-09-24 — `.planning/research/PANDEMIC.md` is required reading before planning. The
recommended signal is the plain field `itemFrame.PandemicIcon`, read inside the already-whitelisted
`itemFramePool:EnumerateActive` walk. Recomputing the window is closed: it needs `auraInstanceID`,
which Blizzard flags `DisallowTaintedAccess`. Five unknowns need an in-game spike first, and they
determine whether a numeric-field fallback is needed at all.

- [x] **PAND-01**: A merged CDM entry inside its pandemic window shows the highlight on TBT's mirrored
      icon
- [x] **PAND-02**: The same entry shows the highlight on TBT's mirrored bar
- [x] **PAND-03**: The highlight clears when the window ends, without waiting on an unrelated aura event
- [x] **PAND-04**: Reading the pandemic state never calls a Blizzard CDM mixin method, so no CDM frame
      is tainted (the locked constraint in `MergeMode.lua`'s header)
- [x] **PAND-05**: Where the pandemic state cannot be observed, TBT renders the entry exactly as it does
      today rather than erroring or showing a stuck highlight

### DISP — Dispel-type border in Merge Mode

Added mid-milestone by user request, 2026-09-24, after Phase 48 closed. Built on the same
"Blizzard computes, TBT mirrors" trade Phase 48 settled on, and on the same whitelisted read
surface, so it is inserted as **Phase 48.1** rather than renumbering — the precedent is Phase 27.1
in v0.3.0.

**It is dispel type, not school of magic.** `AuraUtil.lua:4-10` defines six: Magic, Curse, Disease,
Poison, Bleed and a default None. Fire/Frost/Shadow never appear. Confirmed in source at kickoff,
correcting the initial framing of the request.

**The read is `itemFrame.DebuffBorder`**, two plain table-field reads plus `IsShown()` and
`GetAtlas()` — both plain C widget getters, both already-permitted operations under
`MergeMode.lua`'s locked header. Recomputing the dispel type is closed for the same reason the aura
duration was: `C_UnitAuras.GetAuraDispelTypeColor` is `RequiresUnitAuraAccess`, the flag measured
on 2026-09-22 to *raise* rather than degrade, and it keys off an `auraInstanceID`, which Blizzard
flags `DisallowTaintedAccess`.

- [x] **DISP-01**: A merged CDM entry that Blizzard borders shows the same dispel-type border on
      TBT's mirrored icon
- [x] **DISP-02**: The same entry shows it on TBT's mirrored bar, drawn around the bar's icon at
      Blizzard's own -3/+3 inset rather than around the bar
- [x] **DISP-03**: Where the border cannot be observed — no `DebuffBorder` on the client, or an
      unreadable atlas — TBT renders the entry exactly as it does today, with no stuck border
- [x] **DISP-04**: TBT never draws a border Blizzard is not drawing. Debuff-only is inherited from
      Blizzard's own `Show`/`Hide` inside `SetAuraBorderAtlasFromAura`, never reimplemented as a
      polarity test on TBT's side

**MEASURED — retail, 2026-09-24.** Magic and Bleed both confirmed on TBT's mirrored icon, in
**two container kinds**: Tracked Buffs, and the Cooldown containers, where a spell that tracks its
own aura shows it on the cooldown icon. That second one matters more than it looks — it is a
different code path, not a repeat. `AURA_HOST_KEYS` is `{ "buffs", "essential", "utility" }`, and
on a cooldown container the engine's aura frame **overlays** TBT's icon rather than replacing it,
so the border had to land correctly on a cell that still has TBT's own cooldown drawing underneath
it. Both polarities were worth testing separately too: Magic and Bleed are different atlases
reached through one path, so one working alone would have meant the dispel name never arrived.

The
implementation shipped is **two routes, not one**, and the split is the finding:

- **Ordinary merged tracked buff → the aura ENGINE draws it.** `InitializeAuraFrame` registers a
  dispel-type texture on the aura button and Blizzard fills it. This is the mainstream case and
  the only one the first attempt got wrong: `RenderIconContainer` hides TBT's pooled icon whenever
  the engine draws that aura, so the atlas mirror was drawing onto a hidden widget. The
  hidden-parent hazard `EnsurePandemicIconFX` already documents, walked into a second time.
- **Bars, item-backed tracked buffs, and engine-latched-off → the atlas mirror.** `ReadDispelBorder`
  off `itemFrame.DebuffBorder`. Retained deliberately; these three cases have no engine frame.

DISP-03 is satisfied on both routes without a version check: the engine route is guarded on
`frame.AddDispelTypeTexture` and the enum both existing, the mirror route on `DebuffBorder` being a
non-nil field. A client with neither renders exactly as before.

**DISP-02 closed 2026-09-24** — Moonfire (Magic), Rake (Bleed) and Entangling Roots as bars, in
combat. It took two corrections to get there, and both are worth keeping:

1. **The atlas name is SECRET IN COMBAT.** Measured:
   `dispel=unreadable(secret=true,type=string) aura(dispelName=<secret>,harmful=<secret>)`.
   Both mirror sources go dark together, which is why Roots bordered on a bar *out* of combat and
   nothing bordered in it. The way through is that the two halves of the answer have *different*
   secrecy: `border:IsShown()` stays a plain boolean, so **whether** to draw is readable and only
   **what** to draw is not. The atlas is therefore relayed unread —
   `Texture:SetAtlas` is `SecretArguments = "AllowedWhenTainted"` and `atlas` is the one parameter
   of six not marked `NeverSecret`, which is Blizzard's explicit permission for this.
   A secret cannot stand in for its own presence: `atlas ~= nil` and `atlas == cached` both feed a
   secret into a conditional, which is exactly what made the first attempt fail closed.
2. **The engine route diverged from the CDM's show rule.** The CDM shows for *any* harmful aura and
   falls back to the grey `None` atlas; the engine's `showWithoutDispelType` defaults to false and
   hid precisely that case, so a harmful undispellable debuff bordered on an unmerged tile and not
   on a merged one. Closed by passing `showWithoutDispelType = true`.
   Found only because the user restated the rule — *show whatever atlas the CDM shows, and only
   when the CDM says it should be shown* — against a code comment that had asserted all three
   relevant defaults already matched and was being used to justify not checking.

**MEASURED — Forever 1.60.1, 2026-09-24.** The border works there, with no Lua errors on either
client. Three findings:

- **Forever HAS `DebuffBorder`.** The prediction recorded above — that 1.60.1's CDM likely lacks it,
  and the feature would degrade to nothing — was wrong. `dispel=UI-Debuff-Border-Default-NoIcon
  stamped=UI-Debuff-Border-Default-NoIcon` on a Fireball bar. The mirror route works unchanged.
- **The `showWithoutDispelType` fix earns its keep hardest here.** That Fireball row reads
  `aura(dispelName=<nil>,harmful=<secret>)` — a harmful aura with NO dispel type — and Forever's own
  CDM draws it on the grey `None` atlas. Classic-era debuffs are largely undispellable, so on
  Forever this is the *common* case rather than an edge one. Without that option the engine route
  would have drawn nothing on most of the client's debuffs.
- **No pandemic on Forever, and it degrades exactly as designed.** Every row: `alertCap=no`,
  `no data fields -- 9 pandemic methods only`, `answer=false`. No stuck highlight, no error. That is
  **PAND-05 confirmed on Forever**, the one pandemic requirement that could be tested there at all.

**Secrets exist on Forever too** (`harmful=<secret>`), which is not obvious for a 1.60.1 build and
is worth remembering before assuming any read is plain there.

**Known trade, carried to Phase 50.** While the atlas is secret, `ApplyDispelBorder` re-issues
`SetAtlas` on every render pass for each bordered widget, because no secret may be compared against
the cached value. A handful of C calls per tick with no allocation. Making it fire only on a change
needs a non-secret identity key (the entry's `cooldownID`) to avoid a pooled widget keeping a stale
colour across a re-sort — worth doing in cleanup, not worth destabilising freshly verified code for.

## Out of Scope

Explicitly excluded, with reasoning.

- **Spell-category-based item grouping.** Dropped by user decision, 2026-09-24. A per-item
  `GetItemCooldown` read already reflects shared cooldowns, so a category table buys nothing, and
  Forever's categories were measured to differ from retail's anyway (all potions share one 120s
  cooldown on Forever; retail splits combat and health potions).
- **Engineering-explosive cooldown sharing.** Left untested by user decision, 2026-09-24 — the
  per-item read makes the answer unnecessary.
- **Whether `GetItemCooldown` answers for a zero-count item.** Gap accepted by user decision,
  2026-09-24. It closes for free if `start + duration` is stamped at the moment of the successful use.
  Still the one unobserved corner of ITEM-09 after the 2026-09-24 Forever pass: the tile and its icon
  were confirmed to survive a zero stack, a *running cooldown* on a zero-stack item was not
  separately watched. Left accepted rather than reopened — it is one drink of a last potion to
  settle, if it ever matters.
- **Dispel-type borders on custom (non-merged) trackers.** Dropped by user decision, 2026-09-24,
  when the DISP scope was set. A custom tracker has no Blizzard frame to mirror, and the live aura
  read is measured-dead in combat for a tainted caller (`MergeMode.lua:1253` — every merged slot
  reported `aura=unresolved` mid-combat on retail). A learn-once cache was designed and offered —
  dispel type is a static property of a spell, so reading `dispelName` whenever the game permits
  and caching it per spellID would sidestep the combat restriction entirely — and was declined in
  favour of no new read surface and no cache to invalidate. Revisit only if custom trackers are
  wanted bordered; the design is recorded here, not lost.
- **Dispel-type borders on the player's own buffs.** Dropped by user decision, 2026-09-24. A
  helpful aura does carry a `dispelName` — that is what makes a buff Spellstealable — but no
  Blizzard UI renders it, so drawing one would be a visible divergence from the CDM sitting beside
  it. See DISP-04.
- **Recomputing the pandemic window from aura data.** Closed by the platform: `expirationTime` and
  `duration` are secret, and the two APIs that would redo Blizzard's math key off `auraInstanceID`,
  flagged `DisallowTaintedAccess`.
- **Reading pandemic state by calling CDM mixin methods.** Locked constraint — measured to taint the
  frame permanently.
