## Diagnosis evidence (checked by reading the code at planning time; Task 1 re-checks every item)

Suspect 1 is NOT the cause. That suspect was: the charge text is not re-asserted, or is cleared,
while `ApplyMergedAuraCooldown` owns the sweep.
- `ApplyCooldownSlot` (Display.lua ~1645-1788) calls `ApplyChargeCount(icon, spellID)` at
  ~1691-1695. That call is inside the `_cdGen ~= ns.cooldownGeneration` block but OUTSIDE the
  `if not userOwned and not auraOwned then` guard (~1728). So charges are refreshed on every
  generation change, whoever owns the sweep.
- `ApplyMergedAuraCooldown` (~1399-1453) never touches `icon.chargeCount`. On the non-engine path
  it drives `icon.cooldown` on the same icon. `chargeCount` is a child Frame created after the
  Cooldown (CreateTimerIcon ~564), so it already draws above that sweep.
- Nothing in the cooldown-slot branch hides `chargeCount` while an aura is up.
  `ClearCooldownStamps` hides it only when a pooled widget leaves a cooldown slot.

Suspect 2 IS the cause. That suspect was: the engine-drawn aura frame covers the icon's
`chargeCount`.
- `MergeMode.lua` `AURA_HOST_KEYS = { "buffs", "essential", "utility" }` (~1355). Since Phase
  43.1, merged Essential and Utility entries get an engine AuraContainer too.
- `SyncEntryContainers` creates it with `host` as parent and sets
  `SetFrameLevel(host:GetFrameLevel() + 10)` (~1618, ~1665). The comment there says: "on a cooldown
  container it is what makes the overlay an overlay".
- `InitializeAuraFrame` (~1382-1420) gives the engine aura frame an opaque 40x40 ARTWORK icon
  texture, a CooldownFrameTemplate child, and an applications FontString only. It has no charge
  count, and TBT can never write one into it (DenyTaintedAccessWhenAurasAreSecret).
- `RenderIconContainer`'s cooldown-slot branch (Display.lua ~2520-2540) keeps TBT's icon shown and
  calls `ns:PlaceMergeAura` onto the same cell. The comment there says: "the engine's aura frame is
  placed on the same cell, above it, and covers it for exactly as long as the aura is up".
- TBT's icon is a child of the container (`GetIcon` -> `CreateTimerIcon(ns.containers[key])`,
  ~621-624), so it sits at container+1 and its `chargeCount` at container+2. That is far below the
  aura frame at container+11 and its Cooldown at container+12. The count is still set and shown; it
  is simply covered.
- Precedent for the fix: `EnsurePandemicIconFX` (Display.lua ~679) already puts TBT's pandemic FX
  at `parent:GetFrameLevel() + 11` "to keep this highlight from ever being covered by an engine
  aura frame".

The CDM rule to match, from wow-ui-source `Blizzard_CooldownViewer/CooldownViewer.lua`:
- `CooldownViewerCooldownItemMixin:RefreshSpellChargeInfo` (~1184-1192) does
  `chargeCountFrame:SetShown(self.cooldownChargesShown)` with no aura condition.
- `CacheChargeValues` (~1107) sets that flag from `maxCharges > 1`.
- TBT's `chargeCapable[spellID] = maxCharges > 1` is the same test, cached sticky, so the SHOWN
  decision already matches. Only the draw order is wrong.

Why the raise is conditional on `ns.mergeAuraGroupsActive`, and not permanent:
- TBT's Edit Mode highlight and selected overlays sit at container+10 and container+11
  (EditModeFrames.lua ~109, ~135).
- A permanently raised count would draw over them. That breaks "renders exactly as before" in
  Edit Mode.
- The engine path stands down whenever Edit Mode or the CDM settings are open
  (`ns:IsMergePreviewState`, MergeMode.lua ~1290-1308; `ns.mergeAuraGroupsActive = enabled`
  ~1742), and outside those states nothing else occupies container+12/+13.
- So "raised exactly while `ns.mergeAuraGroupsActive`" covers the bug and changes nothing
  anywhere else.

Regression invariant hashes. They were taken at planning time and must still match after the plan:
- `awk '/^local function ApplyChargeCount/,/^end/' Display.lua | md5sum` gives
  `e499e5fd52c446f5d33be0a20be6953d`
- `awk '/^local function ApplyMergedAuraCooldown/,/^end/' Display.lua | md5sum` gives
  `6c771dbe86d51a82eb6425191aef5c50`
