<objective>
The runtime and data half of Phase 57.5 (RALT-01, RALT-03). A reminder's `alternatives` (saved by
57.5-01's dialog and v11) now satisfy it, and the paladin blessings satisfy each other. The user's
words: "all 3 pally buffs are mutually exclusive, so if I have all 3 reminders on screen, two
reminders will always be up, when in reality I expect any of these buffs to satisfy all 3
triggers."

Purpose: ROADMAP 57.5 success criteria 1 (runtime) and 3.
Output: Core.lua, BuffEngine.lua and Providers.lua changes, two commits.

Decisions this plan takes (Claude's discretion per CONTEXT "Suggested model", recorded for the
SUMMARY):
- **Watched set** = the reminder's own list plus each alternative's family.
  - The own list is today's ns.visibilityWatch[key]; when that is nil, `{ ns.visibilityAuraID[key] }`.
  - Each alternative's family comes from `ns:CastRuleFamily(id)`. This is the cast rule's family
    expansion, moved out of ns:RebuildDetailedRuleIndex into one ns-level helper so both lists
    share it. Forever caches it in ns.endRuleFamilies; retail uses the ID with its base/override.
  - The union is deduplicated and built at rebuild time. It is published as
    ns.visibilityWatch[key], so RefreshAuraStates reads it with no new code path, and as
    ns.satisfiedByWatch[key], so ns:FillUserBuffProc uses it as the timer's aliveBuffs ("End when
    the aura is lost applies to the whole set").
  - A reminder with no alternatives keeps exactly today's list.
- **Cast index.** `ns.alternativeKeysBySpell[id] = { reminderKey, ... }`, one-to-many, because five
  blessings each list the other four. It is built in the same walk as ns.endKeysBySpell, fresh per
  rebuild. OnTrigger does one lookup and starts each listed reminder through
  ns:StartReminderFromCast. It skips the reminder keys this cast already started directly, and
  redraws once, not once per reminder: `StartReminderFromCast(key, entry, skipRedraw)` returns true
  when it started.
- **Latest expiry.** The watch-list loop in RefreshAuraStates no longer stops at the first present
  aura. It keeps the present aura with the latest readable expiry as `seenAura`, or the first
  present one when none has a readable expiry. Five overlapping blessing lists would otherwise
  read the same IDs up to five times per UNIT_AURA. So each read goes through a per-call memo:
  two module tables wiped at the start of every call, filled by a file-local `ReadWatchedAura(id)`
  that calls ns:ReadPlayerAura. No allocation (the tables are wiped, not rebuilt), no new aura
  reader (aura-read-gate unchanged).
- **The cast rule leaves reminders.** ns:RebuildDetailedRuleIndex indexes endOnCast for non-reminder
  buff-like entries and USER_CD only, so a reminder can never be in ns.endKeysBySpell.
  ns:ApplyEndOnCast's reminder branch (the absent write) and its `startingReminderKey` parameter
  are then dead, and are removed. The OnTrigger call passes three arguments.
- **Built-in data.** Load-time helper `MetaReminderGroup(...)` sets each member row's
  `def.alternatives` to the other members, and is called once for the five blessings after the
  rows. `ns:ApplyMetaReminderDef` writes `entry.alternatives = def.alternatives` when the reference
  differs: a row with no group clears it, and after a reload the saved copy is replaced once.
  That is applied like the other def fields, and user input never reaches it (IsEditableTracker is
  unchanged).
- Sanctuary's row is deleted. The orphan path (`ns:IsOrphanMetaReminder`, 57.4 WR-02) already
  greys a placed one with "Not loaded: no longer offered as a class buff. Remove it" and deletes no
  data, so no code is needed for it.
