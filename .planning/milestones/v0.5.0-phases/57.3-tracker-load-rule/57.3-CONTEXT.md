<domain>
## Phase Boundary

Add one generic load rule, "Load: When known / Always / Never", that decides whether a tracker
runs at all. User trackers get it as an editable Advanced setting. Built-in (meta) trackers get a
fixed internal value. It replaces the racial race filter (`ns:IsRacialKeyVisible` and its
race-membership logic) with "is the spell known". The user's framing: "rework this racial
meta-tracking thing into something more generic a user can have too"; "I want our meta-trackers
to abide a very similar rule-set than user created ones".

</domain>

<decisions>
## Implementation Decisions

### The setting (LOAD-01)
- **UI label:** "Load". **Values:** "When known" (default), "Always", "Never". Use a radio dropdown,
  the pattern the user asked to keep: `WowStyle1DropdownTemplate` + `SetupMenu` +
  `rootDescription:CreateRadio`. It sits on the **Advanced** tab. The container settings already
  have a "Visibility", so the setting is never called "visibility" in the UI.
- **Saved key:** `entry.load`. It is nil for When known (the default, per the stored-as-nil rule),
  "always" or "never" otherwise. It is offered on all three user kinds: userCd, userBuff and
  userReminder. Reminders are buffs, so they get it exactly as buffs do.
- **The default applies to existing trackers too:** no migration writes a value, and nil means
  When known. The user accepts that trackers for spells they don't "know" will go grey after the
  update until set to Always. That covers trinket and gear procs, buffs cast on them by others,
  and food and flask buffs. Put this in the UAT so it isn't mistaken for a bug.

### Built-in trackers (LOAD-02)
- Same rule set, with a fixed internal load the user cannot edit:
  - racial buff and cooldown trackers (metaSkill / metaSkillCd): **When known**;
  - Lust, trinket and potion (the metaItem tiles) and bag items: **Always**, on both clients.
- Resolve it through one function, e.g. `ns:TrackerLoad(entry)`, returning the effective rule:
  a user entry's saved value or the default, and a built-in kind's fixed value. Every consumer
  asks that function (or the cached loaded-state below) and never special-cases a kind.

### What "not loaded" means (LOAD-03)
- **Not processed:** the entry is left out of every runtime index. That covers the cast indexes
  (buff, cooldown, meta-cooldown, reminder), the rank indexes, the end-rule index, the reminder
  watch list and aura scans, and any provider path. A running timer or cooldown for a tracker
  that becomes unloaded is cleared.
- **Never drawn:** not on screen, not in preview or Edit Mode. It takes no grid cell, following
  the same slot filtering reminders use.
- **The TBT tab still shows it**, desaturated or greyed like Blizzard's CDM settings show an
  unlearned spell; check `Blizzard_CooldownViewer` settings for their treatment. It can still be
  moved, right-click-edited and removed.
- Loaded trackers behave exactly as today.

### "Known" (LOAD-04)
- Retail: `C_SpellBook.IsSpellKnown` / `IsSpellKnownOrInSpellBook` (in
  Blizzard_APIDocumentationGenerated/SpellBookDocumentation.lua), plus the base/override pair (the
  guarded `C_Spell.GetBaseSpell` / `GetOverrideSpell` lookups already in Core.lua). A known talent
  override counts. Forever: the globals `IsSpellKnown` / `IsPlayerSpell`, if they exist there
  (check the BigWigsMods/WoWUI `forever-beta` tree), and any rank of the family (the existing
  `ns:ResolveRankFamily` / rank index). Guard every call (pcall, issecretvalue first). If the answer
  is unreadable, treat the spell as loaded: fail open, never silently hide.
- Re-evaluate on `SPELLS_CHANGED` (already handled), `LEARNED_SPELL_IN_SKILL_LINE`, spec and talent
  change events (PLAYER_SPECIALIZATION_CHANGED, TRAIT_CONFIG_UPDATED, and whatever exists on Forever,
  registered through the existing guarded `TryRegisterEvent` path), world entry and login. Cache
  the result per key, e.g. `ns.trackerLoaded[key]`, rebuilt at those moments and on add, edit and
  remove. **No per-frame or per-cast API calls.** When the loaded set changes, rebuild the indexes
  once and redraw.
- **The race filter is removed:** `ns:IsRacialKeyVisible` and its callers (Display.lua,
  CDMTab.lua, BuffEngine.lua) are replaced by the loaded state. **Suggested** racial tiles offer
  the racials this character **knows**, using the same check, instead of filtering by race. The
  user said on 2026-09-29 that racials "are not suggested based on character's race, but they are
  just spells". Keep anything the racial *provider* genuinely needs, such as a racial's duration,
  stacks and combat-cooldown data. Only the race *gating* goes.

### Schema
- There are no stored values to migrate; nil means When known. If the planner still finds a need
  for a schema step, it follows the chain rules (v11 block, v10 pinned to the literal) and is
  mirrored in scripts/migrate-dryrun.js with selftests. Prefer none.

### Claude's Discretion
- The exact greyed look (desaturate, alpha), the cache names, and event coverage on Forever.

</decisions>

## Specific Ideas
The user's words: "A 'visible' tracker means it shows on preview on screen and works like anything
we have now, a 'non-visible' one skips any processing and never shows on screen, but is visible and
can be moved on CDM tab, but is always grayed out indicating its status ... Changing spells or
learning new skills might need to refresh this as tracker with visibility set to 'is known' might
change status."
