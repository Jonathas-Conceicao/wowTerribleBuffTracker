## Summary

Scope: `git diff 965cea2..HEAD -- '*.lua' '*.xml' scripts/`. That covers Core.lua, BuffEngine.lua, Providers.lua, Display.lua and CDMTab.lua. No XML or scripts/ changes.

**Plumbing: mostly sound.** Every cast-triggered runtime path resolves through an index that now filters on `ns:IsTrackerLoaded`:
- the cast indexes, the rank indexes and `ns.endKeysBySpell`;
- `ns.visibilityKeys`, and through it `ns:RefreshAuraStates` and `ns:VisibilityShowsIn`;

Greyed tiles keep drag, edit and remove.

**Main defect: the known check.** It OR-combines four APIs, and the first one asked is the most permissive. On retail, off-spec and future spells will very likely read as known, so a spec swap never unloads a spec spell.

**Secondary defects:**
- An in-combat SPELLS_CHANGED unload clears running timers.
- The race-gate removal changed which casts can spend a Eureka! stack.
- The all-races racial memo is now taken at ADDON_LOADED and can freeze a partial list.

## Critical Issues

### CR-01: The known check lets its most permissive API win, so off-spec and future spells count as known and a spec swap never unloads them

**File:** `Core.lua:1102-1105`, `Core.lua:1141-1147`
**Issue:** `ns:SpellKnownState` asks four functions in this order, and the first `true` wins:

1. `C_SpellBook.IsSpellKnownOrInSpellBook`
2. `C_SpellBook.IsSpellKnown`
3. `IsPlayerSpell`
4. `_G.IsSpellKnown`

The first is documented as "known **or present in the spellbook**" (SpellBookDocumentation.lua:701-704, `includeOverrides` default true). The retail spellbook holds more than known spells:
- off-spec skill lines: `isOffSpec`, "belongs to a non-active specialization" (SpellBookDocumentation.lua:958), shown by Blizzard_SpellBookCategory.lua:211;
- not-yet-learned spells: `Enum.SpellBookItemType.FutureSpell`.

On retail, `_G.IsSpellKnown` is also a deprecation shim for `C_SpellBook.IsSpellInSpellBook` (Deprecated_SpellBook.lua:16-20), so it has the same problem. The strict API (`C_SpellBook.IsSpellKnown`, which Blizzard's own CooldownBroadcaster uses) can therefore never veto a spellbook hit.

Consequences on retail:
- A When known tracker for a spec-only spell stays loaded after a spec swap. The LOAD-04 spec-change requirement, and its five new events, then do nothing for exactly the case they exist for.
- On a levelling character, every future class spell reads known.

Confirm in game with one off-spec spell ID: `/dump C_SpellBook.IsSpellKnownOrInSpellBook(id)` against `/dump C_SpellBook.IsSpellKnown(id)`.
**Fix:** Make the strict answer the authority, and fall back to the spellbook-presence functions only when no strict function exists:
```lua
local strict1 = C_SpellBook and C_SpellBook.IsSpellKnown
local strict2 = IsPlayerSpell
local loose1, loose2
if type(strict1) ~= "function" and type(strict2) ~= "function" then
	loose1 = C_SpellBook and C_SpellBook.IsSpellKnownOrInSpellBook
	loose2 = _G.IsSpellKnown
end
-- per candidate id: r1 = AskKnown(strict1, id); r2 = r1 ~= true and AskKnown(strict2, id); ...
```
Update the UAT with a spec-swap item that uses an off-spec spell.

## Warnings

### WR-01: An unload during combat destroys running timers and cooldowns

**File:** `Core.lua:1204-1220` (with `Core.lua:1884-1890`, SPELLS_CHANGED)
**Issue:** SPELLS_CHANGED rebuilds the load state in combat as well. When a tracker flips from loaded to not loaded, `ns:EndTrackerRuntime` clears its active timer, cooldown start and aura state at once. Retail fires SPELLS_CHANGED in combat when a temporarily granted or proc override spell goes away. The API doc says IsSpellKnown "can also return true for ... temporarily-granted abilities", and returns false once they are gone.

The failure: the user tracks such a spell (a buff or cooldown for a proc override) under the default When known. They cast it. The grant ends, and the tracker unloads mid-fight. Its buff timer and its cooldown sweep vanish although the effect or cooldown is still running. The next grant reloads it with no state.

A transient false read in combat does the same, and afterwards `ns.spellKnownHeld` holds the false.
**Fix:** Do not apply loaded-to-unloaded flips while `InCombatLockdown()`: keep the previous state and set `ns.loadRefreshPending`-style flag, then re-run `ns:RebuildRankIndex()` from the existing PLAYER_REGEN_ENABLED branch. Unloaded-to-loaded flips can still apply at once.
```lua
if not loaded and wasLoaded and InCombatLockdown() then
	loaded = true
	ns.loadRecheckAfterCombat = true
end
```

### WR-02: A cast of an untracked or unloaded racial can now spend a Eureka! stack

**File:** `Providers.lua:2157-2166`
**Issue:** Before this phase, the granting-cast loop walked every racial of the player's race, whether or not it was tracked. A cast of any own-race racial was therefore terminal and returned before `ConsumeRacialStack`, following the code's own rule that "a racial cast never spends a stack". The loop now walks only `ns.racialDefsActive`, the racials that are tracked and loaded. A cast of an untracked own racial falls through to `ConsumeRacialStack(spellID)`.

The failure: a gnome priest tracks Eureka! but not Escape Artist, and casts Escape Artist while Eureka! is up. `CastSpendsStack` skips the harmful check for priests, so a Eureka! stack is spent. This is a behaviour regression from the race-gate removal, which should have removed only the race gating (focus item 6).
**Fix:** Keep the terminal rule independent of tracking, using the existing O(1) ownership map:
```lua
-- Otherwise it may be a consuming cast for a live stack-driven racial. A racial cast never
-- spends a stack, tracked or not.
if ns:IsRacialSpellID(spellID) then
	return nil
end
return ConsumeRacialStack(spellID)
```

### WR-03: The all-races racial memo is now taken at ADDON_LOADED and can freeze a partial list for the session

**File:** `Providers.lua:1180-1214`, reached from `Providers.lua:1234` via `Core.lua:1226` and `BuffEngine.lua:243`
**Issue:** `ns:RacialDefsAll` drops any def whose `C_Spell.GetSpellInfo` returns nil, and it memoises for good as soon as one def resolves (`#racialDefsAll > 0`). Two things have changed since the old per-race list:
- **Earlier first call.** It is now reached from `InitBuffEngine` → `RebuildCastIndex` → `RebuildTrackerLoad` → `RebuildRacialLoadLists`, at ADDON_LOADED. The file's own comments say spell data is not ready that early ("this can be reached before spell data has loaded").
- **Longer list.** It covers about 20 defs, not 2 or 3.

A partially resolved list becomes permanent. Every racial it misses then gets nil from `ns:RacialDefForSpellID`, which breaks four things:
- the provider's granting cast, because the def is absent from `racialDefsActive`;
- `ns:ConditionalCooldown`, so Shadowmeld loses its combat cooldown;
- `GetDisplayInfo`, so the tile loses its icon and name;
- the Forever Suggested offer.

Conversely, if nothing resolves, each call reruns the full scan. `RacialDefForSpellID` is on the per-frame placeholder path, so that scan would then run every frame.
**Fix:** In `ns:RebuildRacialLoadLists`, do not touch `ns:RacialDefsAll()` before `ns.knownReady` (wipe both lists and return). Only memoise once `ns.knownReady` is set, so the memo is taken after world entry.

## Info

### IN-01: Any RebuildCastIndex-only caller can flip the load state without rebuilding the rank index or aura watch

**File:** `Core.lua:1275`; callers `CDMTab.lua:219`, `BuffEngine.lua:243/514/575/656`
**Issue:** The load state is rebuilt inside `ns:RebuildCastIndex`. `ns.rankIndex*`, `ns.rankFamilies` and `ns.visibilityWatch` are rebuilt only by `ns:RebuildRankIndex`. If the load state flips during a CDM drop or a migration rebuild, an unloaded "Cover all ranks" owner stays in the rank index until the next SPELLS_CHANGED, and `UserSpellProviderMixin:OnTrigger` would still start it from a rank cast. This is unlikely today, because those sites run before `knownReady` or right after a full rebuild. It is fragile structurally.
**Fix:** In `RebuildTrackerLoad`, when `changed` is true, set a flag. `RebuildCastIndex` callers outside `RebuildRankIndex` then escalate to `ns:RebuildRankIndex()`, or `RebuildTrackerLoad` itself requests `ns:RequestLoadRefresh()`.

### IN-02: `ns.spellKnownHeld` mixes answers computed with and without the rank family

**File:** `Core.lua:1170`, `Providers.lua:1235`
**Issue:** The Suggested racial list calls `ResolveSpellKnown(id, false, true)`, which skips the rank family. The tracker path calls `ResolveSpellKnown(id, true)`, which uses it. Both write and read the same `spellKnownHeld[spellID]`, so an unreadable read on one path can fall back to an answer the other path computed differently.
**Fix:** Key the held answer by `noRanks`, or keep a separate held table for the noRanks path.

### IN-03: Forever: built-in racial trackers still run the full spellbook rank scan (SUMMARY claims otherwise)

**File:** `Core.lua:1211`, `Core.lua:1125-1132`
**Issue:** `RebuildTrackerLoad` never passes `noRanks`. On Forever, every unknown When known tracker therefore runs `ns:ResolveRankFamily` again after each out-of-combat SPELLS_CHANGED wipe. That is a full spellbook walk plus five allocated tables per spell. Other races' racials left behind by the account-wide DB are included. The 57.3-03 SUMMARY states the racial lists skip ranks, but that holds only for the Suggested list.
**Fix:** Pass `noRanks` for `META_SKILL`/`META_SKILL_CD` entries, since racials have one rank. Optionally pass it for user entries without `coverAllRanks` too.

### IN-04: The retail racial list rebuild concatenates about 20 key strings on every SPELLS_CHANGED

**File:** `Providers.lua:1238`
**Issue:** `META_SKILL_PREFIX .. def.spellID` runs for every def in `ns:RacialDefsAll()` on each rebuild, on both clients, even with zero racial trackers. This is rebuild-time work, not per frame, but it is avoidable garbage on retail, which fires SPELLS_CHANGED often.
**Fix:** Store `key = META_SKILL_PREFIX .. def.spellID` on the resolved def once, inside `RacialDefsAll`, and read `def.key` here. `ConsumeRacialStack`, `RacialAuraTrigger` and `EndCombatClearedRacials` can then use it too, which removes their per-cast and per-aura concatenations.

### IN-05: A new tracker for an unknown spell is silently added greyed

**File:** `CDMTab.lua:2186-2244` (the `load` field)
**Issue:** The default is When known. A user who adds a buff cast on them by others, or a trinket, food or flask proc, gets "Now tracking ..." and a grey tile, with no hint at add time. Only the tile tooltip explains it afterwards.
**Fix:** Give the field a non-blocking `validate` hint, the WR-01 hint path that already exists. When the selection is When known and `ns:SpellKnownState(spellID)` reads false, return `true, "this character does not know this spell; set Load to Always to track it anyway"`. This runs at dialog time only.

### IN-06: The base-spell candidate may over-report an override tracker as known

**File:** `Core.lua:1107`, `Core.lua:1117-1118`
**Issue:** A tracker on an override ID B counts as known whenever `GetBaseSpell(B)` returns a known base A. If `GetBaseSpell` resolves static override data rather than only active overrides, a tracker for a talent override stays loaded after the talent is dropped. This is unverified and needs one in-game check.
**Fix:** Count the base spell only when `GetOverrideSpell(base) == spellID`, which means the override is currently active.
