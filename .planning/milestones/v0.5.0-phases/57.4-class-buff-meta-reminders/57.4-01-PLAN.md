<objective>
The engine half of Phase 57.4 (MREM-01, MREM-03). Adds the built-in reminder kind, its data table,
its own cast namespace, its fixed When known load, rank coverage from the spellbook, and the Blood
Pact pet-spell handling. After this plan a metaReminder entry, however created, behaves exactly like
a user reminder through the shared buff code paths (the standing rule: reminders are buffs). The
Suggested tiles that create one land in 57.4-02; until then no entry of this kind can exist, so every
commit leaves a working addon.

Purpose: the user's class buffs as ready-made reminders with no IDs to type (ROADMAP 57.4 goal).
Output: Core.lua, BuffEngine.lua and Providers.lua changes, two commits.

Decisions this plan takes (Claude's discretion, recorded for the SUMMARY):
- Kind name `metaReminder` (`ns.KIND.META_REMINDER`), keyed `metaReminder:<spellID>` (Phase 53
  scheme). The data table lives in Providers.lua, below the racial API. Tile order is table order.
- One source of truth (CONTEXT "Kind and behaviour"): the table. The racial precedent resolves its
  runtime data from the table, not from the entry; here the shared buff paths read entry fields
  (`FillUserBuffProc` reads `entry.duration`, `RebuildRankIndex` reads `entry.coverAllRanks`), so
  instead of forking those paths `ns:ApplyMetaReminderDef(entry)` rewrites the entry's derived fields
  from the table at every `ns:RebuildCastIndex` (duration, coverAllRanks = true, and clears auraID,
  keepOnAuraLoss and endOnCast). The entry copy is a cache the table overwrites; a changed table row
  takes effect at the next rebuild with no migration. The label is the spell name at creation.
- A zero duration (Blood Pact) is stored as nil: no cast timer, and `ns:ReadableAuraExpiry` returns
  nil for an aura with no expiry, so no read-started timer either. It shows while the aura is
  readably missing and hides while present.
- Blood Pact (CONTEXT "Ranks", verified statically against BigWigsMods/WoWUI forever-beta):
  `C_SpellBook.IsSpellKnown(spellID, spellBank)` takes `Enum.SpellBookSpellBank.Pet` (= 1) on
  Forever, and the deprecated `IsSpellKnown(spellID, isPet)` is a shim for
  `C_SpellBook.IsSpellInSpellBook(id, bank)`. But `C_SpellBook.HasPetSpells()` "Returns nothing if
  player has no pet spells" (SpellBookDocumentation.lua) and Blizzard's pet spellbook tab exists only
  while it answers (Blizzard_SpellBookCategory.lua `SpellBookPetCategoryMixin:IsAvailable`), so a
  pet-bank known check would unload the reminder exactly when the imp is dismissed, which is when it
  must show. So the row's LOAD and Suggested offer ask the player spell Summon Imp (688) instead
  (`knownID`), and the pet spellbook is used only for the rank family (the aura watch), where
  "imp out" is exactly when it matters. Blizzard's own spellbook refreshes its pet tab on
  SPELLS_CHANGED, which TBT already rebuilds the rank index on (in combat too), so no new event is
  registered. 688 is the classic-era Summon Imp ID and cannot be proven on Forever statically: the
  57.4 UAT verifies it (if it is wrong the Blood Pact tile never appears; the fix is one number).
- The pet pass takes `itemInfo.spellID` only, never `itemInfo.actionID` (a pet action ID can be a
  packed value), and accepts a pet item of type Spell or PetAction.
- Not editable needs no code: `ns:IsEditableTracker` already names only the three user kinds.
</objective>
