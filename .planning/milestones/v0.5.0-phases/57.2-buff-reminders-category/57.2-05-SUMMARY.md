# Phase 57.2 Plan 05: Reminders are buff trackers in their own category Summary

**A reminder now works exactly like a buff tracker: it has a duration (with the live-aura suggestion), a cast starts its timer and hides it, and "End when the aura is lost" and "Ends when you cast:" apply to it. When the timer ends, a readable read finds the aura gone, or a cast rule fires, the reminder shows at once, in combat too. Its state is held while the aura cannot be read, and a readable expiry starts or corrects its timer. Schema v10 now keeps a migrated reminder's duration and rules. The buff paths are shared through `ns.BUFF_LIKE_KINDS`. The only reminder-specific paths are its own cast namespace, its display, and the expiry sync.**

## Performance and cleanup review

**(a) Cast path.** OnTrigger now makes two more table lookups per cast (`ns.reminderKeyBySpell[spellID]`, then `ns.rankIndexReminder[spellID]`) on a cast that matches no reminder. There is no constructor, no API call and no closure. A matching reminder fills its pooled proc through `ns:FillUserBuffProc`, and `ns:PreallocateProc` now runs for reminders again (Add, Update-move, InitBuffEngine), so the first cast allocates nothing. A spell tracked as both a buff and a reminder redraws twice (reminder side plus dispatcher), which the plan accepts.

**(b) UNIT_AURA.** `ns:RefreshAuraStates` uses numeric loops only, with no `{` and no pairs (the gate checks this). It makes one `ns:ReadableAuraExpiry` call per present reminder per readable event. That call only inspects a table ReadPlayerAura already returned. The expiry correction writes only when the timer is more than 0.5s off, and the write does not raise another aura event, so it cannot loop. A timer started from a read uses the pooled proc. On a secret event the function returns before any read. Nothing is cleared, and there is no redraw.

**(c) Render tick.** `ns:GetActiveTimers` adds one hash lookup (`ns.visibilityAuraID[key]`) per live timer inside the existing loop. `ns:VisibilityGate` adds one hash lookup (`ns.activeTimers[key]`) per reminder slot. Nothing else runs per frame, and nothing allocates.

**(d) Display consistency (Display.lua read, not edited).** Reminder procs never enter the list GetActiveTimers returns, so they never reach `timersByContainer`, and `activeByKey` never holds a reminder. The gate's true branch draws the full-colour no-sweep placeholder (SlotDraws, the icon placeholder chain around line 2515). The false branch hides it outside Edit Mode and the settings window. hideWhenInactive and centring count a reminder only through `ns:VisibilityShowsIn` (line 2283), so only drawn reminders count. `ns:StartAllPreviewTimers` skips reminders, so no demo sweep can reach one. Display.lua needed no change.

**(e) Dead code.** No `ClearReminderStates` and no `playerInCombat` remain in any shipped Lua file, comments included. No reminder-only exemption remains in Add, Update, InitBuffEngine or the CDMTab field hooks (`isReminder` is gone, and CDMTab.lua code has no `REMINDER_KINDS`). The remaining reminder-specific uses are all genuine reminder-vs-buff differences:
- Core.lua:123 `ns:GetTrackerCategory`: the category
- Core.lua:1005 RebuildCastIndex branch and :1287 RebuildRankIndex namespace pick: the reminder's own cast namespace
- Core.lua:1059 RebuildDetailedRuleIndex: the reminder watch list (`ns.visibilityKeys`)
- BuffEngine.lua:909 TrackerKindWord ("reminder") and :978 FindTrackerConflict: the separate namespace for duplicates
- BuffEngine.lua:1418 ApplyEndOnCast: the reminder absent write (display)
- BuffEngine.lua:1462 preview skip and :1582 VisibilityGate: the display

**(f) Unify what this plan introduced.** The reminder side and the buff side of OnTrigger share `ns:FillUserBuffProc`, and RefreshAuraStates' start path shares it too. Both sides resolve with the same two-step block (direct index, then rank index). Folding those blocks into one shared local would touch the buff block, which predates the milestone, so that call belongs to Phase 58 (PROJECT.md "No refactors during cleanup phases"). The reminder block copies the buff block's shape on purpose.

## Known behaviour (for in-game testing)

- **Existing v10 databases are not re-migrated.** Reminders created or migrated by the earlier 57.2 build have no duration. They cause no errors, a cast starts no timer and does not hide them, and they still show or hide from readable reads out of combat. Edit one, enter a duration, and it behaves fully (UAT item 22).
- **Cast before aura application.** If a readable UNIT_AURA arrives between the cast and the aura landing, it counts as a readable absent read. The reminder timer ends and the reminder shows until the aura's own UNIT_AURA arrives, which then hides it and starts the timer from the real expiry. The buff cancellation scan has the same race. This is not observed yet. Watch for a one-frame flicker on cast (UAT item 7/20).
- **Unreadable expiry and a short typed duration.** When the expiry cannot be read and the typed duration is shorter than the buff, the reminder shows at the typed end. The next readable aura event corrects it (UAT item 23 exercises the readable case).
- **Buffs are unchanged.** The expiry sync is reminder-only.
