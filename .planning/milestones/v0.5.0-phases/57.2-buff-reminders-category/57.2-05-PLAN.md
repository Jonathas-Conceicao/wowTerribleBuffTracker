<objective>
Gap closure for Phase 57.2, from two user decisions on 2026-09-29 that override 57.2-CONTEXT's
"no duration, no timer, no cast rule" (REM-02) and its "hide on combat start / hide on any unreadable
read" (REM-03):

1. "Let's add the duration field, it was always supposed to have it ... have the user duration input
   (which is the duration we assume while unknown) and then when available update it if we detect any
   changes" -- "that way we can alert ends mid-combat". Chosen: restore the pre-category (Phase 57
   "absent") behaviour.
2. "reminders are essentially skill buffs that last long times, like 5m, 30m or 1h, they should work
   exactly like buffs do, but be presented and stored in its own category ... in general any changes
   we wanna do to how buff tracking works will prob be done to reminders as well."

So a reminder is a buff tracker in its own category. It has the buff's fields, timer, aura-loss
cancellation, cross-spell end rules and rank families. Only its category and container (Reminders
tab, Buff Reminders), its kind and key (`userReminder:<id>`) and its display differ: it draws while
the buff is missing and hides while the buff is up. Its state is held while the aura cannot be read.
The buff paths are shared through one buff-like kind set (`ns.BUFF_LIKE_KINDS` /
`ns:IsBuffLikeEntry`) instead of special cases. The one exception is the cast index, where a
reminder needs its own namespace, because a spell may be both a buff and a reminder (57.2 REM-02
duplicate rule).

New on top of Phase 57: while the aura reads present with a readable, non-secret expiry, the
reminder's timer is synced to the real expiry. It is started when none runs, and corrected when it
is more than 0.5s off.

Purpose: a reminder can fire mid-combat when its buff runs out, which the 57.2 combat-hide made
impossible.
Output: the code changes, schema v10 changed in place (it is unreleased), updated UAT, REQUIREMENTS,
ROADMAP and STATE, and 57.2-05-SUMMARY.md.

Decisions this plan takes (Claude's discretion, recorded for the SUMMARY):
- A reminder with no duration (saved by the earlier v10 build) starts no timer from either a cast or
  an aura read ("no timer until the user edits one in", taken literally). It still shows or hides from
  readable reads.
- The expiry sync is reminder-only. Buffs keep their behaviour: they are not in the reminder watch
  list, and syncing them would be a separate, unrequested change.
- A reminder's running timer is engine-internal. `ns:GetActiveTimers` never hands it to Display, so no
  container ever draws its swipe, timer text or preview, and Display.lua needs no code change. Unknown
  state (never read, no timer yet) still hides, as in 57.2 (DTRK-06).
- With "End when the aura is lost" off, a readable absent read does not end a running reminder timer.
  The timer governs, exactly as it does for a buff, and the reminder shows when the timer ends.
- Advanced tab: per the second decision, a reminder regains "End when the aura is lost" and "Ends
  when you cast:". This supersedes item 5 of the first brief, which kept Advanced to the aura ID only.
</objective>
