# Phase 57.2: Buff Reminders Category - Context

**Gathered:** 2026-09-29
**Status:** Ready for planning
**Mode:** Decisions taken with the user in conversation. The ROADMAP.md "### Phase 57.2" section and
REQUIREMENTS.md REM-01..04 are authoritative. This file restates them for the planner.

<domain>
## Phase Boundary

Buff reminders become their own tracker category: a third TBT tab, "Reminders", beside Cooldowns
("spells") and Buffs, with its own base container and its own tracker kind. A reminder is a buff
that shows ONLY while its aura is known to be missing. The Phase 57 visibility option
(always/present/absent) is removed from buff and cooldown trackers, and its "absent" use migrates
into reminders.

Requirements: REM-01, REM-02, REM-03, REM-04. DTRK-03 is superseded.

</domain>

<decisions>
## Implementation Decisions

### Category and container (REM-01)
- A third CDM-settings side tab, "Reminders", set up the same way as the two existing TBT tabs
  (`SetUpTBTTab`, `ns:SelectTBTCategory`, the XML tab frames in CDMTab.xml). Add a new category key,
  e.g. "reminders", beside "spells" and "buffs". Every place that accepts only those two keys must
  accept the third one.
- A fifth base container, "Buff Reminders", in the base container table in Core.lua. It holds icons
  only, is undeletable and can be moved in Edit Mode, and has its own container settings.
- It has **no CDM counterpart**. It has no `cdmViewerGlobal` or `cdmCategoryName`, so steal mode and
  merge mode must skip it and must never mirror anything into it.
- Adding a base container to existing saved data follows the Phase 35 precedent: the container is
  created if missing, and no existing position is touched.
- User containers can be created in the reminders category. The new-container dialog's category
  choice gains the third option. Its current polarity is two exclusive checkboxes, so pick the
  simplest template-based form. Per the user's standing preference, a radio dropdown (the pattern
  below) is acceptable.
- Cross-category drag stays blocked. The sections of a category show only under its tab, as today.
  The shared "Not Displayed" section filters by `ns:GetTrackerCategory`. Don't show "Suggested" on
  the Reminders tab; that is at Claude's discretion.

### Reminder kind and dialog (REM-02)
- Add a new canonical kind in `ns.KIND`, e.g. `USER_REMINDER = "userReminder"`, keyed
  `userReminder:<spellID>`, following the Phase 53 naming scheme.
  - `ns:GetTrackerCategory` returns "reminders" for it.
  - The cast index must not start a timer for it: a reminder has no timer.
  - Duplicate rejection works per kind: the same spell may exist as a buff AND as a reminder.
- The dialog is the TRACKER_FIELDS dialog. On the Reminders tab, General shows the portrait, the
  Spell ID with its secret? badge, and "Cover all ranks" on Forever, with **no Duration**. Advanced
  shows the portrait and **only the aura ID**: default = the spell's ID, following the Spell ID box
  as it does today, stored as nil when equal. There is no "End when the aura is lost" and no cast
  rule.
  - Drive this through the existing per-field `available`/`visible` hooks by kind. Don't special-case
    the walker.
- Title: "Add Reminder" / "Edit Reminder". Right-click Edit works on reminder tiles.
- Tooltips and icon resolution for a reminder are the same as for a user buff (the spell's icon and
  name, and the secrecy line).

### Runtime (REM-03)
- A reminder shows iff **the aura is readable right now** and the latest real read says it is
  **absent**.
  - It hides while the aura is present.
  - It hides **the moment combat starts** (PLAYER_REGEN_DISABLED), even though no UNIT_AURA fires
    then.
  - It hides whenever the read is unreadable: secret, restricted, or an M+ key. **Never** show a
    stale "missing" state.
  - This deliberately differs from Phase 57's "absent", which held its last known state.
- Reuse the Phase 57 aura-state machinery (ns:RefreshAuraStates, ns.auraState, the watch list, the
  rank and aura-ID families, and the allowlisted aura readers checked by scripts/aura-read-gate.js).
  Key it on reminder entries instead of on `entry.visibility`. Keep the "an unreadable read is never
  absent" rule (DTRK-06) intact.
- Leaving combat refreshes the states, as today, so a missing buff shows again out of combat.
- Display: a reminder draws as a full-colour CDM-styled icon with no cooldown swipe and no timer
  text. It takes no grid cell while hidden (the Phase 57 WR-01 slot-filtering behaviour). In
  Edit Mode and preview, reminders draw so the container can be arranged.
- Hot paths: no new per-frame work or per-event allocation. The combat-start hide is a dirty flag
  and a redraw, not a polling loop.

### Visibility option removed (REM-04)
- Remove the visibility dropdown field and its WR-01 cooldown tip from TRACKER_FIELDS. Remove the
  "present" aura-driven start (ns.auraStartPending and its paths) and the VisibilityGate branches
  for buffs and cooldowns, and any code that exists only for them. What reminders reuse stays,
  renamed if its name now misleads.
- **Keep the pattern on record:** the radio dropdown (`WowStyle1DropdownTemplate` + `SetupMenu` +
  `rootDescription:CreateRadio`) is the chosen control for any future multi-choice setting. The user:
  "do keep the note/pattern of using dropdowns for multi-selection like that in case we want
  something like this in the future". Put a short comment where the dropdown code was removed, or
  beside the TRACKER_FIELDS contract comment. If the new-container dialog uses the pattern, that
  keeps a live example.
- **Migration, schema v10**, following the chain rules (a new block; the v9 block is pinned to its
  literal; mirrored in scripts/migrate-dryrun.js with selftest cases first):
  - A `userBuff` entry with `visibility == "absent"` becomes a `userReminder`:
    - re-keyed `userReminder:<id>`;
    - keeps `spellID`, `auraID`, `coverAllRanks`, and its layoutOrder when possible;
    - drops `duration`, `keepOnAuraLoss`, `endOnCast` and `visibility`;
    - moves into the "Buff Reminders" container, or keeps its container if that container was
      re-categorised; Claude's discretion, and the simplest correct rule wins.
  - If the target key already exists, keep the existing record and drop the migrant.
  - Every other `visibility` value, on buffs and cooldowns alike, is removed.
  - Verify with a real logout/login.
- Cooldown trackers keep their aura ID (it still drives nothing else, unless a remaining rule uses
  it). If nothing reads a cooldown's aura ID after the visibility removal, remove the cooldown's
  aura ID field and drop the key in v10 too. The planner verifies this against the code.

### Claude's Discretion
- The exact category key, container key/frame name, default position, tab label and icon, and the
  reminder icon's in-game look beyond "full colour, no timer".

</decisions>

## Specific Ideas

The user's words: "I want to simplify making a aura reminder, I want it to not be a advanced option
anymore and be instead of category of it's own, like cds, buffs and reminders, where all reminders
are buffs but they only show when buff is not present (or not show in combat aswell, due to
secret)."

On visibility: "Let's remove the 'visibility' dropdown all together for now. I think the real use
case is only buff reminders and they are getting their own major category now, so no visibility
option on either for now."
