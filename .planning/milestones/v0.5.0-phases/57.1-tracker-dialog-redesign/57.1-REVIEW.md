## Warnings

### WR-01: A cooldown set to "Only while the aura is up" with the default aura ID can be hidden permanently

**File:** `CDMTab.lua:2082-2088` (visibility `validate`), runtime `BuffEngine.lua:1444-1463` (`ns:VisibilityGate`)
**Scenario:** On the Cooldowns tab, open Add and go to Advanced. Pick "Only while the aura is up" and leave the aura ID at its prefilled default (the spell's own ID). Save stores `visibility = "present"` and `auraID = nil`. Most cooldown spells never apply an aura under their own ID, so once the aura is readable `ns.auraState[key]` becomes false. `VisibilityGate` then returns false and the cooldown slot never draws again. The user gets no warning. Phase 57 review IN-05 existed to catch exactly this case. 57.1-CONTEXT left it to planning to decide whether the default aura ID satisfies that rule. The retirement comment only argues that the ID is visible in the box. It does not deal with the case where the spell ID has no aura, which is the common case for a cooldown.
**Fix:** Keep a hint but do not block saving, so General is still never disabled by Advanced. For example, in `update`, show a note under the dropdown when `ctx.kind == ns.KIND.USER_CD`, `state.mode == "present"` and the aura box equals the Spell ID box. Alternatively, restore the IN-05 check only when the aura box still follows the spell:
```lua
validate = function(state, ctx)
	if ctx.kind == ns.KIND.USER_CD and state.mode == "present" and state.aura and state.aura.followsSpell then
		return false, "Enter the buff's aura ID to show a cooldown only while it is up"
	end
	return true
end,
```
With this option, capture `local aura = dialog.GetFieldState("auraID")` at build time, as the old code did.

### WR-02: A too-large Spell ID shows up as an "Advanced: Aura ID is too large" error

**File:** `CDMTab.lua:1945-1949` (follow) together with `CDMTab.lua:1980-1985` (auraID `validate`) and `CDMTab.lua:1620-1630` (spellID `validate`, which has no size check)
**Scenario:** On General, type a 10-digit Spell ID above 2147483647 (the box allows 10 digits). The spellID validator accepts it. The aura box copies the text while it follows the spell, and its own size check then fails. The user, still on General, sees "Advanced: Aura ID is too large" and Add is disabled, pointing at a tab and a field they never touched. This breaks the spirit of "Advanced never disables General": the actual fault is the General value.
**Fix:** Put the 32-bit bound on the Spell ID validator, so the General message comes first in field order. Also skip the aura check while the aura box follows the spell:
```lua
-- spellID validate
if spellID > 2147483647 then return false, "Spell ID is too large" end
-- auraID validate
if not state.followsSpell and state.editBox:GetNumber() > 2147483647 then ...
```

## Info

### IN-01: The comment about the aura badge contradicts the code

**File:** `CDMTab.lua:1956-1960`
**Issue:** The comment says the aura badge stays hidden while the box follows the spell ("badgeID 0 leaves the level nil"). Following now fills the box with the spell ID, so `typed > 0`, `badgeID` becomes the spell ID, and the badge shows. On the Advanced tab that is arguably what the user wants, because the General badge is not visible there. But the comment describes behaviour the code does not have.
**Fix:** Update the comment to say the badge shows the watched ID's secrecy on Advanced, including while following. Or, if the old intent still holds, use `local badgeID = (typed > 0 and not state.followsSpell) and typed or 0`.

### IN-02: The follow write calls RefreshState from inside RefreshState's own update loop

**File:** `CDMTab.lua:1945-1949`
**Issue:** `state.editBox:SetText(spellText)` inside `update` fires OnTextChanged, which calls `onChange` and then `RefreshState()` while the outer RefreshState is still in its update loop. Fields after auraID get `update` twice, and `Layout`/`ValidateAll` can run twice. It is harmless today, because every `update` compares before writing and the nested follow is a no-op. It is fragile, though: any later field whose `update` is not idempotent would misbehave.
**Fix:** Add a guard, for example `state.syncing = true; SetText(...); state.syncing = false`, and skip `onChange()` in the OnTextChanged handler while `state.syncing` is set. The outer pass already updates the later fields and validates.

### IN-03: Advanced-tab errors still disable Add/Save while General is shown

**File:** `CDMTab.lua:2337-2353` (ValidateAll), `CDMTab.lua:2177`
**Issue:** An invalid Advanced value disables confirm on either tab, for example a malformed cast rule, or the new General Spell ID matching an ID already listed in "Ends when you cast". This is the planned design, and the "Advanced: " prefix points the user to the right tab (57.1-02 "Known behaviour"). Recording it in case "Advanced never disables General" was meant to cover the confirm button as well. The Spell ID ↔ cast-rule case is the one where a General edit produces an Advanced error.
**Fix:** No change needed if the current reading is the intended one. Otherwise, confirm with the user.
