# Phase 57.1 Plan 01: Drop the saved `detailed` flag Summary

**Schema v9 (ns:MigrateDropDetailedFlag) drops the saved `detailed` mode flag on login, clearing auraID/keepOnAuraLoss/visibility/endOnCast only on records that never opted in; every runtime gate that used to read entry.detailed now keys on the value itself, specified first in scripts/migrate-dryrun.js's migrateV9 and reconciled line-for-line in Lua.**

## Performance

- **Duration:** ~35 min
- **Tasks:** 3/3 completed

## Accomplishments

- `scripts/migrate-dryrun.js` gained `migrateV9(db, log)`, run last in `migrate()` after `migrateV7`/`migrateV8`. It clears the four Advanced keys (`auraID`, `keepOnAuraLoss`, `visibility`, `endOnCast`) on any entry whose `detailed` was not exactly `true`, then deletes `detailed` unconditionally. Cases A, D, F and G now assert `schemaVersion === 9`; a new Fixture E + case H covers a `detailed = true` record keeping all four values, a `detailed = false` record and a no-`detailed`-key record both losing them, `detailed` gone everywhere, and a second `migrate()` pass changing nothing (same object identity, same fields). `--selftest` reports `SELFTEST PASS (8 cases)`.
- `BuffEngine.lua`: `CURRENT_SCHEMA_VERSION = 9`. `ns:MigrateKindKeys` (schema v8) is now pinned to the literal `8` on both its early-return gate (`if ver >= 8 then`) and its stamp (`ns.db.schemaVersion = 8`), matching the v6/v7 precedent, so bumping the constant to 9 can never let a completed v8 database re-run v8 or skip v9. The new `ns:MigrateDropDetailedFlag()` walks `ns.db.trackedBuffs`, clears the four Advanced keys on any `type(entry) == "table"` whose `entry.detailed ~= true`, then sets `entry.detailed = nil` unconditionally, stamps `CURRENT_SCHEMA_VERSION` and calls `ns:RebuildCastIndex()` -- line-for-line equivalent to the node mirror's `migrateV9`.
- Both `ns:InitBuffEngine` (BuffEngine.lua) and the `PLAYER_ENTERING_WORLD` branch (Core.lua) call `ns:MigrateDropDetailedFlag()` immediately after `ns:MigrateKindKeys()`, so a race-deferred v7/v8 still resolves v9 in order on the same retry. The v6 stamp comment now names v9 as the block that writes `CURRENT_SCHEMA_VERSION`.
- Runtime gates are now value-keyed everywhere (ADD-07 "no `detailed` flag anywhere"): `ns:DetailedAuraID` returns `entry.auraID` whenever it is a number > 0 (no `entry.detailed and` term); `ns:CancelsOnAuraLoss` returns `false` whenever `entry.keepOnAuraLoss` is truthy; `ns:ApplyEndOnCast`'s `if e and e.detailed then` is `if e then`; `ns:VisibilityGate` no longer early-returns on a missing `detailed` flag (the kind and `entry.visibility` checks that follow it already return `nil` for a tracker with no mode); Core.lua's `ns:RebuildDetailedRuleIndex` drops the `entry.detailed` term from both of its indexing conditions. `AddTrackedBuff`'s IN-01 block (a built-in kind minted from a racial cooldown) still clears the four Advanced keys, just no longer a flag that no longer exists.
- Comments across BuffEngine.lua, Core.lua and Providers.lua that described "a detailed tracker" or "entry.detailed"-gated behaviour were reworded to describe value-keyed behaviour (e.g. "only entries with a saved rule are indexed", "a tracker with an Advanced value", "which lists only trackers with a saved visibility mode"). `ns.detailedRankFamilies` and the `DetailedAuraID`/`RebuildDetailedRuleIndex` function names are unchanged (renaming was out of scope).

## Decisions Made

- The node mirror's `migrateV9` logs a per-key line only when a field actually changed (mirroring the "one log line per changed key" example in the plan), while the Lua migration prints nothing per-key -- consistent with the existing v7/v8 blocks, which also print nothing per-key (only v0-v3's earlier, pre-Phase-53 blocks print a summary line).
- Both the JS and Lua deletions of `detailed` are unconditional (`entry.delete('detailed')` / `entry.detailed = nil`) regardless of whether the key was present, rather than branching on "had detailed" vs "never had detailed" -- this is what the plan's action text specifies and it keeps the two implementations trivially reconcilable.

## Performance and Cleanup Review (CLAUDE.md)

- No new allocations were introduced: every edit either deletes a boolean condition (`entry.detailed and ...`, `if not entry.detailed then return nil end`) or rewords a comment. `ns:DetailedAuraID` and `ns:CancelsOnAuraLoss` remain allocation-free, single-branch functions with one fewer field read each now that `entry.detailed` is gone.
- `ns:MigrateDropDetailedFlag` is a login-time-only migration (gated to run at most once per database, like v7/v8), not a hot path -- its `pairs(ns.db.trackedBuffs)` walk mutates existing tables in place and allocates nothing.
- No dead code was left behind: every removed `entry.detailed` read was either a condition term deleted outright or an early-return block deleted outright, not commented out or stubbed.
- No duplication was introduced by this plan; nothing to unify.
