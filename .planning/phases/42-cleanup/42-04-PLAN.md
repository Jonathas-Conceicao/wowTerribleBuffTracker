  <name>Task 2: Reuse a per-widget table for the placeholder proc (D2)</name>
  <files>Display.lua, .planning/todos/2026-09-21-placeholder-proc-table-allocates-per-tick.md</files>
  <action>
Implement 42-CONTEXT.md **D2**, the solution the todo file already had approved.

Two sites allocate a fresh table per inactive placeholder slot per tick:

- `RenderBarContainer`, around line 1196:
  `bar.proc = { spellID = info.spellID, label = info.label, key = slot.key }`
- `RenderIconContainer`, around line 1558:
  `icon.proc = { spellID = info.spellID, label = info.label, key = entry.key }`

Both are reached whenever `showPlaceholders` is true — `not settings.hideWhenInactive or
ns.configOpen or barEditing` — inside a 20 Hz loop, in combat. A player who turns off "hide when
inactive" pays one table allocation per inactive tracker per tick, and Phase 36 made the container
count unbounded, which is what turns it from a rounding error into something worth fixing.

Replace each with a per-widget owned table, exactly as the todo sketches:

    local p = bar._placeholderProc
    if not p then
        p = {}
        bar._placeholderProc = p
    end
    p.spellID, p.label, p.key = info.spellID, info.label, slot.key
    bar.proc = p

and the `icon` / `entry.key` equivalent at the second site.

**`bar._placeholderProc` must be a separate field. Never wipe or reuse `bar.proc` itself.**
`bar.proc` is sometimes a *borrowed* reference: the timer branch does `bar.proc = timer`, storing
the live timer table directly, and the merged branch does `bar.proc = slot`. A naive
"wipe and reuse `bar.proc`" would wipe a live timer.

**Assign all three fields on every pass, unconditionally**, as written above. The table outlives the
slot that last used it, so a field assigned only on some paths would leak a previous slot's value
into the next one's tooltip. Concretely: `ns:ShowBuffTooltip` reads `proc.duration` when
`opts.showDuration` is set. This table has no `duration` today and must never gain one
conditionally — if a future change needs a fourth field, it is assigned on every pass or it does not
go in this table.

**Before committing, grep every read of `.proc`** and record the result in the summary. Planning
found these and nothing else, but re-run it rather than trusting this list:

    grep -rn '\.proc\b' *.lua

- `Display.lua:393` and `Display.lua:508` — the bar and icon `OnEnter` handlers, both
  `ns:ShowBuffTooltip(self, self.proc)` (D-19). `ns:ShowBuffTooltip` reads `proc.spellID`,
  `proc.label` and `proc.duration` synchronously and never stores the table, so it cannot observe
  the reuse.
- `CDMTab.lua`'s two `ns:ShowBuffTooltip` call sites pass tables of their own, not a widget's
  `.proc`. They are unaffected.
- Nothing anywhere compares two `.proc` values for identity, or retains one across frames. That is
  the property the reuse depends on — if the grep turns up a site that does, stop and report rather

Do not change the surrounding branch structure, the `info`/`resolvedSpellID` resolution, the
