## Summary

The metaReminder kind goes through the shared reminder paths the way the phase intended. I traced each of these and found them correct:

- `ns.REMINDER_KINDS` feeds category, watch list, VisibilityGate, preview exclusion and ApplyEndOnCast.
- `ns:StartReminderFromCast` is the one shared cast start.
- RefreshAuraStates handles expiry sync, hold-while-unreadable and cast grace.
- `FIXED_LOAD` pins the load rule to When known.
- Each kind has its own cast and rank namespaces, so a userReminder and a metaReminder for one spell both start on one cast and neither blocks the other.

Other checks came out clean:

- **Upvalue order:** `PlaceSuggestedKeyTile` is declared above `RefreshTBTSections`. The Providers.lua table locals are declared above their functions. Every cross-file call goes through `ns` with a nil guard.
- **Allocations on the hot path:** none new. OnTrigger adds two table lookups. The Suggested key list is a wiped module array.
- **Secret values:** the pet-spellbook pass guards every value it reads.
- **`ns:ApplyMetaReminderDef`:** it is idempotent (it writes only on a difference) and touches only metaReminder entries. `ns:RebuildRankIndex` runs it before `rebuildOwners` reads `coverAllRanks`, so a freshly dragged entry gets its rank family in the same call.
- **Racial cooldown tiles:** the shared `PlaceSuggestedKeyTile` does not break them. It now also hides a pooled `chargeCount` the old inline code left stale, which is a small fix.

The main defect is inherited from 57.2-05, but this phase makes it the default path. A reminder treats any player cast of the spell as proof that the buff is on the player. Ten of the fourteen class-buff rows are spells normally cast on other people. The rest of the findings are about Blood Pact's pet-book refresh, orphaned or re-keyed table rows, and dead or misleading code.

## Critical Issues

### CR-01: Buffing another player hides the caster's own missing-buff reminder

**File:** `Providers.lua:201-222` (the cast start, called from `Providers.lua:308` and `:325`)
**Issue:** `UNIT_SPELLCAST_SUCCEEDED` carries no target. `ns:StartReminderFromCast` sets `ns.auraState[key] = true` and refills a full-duration timer on any player cast of the spell. It runs for every metaReminder row. Ten of the fourteen rows are routinely cast on other players: Arcane Intellect, Power Word: Fortitude, Mark of the Wild, Thorns and all six Blessings.

Here is the failure. A paladin whose own Blessing of Might has run out blesses the tank. The reminder, whose only job is to show that the paladin's own buff is missing, hides at once, and a 60-minute timer starts. Nothing corrects this until some later player `UNIT_AURA`. That event finds the aura readably absent after `CAST_AURA_GRACE`, ends the timer and shows the reminder again. Out of combat, for example while buffing the group before a pull, that event can be minutes away. No removal event is coming, because the buff was already gone.

A second, smaller effect: if the caster's own buff is up with 3 minutes left, the refill moves the timer to 60 minutes. Only the next readable aura read shortens it back.

The same logic already applies to a userReminder (57.2-05 WR-05: "the cast is evidence the buff is up"). For class buffs, though, that assumption is wrong in the common case, and MREM-01 routes every row through it.
**Fix:** Keep the cast start, which is right for self-cast buffs and still covers the case where the aura arrives after the cast. Also queue one coalesced re-read just after the grace window, so a readable absence corrects the state within about 0.6 s instead of waiting for an unrelated aura event. Use a file-scope function and a pending flag, with no closure per cast:
```lua
-- Providers.lua, file scope (above ns:StartReminderFromCast)
local reminderRecheckPending = false
local function RecheckReminderAuras()
	reminderRecheckPending = false
	if ns.RefreshAuraStates then
		ns:RefreshAuraStates()
	end
end

-- inside ns:StartReminderFromCast, after ns.auraState[key] = true
if not reminderRecheckPending then
	reminderRecheckPending = true
	C_Timer.After(ns.CAST_AURA_GRACE + 0.1, RecheckReminderAuras)
end
```
RefreshAuraStates already does the rest. After the grace window, a readable absence ends the proc (cancel-on-aura-loss is forced on for metaReminder) and sets the state to false. A readable presence syncs the expiry down to the aura's real value. Add a UAT row: "Paladin with own blessing missing blesses a party member: reminder stays or reappears within 1 s."

## Warnings

### WR-01: Blood Pact's rank family is only refreshed if SPELLS_CHANGED fires when the pet changes

**File:** `Core.lua:975-1011` (step 5), `Core.lua:2018-2027` (the only rebuild trigger)
**Issue:** The imp's Blood Pact rank reaches the aura watch only through step 5 of `ns:ResolveRankFamily`, and only on a `ns:RebuildRankIndex`. The addon registers no `UNIT_PET` or `PET_BAR_UPDATE` handler, so the design assumes `SPELLS_CHANGED` fires whenever the imp is summoned, dismissed or replaced. Retail's spellbook pet category does refresh on SPELLS_CHANGED, which suggests it does, but that is not proven for Forever.

If the event does not fire, a leveling warlock is affected. Their imp casts a lower rank (6307, 7804, 7805 or 11766), so the watch list stays `{11767}` and the reminder shows while Blood Pact is on the player.

A related gap: the pass also admits `Enum.SpellBookItemType.PetAction` items. `SpellBookItemInfo.spellID` is documented as "May be nil if item is not a spell", so a Blood Pact entry reported as PetAction would add nothing. `AddFamilyID` drops the nil silently, which is safe but a silent failure.
**Fix:** Register `UNIT_PET` and route `unit == "player"` (with an issecretvalue check) to the existing coalesced `ns:RequestLoadRefresh()`. That call already rebuilds the rank index. Add to the UAT: summon the imp after login with a warlock below 60 (imp rank below 5) and confirm the reminder hides. If Forever reports Blood Pact as PetAction with a nil spellID, the family needs a different source, such as the known rank IDs.

### WR-02: A re-keyed or removed row leaves a silent orphan that runs on stale data, and can end up as two reminders for one buff

**File:** `Providers.lua:1525-1531` (`ns:ApplyMetaReminderDef` early return), `Providers.lua:1490-1503` (rows keyed by spell ID)
**Issue:** The key is `metaReminder:<spellID>`, and `ns:ApplyMetaReminderDef` looks the entry up by `entry.spellID`. If a row is removed, or its spell ID changes, existing saved entries quietly become orphans.

A spell ID change is likely soon. The CONTEXT says each aura ID is assumed equal to its spell ID and that the user will verify every row in game, and a correction means a new ID. After such a change:

- The old `metaReminder:<oldID>` keeps its last copied duration and `coverAllRanks`. It is still loaded and still drawn, with no row behind it.
- The Suggested tab now offers `metaReminder:<newID>`, which creates a second reminder for the same buff.
- The orphan cannot be edited (IsEditableTracker), and nothing marks it as orphaned.

So the "one source of truth" holds only while the rows never change, and `entry.label` is never re-derived at all.
**Fix:** Either add a small alias map (`[oldID] = newID`) that `ApplyMetaReminderDef` or a migration uses to re-key the entry, or leave orphans unloaded: in `ns:RebuildTrackerLoad`, treat a metaReminder with no `ns:MetaReminderDef` as not loaded, so it greys out with a reason such as "no longer a built-in class buff". At minimum, write this down beside the table as the rule for changing a row's ID.

### WR-03: Dropping a class-buff Suggested tile on the delete zone deletes the placed reminder

**File:** `CDMTab.lua:758-764` together with `CDMTab.lua:1052-1063`
**Issue:** Racial buff, item and SUGGESTED_KEYS tiles drop out of the Suggested list once tracked. Class-buff tiles stay by design ("dragging it again moves that reminder"). `EndDrag`'s delete branch calls `ns:RemoveTrackedBuff(tbtDragState.spellID)` with the tile's key, which for a class-buff tile is the key of the live tracker. So an accidental drop of a catalogue tile on the red X removes the tracker the user placed, with no confirmation.

The same path already exists for the racial cooldown tiles, but this phase adds fourteen more tiles that behave this way.
**Fix:** In the `result == "delete"` branch, ignore drags that started in Suggested:
```lua
if result == "delete" then
	local spellID = tbtDragState.spellID
	local fromSuggested = tbtDragState.isFromSuggested
	wipe(tbtDragState)
	if not fromSuggested then
		ns:RemoveTrackedBuff(spellID)
	end
	...
```

### IN-01: The metaReminder branch of FindTrackerConflict is unreachable

**File:** `BuffEngine.lua:982-985`
**Issue:** None of the three callers passes `ns.KIND.META_REMINDER`: `AddTrackedBuff` (`:1116`) and `UpdateTrackedBuff` (`:1258`) only ever use user kinds, and the dialog (`CDMTab.lua:1696`) only opens editable kinds. A duplicate metaReminder is really refused by the canonical-key check at the top of `AddSuggestedTracker` (`CDMTab.lua:143`). The branch and the SUMMARY both claim a refusal path that never runs.
**Fix:** Remove the branch, or keep it and change the comment to say it exists for future callers and that `AddSuggestedTracker`'s key check is the real guard.

### IN-02: Blood Pact's "not loaded" tooltip names the wrong spell, and any non-imp warlock gets a reminder that never goes away

**File:** `Core.lua:701`, `Core.lua:1295-1301`, `Providers.lua:1497`
**Issue:**
- The load gate asks about Summon Imp (688), but `LOAD_REASON_UNKNOWN` says "this character does not know this spell" on a Blood Pact tile.
- Summon Imp is learned at level 1, so every warlock who places the tile and plays with a Voidwalker, Succubus or Felhunter sees the reminder all the time. This follows the spec, but it should be written into the UAT and the tooltip.

**Fix:** Pass the known ID into the reason text, e.g. "does not know Summon Imp". Add a note to the tile tooltip.

### IN-03: Some rows cannot behave as reminders for common specs

These rows are the user's data. The point is to record the consequence.
**Fix:** Add both notes to the row comments and the UAT.
