# Phase 57.1 Plan 02: Tracker Dialog Redesign Summary

**The add/edit dialog is now two Blizzard text tabs (General, Advanced) built from a one-line XML virtual and a generic per-field `tab` property; the Detailed checkbox and its two helper functions are gone, Advanced opens prefilled with every default (the aura ID box follows the Spell ID box until edited), and visibility is one WowStyle1DropdownTemplate radio dropdown instead of three checkboxes.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 3/3 completed

## Accomplishments

- `CDMTab.xml` gained `TBTTopTabSystemTemplate`, a virtual `TabSystemTemplate` frame with `tabTemplate = "TabSystemTopButtonTemplate"` and `minTabWidth = 80` set as XML KeyValues (required, since `TabSystemMixin:OnLoad` reads `tabTemplate` before any Lua could set it), inserted above the existing `<Script file="CDMTab.lua"/>` line. The TOC was not touched.
- `CreateAddDialog` now creates one `TBTTopTabSystemTemplate` frame anchored above the dialog (`BOTTOMLEFT` to the dialog's `TOPLEFT`), adds "General" and "Advanced" tabs, and wires `SetTabSelectedCallback` to a closure that updates a new `currentTab` local, forces `RefreshState(true)`, focuses the first shown box only while the dialog is already visible, and returns `false` (required, or `TabSystemMixin:SetTab` suppresses its own visual selection). `OpenForAdd` and `OpenForEdit` both call `tabSystem:SetTab(generalTabID)` before `dialog:Show()`, so opening always selects General, then call the new shared `FocusFirstShown()` helper that replaces the two near-identical focus loops that used to live at the end of each Open function.
- The walker's field visibility split into two flags. `field.relevant` is a field's own `visible(state, ctx)` answer, independent of the tab -- `ValidateAll` and the confirm handler's read loop both walk `field.relevant`, so a value on the tab that is not currently shown is still validated and still saved. `field.shown` additionally requires `not def.tab or def.tab == currentTab` -- `Layout()` and the Tab/Enter ring still walk `field.shown` only, so the dialog's height and focus order follow whichever tab is selected. A validation failure on a `tab = "advanced"` field is prefixed `"Advanced: "` in the dialog's error label, regardless of which tab is currently selected, so a user reading General still knows where to look.
- `TRACKER_FIELDS`: the whole `detailed` entry (the master checkbox) is deleted, along with `ns:DetailedModeOffered` and `ns:DetailedChildShown` and their comment block. `spellID`, `secrecyBadge`, `duration` and `coverAllRanks` are tagged `tab = "general"`; `auraID`, `keepOnAuraLoss`, `visibility` and `endOnCast` are tagged `tab = "advanced"`; `spellPreview` (the portrait) carries no `tab`, so it still draws on both tabs. `keepOnAuraLoss` keeps its own `visible()` (`ctx.kind == ns.KIND.USER_BUFF`) on top of its tab tag, since a cooldown tracker has no aura to lose and that field is genuinely irrelevant there, not just on the other tab.
- `auraID`'s label changed to "Aura ID:" (no longer "blank = same as spell" -- the box is prefilled now). Its state gained `followsSpell`, starting `true`; the box's `OnTextChanged` only sets `followsSpell = false` when `userInput` is `true`, so a programmatic `SetText` (the follow itself) never breaks following. `update` compares the box's text against the Spell ID box's text before writing, so the follow's own `SetText` cannot recurse. `reset` sets `followsSpell = true` and blanks the box (the first `RefreshState(true)` of every open fills it in via the follow, before the dialog shows); `prefill` sets `followsSpell = (entry.auraID == nil)`. `read` and `validate` are unchanged: blank or equal to the spell ID still stores nil.
- Visibility is now one `WowStyle1DropdownTemplate` dropdown driven by a new file-local `VISIBILITY_CHOICES` array (`always`/`present`/`absent` with their display text), built via `SetupMenu` + one `CreateRadio` call in a loop, with `IsSelected`/`SetSelected` closures built once at build time (not inside the menu generator). `reset` and `prefill` both call `state.dropdown:GenerateMenu()` after changing `state.mode`, which is the mechanism `Blizzard_Menu/DropdownButton.lua`'s own `SetupMenu` comment documents for refreshing the button's shown text outside of a menu open. `ns:SyncVisibilityChecks` and the three checkboxes it used to synchronize are deleted. The Phase 57 IN-05 rule ("Enter the aura ID to show a cooldown by aura") is retired -- `validate` always returns `true` now, since the aura ID box is prefilled with the spell's own ID on the same tab, so the watched ID is always visible without a separate hint.
- The `TRACKER_FIELDS` contract comment above the array was rewritten: `tab` is documented in the per-element list; `NOT READ MEANS NOT WRITTEN` (WR-02) is now explicitly restricted to a field hidden by its own `visible()`, with a new one-line sentence -- `-- Tab-hidden fields are still validated and read; defaults are stored as nil.` -- covering the tab case; both "Detailed mode (Phase 56)" and "Detailed mode (Phase 57)" paragraphs are replaced by one "Advanced tab (Phase 57.1)" paragraph naming the four Advanced fields in order, their prefilled defaults, and the value-keyed runtime readers (`ns:DetailedAuraID`, `ns:CancelsOnAuraLoss`, `ns:VisibilityGate`, `ns:ApplyEndOnCast`, `ns:RebuildDetailedRuleIndex`); the hazard paragraph's helper list drops the three deleted helpers and adds `VISIBILITY_CHOICES`.

## Decisions Made

- The tab system frame is created once inside `CreateAddDialog` (matching the existing once-per-dialog construction of `fieldStates`/`focusRing`/buttons) and reselected to General via `SetTab(generalTabID)` on every `OpenForAdd`/`OpenForEdit`, rather than recreated per open.
- `keepOnAuraLoss` is the one Advanced field that keeps a `visible()` hook alongside its `tab` tag, since USER_CD trackers genuinely have nothing for it to control (not merely "on the other tab").
- `auraID`'s `reset` blanks the box and relies on the guaranteed `RefreshState(true)` from `SetTab(generalTabID)` to fill it via the follow, rather than duplicating the Spell ID box's text at reset time.

## Performance and Cleanup Review (CLAUDE.md)

- No `OnUpdate` or other per-frame script was added anywhere in this plan; every new script is event-driven (`OnClick`, `OnTextChanged`, tab-system's own click-driven callback). The dialog remains open-time/change-time work only, same as before.
- `FocusFirstShown()` replaces two copy-pasted focus loops (the old `OpenForAdd`/`OpenForEdit` each ended with an identical `for _, entry in ipairs(focusRing) do if entry.field.shown then ... break end end`) with one shared local function -- a duplication this plan itself introduced by touching both call sites, unified per the CLAUDE.md GSD Workflow rule.
- `IsSelected`/`SetSelected` for the visibility dropdown are built once per field `build()` (not per `SetupMenu` generator call, which can run more than once per dialog open per `DropdownButtonMixin:SetupMenu`'s own comment), so no closures are allocated on menu regeneration.
- No dead code left behind: every deleted reference (`ns:DetailedModeOffered`, `ns:DetailedChildShown`, `ns:SyncVisibilityChecks`, the `detailed` field, the three visibility checkboxes) was removed outright, not commented out.
- Nothing pre-existing was refactored beyond what this plan's own tab split required (PROJECT.md's "No refactors during cleanup phases" boundary was not tested here, since no cleanup phase is running, but the same discipline was applied: only code this plan touched was changed).

## Known behaviour

- A validation message from a field whose `tab` is `"advanced"` is shown in the dialog-level error label prefixed with the literal string `"Advanced: "` -- and this happens regardless of which tab is currently selected. If the user is looking at General and an Advanced field is invalid (for example, a cast-rule ID list that includes the tracker's own spell ID), confirm stays disabled and the error label reads `"Advanced: Remove this tracker's own spell ID"` even though nothing on the visible General tab looks wrong. This is intentional (57.1-CONTEXT, task 1 acceptance criteria) and is the mechanism that lets Rule "General never becomes invalid or disabled because of Advanced" still surface an Advanced-tab problem without silently blocking Save.
