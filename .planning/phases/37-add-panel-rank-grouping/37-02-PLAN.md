# Phase 37 — Plan 02: Tracker Type, Container Choice & Rank Dispatch

**Created:** 2026-09-21
**Requirements:** ADD-01, ADD-02 (the data half — Plan 03 builds the controls), RANK-01, RANK-02

## Approach

Plan 03's dialog needs somewhere to put the three answers it collects. This plan builds that, and wires
the rank lookup into the cast path. It shares no file with Plan 01, so both run in wave 1.

**Three new fields on a `ns.db.trackedBuffs` entry, and no schema bump.**

| field | values | absent means |
|---|---|---|
| `trackerType` | `"buff"` / `"cooldown"` | `"buff"` — every entry written before this phase |
| `section` | already exists | already `"hidden"` |
| `coverAllRanks` | `true` / nil | not covered |

`section` is not new; this plan only lets the caller supply it. No `schemaVersion` bump is needed or
wanted: every one of these reads through an `or` default, so a v0.4.0-era database and a v0.3.0 one
converge with no migration. This is the same rule `stealMode`, `userContainers` and `nextContainerId`
were added under in Phases 35.1 and 36 — additive keys with an idempotent default are seeded at read
time, not version-gated. Do not touch `CURRENT_SCHEMA_VERSION`.

**`ns:AddTrackedBuff(spellID, duration, label, opts)`.** One new trailing table parameter, so the existing
call shape stays valid. `opts` is `{ trackerType, section, coverAllRanks }` and every field is optional.
`opts.section` is written through as-is when it is a string, and falls back to `"hidden"` otherwise —
that is the locked v0.2.0 "new trackers land in Not Displayed" decision, preserved exactly. The container
choice supersedes it only when the caller actually supplies one; an unchosen container must never resolve
to a visible container. `opts.trackerType` is written only when it is exactly `"cooldown"` (anything else,
including nil, stores `"buff"`), so a malformed caller cannot invent a third type.

**Cooldown trackers are created here and deliberately do not render.** Phase 38 owns cooldown rendering
(`CD-01`…`CD-06`): an icon-only tracker driven by `C_Spell.GetSpellCooldownDuration` handed to
`Cooldown:SetCooldownFromDurationObject`. Until that lands, a cooldown entry carries a nominal duration
that means nothing, and letting the buff engine start a timer on it would draw a countdown bar that is
simply wrong. So `UserSpellProviderMixin:OnTrigger` and `ns:StartAllPreviewTimers` both skip entries whose
`trackerType` is `"cooldown"`, each with a comment naming Phase 38 as the owner of the removal. The entry
still exists, still appears in the CDM tab's section list (that list reads `ns.db.trackedBuffs` directly
and is untouched by this plan), and still moves between containers. **A cooldown tracker created in this
phase is expected to show nothing in the world — that is correct behaviour for Phase 37, not a defect.**

**The rank lookup is one table read on the miss path.** `UserSpellProviderMixin:OnTrigger` already does
`ns.db.trackedBuffs[spellID]`. When that misses, it now tries `ns.rankIndex[spellID]` — Plan 01's flat
`castSpellID -> ownerKey` map — and re-looks-up the entry under the owner key. Plan 01 guarantees that map
never contains an ID that is itself a tracker slot, so the direct hit always wins and the fallback can
never shadow a real tracker. Cost on a cast that matches nothing: one extra failed table lookup. Cost on a
cast that matches: one extra successful lookup. No API call, no `pcall`, no allocation — all of that
happened at rebuild time in Plan 01.

**The proc keeps the owner's identity, which is the whole point.** When rank `133` drives the tracker
owned by `145`, the returned proc has `key = 145` and `spellID = 145`, not `133`. `proc.key` stays the
stable slot identity and `proc.spellID` stays the derived numeric — the locked v0.2.4 decision, not
inverted. This is also literally what `RANK-02` asks for: whichever rank the player casts, TBT's timer is
filed under the same ID the CDM holds, so the two cannot show contradictory state side by side.

**`aliveBuffs` becomes the family when there is one.** The cancellation scan
(`ns:ScanActiveTimersForCancellation`) walks `proc.aliveBuffs` looking for any live aura. Rank 1's aura and
rank 3's aura are different IDs, so a single-element `aliveBuffs` would cancel a covered tracker the moment
the scan ran. Assign `ns.rankFamilies[ownerKey]` when present, else `{ spellID }` as today. The proc holds a
**reference** to Plan 01's array, not a copy — that is safe because the scan only reads it with `ipairs`,
and Plan 01 allocates fresh family arrays per rebuild precisely so a live proc's reference stays valid.
Say both halves of that in a comment; the next reader's instinct will be to copy it or to wipe it, and
either would be wrong.

**Plan 01 is a wave-1 sibling, so every reference to it is nil-guarded.** `ns.rankIndex`, `ns.rankFamilies`
and `ns:RebuildRankIndex` are all guarded here, exactly the way `Core.lua`'s `ns:AttachContainerRuntime`
nil-guards the subsystem hooks it calls. This plan therefore lands and works standalone; when Plan 01 lands
too, the guards simply stop firing.

## Risks

- **A covered tracker's `aliveBuffs` is a shared table.** If a future change ever mutates `proc.aliveBuffs`
  in place, it would corrupt every other proc from the same family. Guarded by comment, and by Plan 01
  allocating fresh arrays per rebuild rather than reusing them. The current cancellation scan only reads.
- **A cooldown tracker silently does nothing in-game.** Intended and scoped: Phase 38 renders it. The
  confirmation `print` naming the type is what makes the creation observable in the meantime. Do not
  "fix" this by letting the buff engine start a timer on it.
- **`ns.rankIndex` could in principle go stale between a spellbook change and the next rebuild.** Bounded:
  `SPELLS_CHANGED` covers learning a rank, and add/remove covers the tracker set. A stale index fails by
  not starting a timer, never by starting the wrong one, because the index only ever maps to a key that is
  re-validated against `ns.db.trackedBuffs` before use.
- **`opts.section` could name a container that no longer exists** if a user container is deleted between
  the dialog opening and Add being clicked. Out of scope to defend here: Phase 36 fixed the key-reuse half
  (`nextContainerId` never decrements), and an entry in an unknown section renders nowhere, which is the
  same safe state as `"hidden"`.
