# Phase 37 — Plan 01: Rank Family Resolution & the One Flavour Check

**Created:** 2026-09-21
**Requirements:** ADD-03 (the flavour check itself), RANK-01, RANK-02

## Approach

This plan builds the two things the rest of the phase consumes and nothing else: the single sanctioned
flavour boolean, and the machinery that turns "spell 145" into "145, 133, 143".

**Why the whole rank feature lives in `Core.lua`.** `Core.lua` already owns the only
`C_Spell.GetBaseSpell` / `C_Spell.GetOverrideSpell` calls in the addon (the `TOOL-01` tooltip, near the
end of the file) and with them the `pcall` + `issecretvalue` screening idiom those APIs require. Putting
the family resolver beside its only existing neighbour keeps that idiom in one file instead of copying it
into `Providers.lua`. `Core.lua` also loads first, so `BuffEngine.lua`, `Providers.lua` and `CDMTab.lua`
all see these symbols at both load and run time. Plans 02 and 03 therefore only *read* what this plan
defines, and both nil-guard it so all three plans land independently.

**ADD-03's flavour check is `ns.CLIENT_HAS_SPELL_RANKS`, computed once at file scope in `Core.lua`.**
That is the one place. It is a load-time constant, not a runtime branch, and it has exactly one consumer
in the whole addon: Plan 03's decision to create a "Cover all ranks" checkbox or not create it. Nothing in
this plan reads it — rank resolution is driven entirely by `entry.coverAllRanks`, which only the Forever
checkbox can ever set. That is what keeps this a single check rather than a pattern: the flag gates a
widget's existence, never behaviour.

**Why `GetBaseSpell`/`GetOverrideSpell` alone are not enough, and what actually bridges the ranks.**
The research (`.planning/research/TEST-PLAN-CDM-INJECTION-AND-COOLDOWNS.md`, "New finding not in the
plan — ranked spell IDs on Forever") calls these two APIs the *likely* bridge and records the probes as
never confirmed. They cannot be the only mechanism, because vanilla rank variants are siblings, not
overrides — nothing guarantees `GetBaseSpell(133)` yields `145`. The mechanism that is reliable on a
vanilla client is the one vanilla addons have always used: **all ranks of a spell share a name in the
spellbook**, with the rank in `subName`. So the resolver seeds from base/override (cheap, and it is what
covers retail-style overrides) and then does a **name-matched spellbook scan**, which is what actually
produces `133` and `143` from `145`.

**`RANK-02` is satisfied by the seed, not by the scan.** A user adds the ID their tooltip showed —
say `133` — while the CDM holds `145`. Step 1 asks `133` for its base and override; step 3 finds the
other `133`/`143` siblings by name; step 4 asks each *newly found* sibling for its base and override,
which is where `145` enters the family if the client knows the relationship at all. One extra pass, not a
recursive closure — the family is a set, not a graph walk.

**Storage split — intent persists, derivation does not.** `ns.db` stores only the user's *intent*
(`entry.coverAllRanks`, written by Plan 02). The family is derived at runtime into two module-level
tables, because a spellbook changes between sessions and a persisted family would go stale:

| symbol | shape | lifetime |
|---|---|---|
| `ns.rankFamilies` | `[ownerKey] = { id, id, ... }` (array of numeric IDs, includes the owner's own) | rebuilt; **freshly allocated each rebuild** |
| `ns.rankIndex` | `[castSpellID] = ownerKey` (flat map, excludes IDs that are themselves tracker slots) | rebuilt; **wiped in place** |

`ns.rankFamilies` entries are new tables every rebuild *on purpose* — a live proc in `ns.activeTimers`
holds a reference to one as its `aliveBuffs` (Plan 02), so wiping it in place would silently empty a
running timer's cancellation list. `ns.rankIndex` has no such holder and is wiped with `wipe()` per the
repo's GC-pressure convention.

**Hot-path discipline.** `ns:OnSpellCastSucceeded` runs on every player cast. Plan 02's read is
`ns.rankIndex[spellID]` — one table lookup, no API call, no allocation. Every `pcall`, every
`C_Spell.GetSpellInfo` and the entire spellbook walk happen only inside `ns:RebuildRankIndex`, which runs
at login, on `SPELLS_CHANGED`, and when a tracker is added or removed.

**The rebuild early-outs before it scans anything** when no tracked entry carries `coverAllRanks`. On
retail the checkbox does not exist, so no entry ever carries it, so a retail client never touches
`C_SpellBook` at all — the feature costs nothing where it does not apply, and it costs nothing through a
data-absence check rather than through a second flavour branch.

## Tasks

1. **`Core.lua` — the flavour constant and `ns:ResolveRankFamily`.**
   *Read first:* `Core.lua` (whole file; specifically the `TOOL-01` tooltip block near the end for the
   existing `RelatedID` `pcall` + `issecretvalue` idiom, and the top-of-file `ns.CONTAINERS` block for the
   comment style), `.planning/phases/37-add-panel-rank-grouping/37-CONTEXT.md`.

   Open a new section in `Core.lua` immediately **before** `local eventFrame = CreateFrame("Frame")`.
   Head it with a comment that says, in these terms: this is the milestone's one sanctioned runtime
   flavour check, licensed by explicit user decision 2026-09-20 recorded in `37-CONTEXT.md`; the user was
   offered the data-driven alternative and declined it; no second flavour check may be added anywhere,
   and everything else in the addon stays on data-absence / capability checks.

   Define `ns.CLIENT_HAS_SPELL_RANKS` at file scope:
   - read the interface version with `select(4, GetBuildInfo())`;
   - screen it with `issecretvalue` and `type(...) == "number"` **before** comparing it — the locked rule
     applies even to an API that cannot plausibly return a secret, because the cost of following it is
     nothing and the cost of making an exception is a precedent;
   - the value is `true` when the version is `>= 16000 and < 20000` (the Forever range from
     `37-CONTEXT.md`), `false` otherwise (retail is `120100`);
   - a non-number screens to `false` — absent the ability to tell, do not offer the control.

   Define `function ns:ResolveRankFamily(spellID)` returning a **freshly allocated** array of distinct
   numeric IDs, or `nil` when `spellID` is not a positive number. Use a file-local `AddFamilyID(list, seen, id)`
   helper that screens `issecretvalue(id)`, `type(id) == "number"` and `id > 0`, dedupes via `seen`, and
   otherwise drops the value silently. Use a file-local `RelatedSpellID(fn, id)` helper — the same shape
   as the tooltip's `RelatedID` but taking `id` as a parameter instead of closing over it, so it is
   defined once at file scope and allocates no closure per call — which returns `nil` unless
   `type(fn) == "function"`, `pcall(fn, id)` succeeded, and the result survives the `issecretvalue`/`type`
   screen.

   The four steps, in order:
   1. Seed with `spellID`, then `RelatedSpellID(C_Spell and C_Spell.GetBaseSpell, spellID)` and
      `RelatedSpellID(C_Spell and C_Spell.GetOverrideSpell, spellID)`.
   2. Collect the distinct spell **names** of the seeds via `C_Spell.GetSpellInfo(id)`, taking
      `info.name` only when it survives `issecretvalue` and is a non-empty string.
   3. Scan the player spellbook, capability-guarded — do nothing unless `C_SpellBook`,
      `C_SpellBook.GetNumSpellBookSkillLines`, `C_SpellBook.GetSpellBookSkillLineInfo`,
      `C_SpellBook.GetSpellBookItemInfo`, `Enum.SpellBookSpellBank` and `Enum.SpellBookItemType` are all
      present. For each skill line index, read `skillLineInfo.itemIndexOffset` and
      `skillLineInfo.numSpellBookItems`, then for slot indices `itemIndexOffset + 1` through
      `itemIndexOffset + numSpellBookItems` call
      `C_SpellBook.GetSpellBookItemInfo(slot, Enum.SpellBookSpellBank.Player)`. Keep an item only when
      `itemInfo.itemType == Enum.SpellBookItemType.Spell` and `itemInfo.name` matches a name from step 2
      (screen `itemInfo.name` with `issecretvalue` before the comparison). Add both `itemInfo.actionID`
      and `itemInfo.spellID` through `AddFamilyID` — `actionID` is the base spell ID and `spellID` is the
      overriding one, and on a ranked client they can differ.
   4. One bounded pass, explicitly **not** recursive: for each ID added by step 3, add its
      `GetBaseSpell` and `GetOverrideSpell`. This is what lets a user who added the rank they cast still
      reach the ID the CDM holds (`RANK-02`). Note in a comment that the family is a set and this pass
      runs once, not to a fixed point.

   *Acceptance:*
   - `grep -n 'GetBuildInfo' *.lua` returns **exactly one** line, in `Core.lua`. One, because this is the
     addon's only flavour check by design and the criterion exists to prove that.
   - `grep -n 'CLIENT_HAS_SPELL_RANKS' *.lua` returns exactly one line at this point in the phase — the
     definition. Plan 03 adds its single reader.
   - `ns.CLIENT_HAS_SPELL_RANKS` is assigned at file scope, not inside a function: reading the file shows
     the assignment at indentation level zero.
   - Reading `ns:ResolveRankFamily` shows every value taken from `C_Spell.*` or `C_SpellBook.*` passing
     through an `issecretvalue` screen **before** any `==`, `~=`, `<`, `>` or `..` touches it.
   - `grep -n 'C_SpellBook' Core.lua` shows every call site inside the capability guard — no `C_SpellBook`
     call appears above the guard.
   - `ns:ResolveRankFamily` contains no `while` loop and no self-call: `grep -n 'ResolveRankFamily' Core.lua`
     shows the definition and no call from within its own body.

2. **`Core.lua` — `ns.rankIndex`, `ns.rankFamilies` and `ns:RebuildRankIndex`.**
   *Read first:* `Core.lua` (the section written in Task 1, and `ns:CountContainerTrackers` for the
   established `pairs(ns.db.trackedBuffs)` walk), `BuffEngine.lua` lines 150-200 (`ns:OnSpellCastSucceeded`
   and `ns:AddTrackedBuff` — the shape of a `trackedBuffs` entry and the hot path this feeds).

   Declare `ns.rankIndex = {}` and `ns.rankFamilies = {}` at file scope in the same section, each with a
   one-line comment naming its shape from the table in Approach.

   Define `function ns:RebuildRankIndex()`:
   - Return immediately if `ns.db` or `ns.db.trackedBuffs` is nil (it is called from event handlers that
     can in principle fire before `ADDON_LOADED` has run).
   - Build the owner list into a **module-level reusable table wiped with `wipe()`** — collect every key
     `k` of `ns.db.trackedBuffs` whose entry has a truthy `coverAllRanks` **and** where `type(k) == "number"`
     (a string meta-slot key like `"trinket"` has no rank family). If that list is empty, `wipe(ns.rankIndex)`,
     `wipe(ns.rankFamilies)` and return — this is the early-out that costs a retail client nothing.
   - `table.sort` the owner list ascending, so the result is deterministic. `pairs` order is not, and two
     families can legitimately claim the same ID; a stable order means the same client produces the same
     index every time rather than a coin flip. Say this in a comment.
   - `wipe(ns.rankIndex)`. Do **not** `wipe` the tables inside `ns.rankFamilies` — clear the outer table's
     keys by assigning `nil`, or rebuild `ns.rankFamilies` fresh, because a live proc may hold a reference
     to one of those arrays as its `aliveBuffs`. Comment this; it is the non-obvious half of the design.
   - For each owner key in sorted order: `local family = ns:ResolveRankFamily(ownerKey)`; skip if nil;
     assign `ns.rankFamilies[ownerKey] = family`; then for each `id` in the family insert
     `ns.rankIndex[id] = ownerKey` **only when** `ns.db.trackedBuffs[id]` is nil (an ID that is itself a
     tracker slot owns itself — the index must never shadow a direct lookup) **and** `ns.rankIndex[id]`
     is nil (first owner in sorted order wins a contested ID).

   *Acceptance:*
   - `grep -n 'function ns:RebuildRankIndex' Core.lua` matches, and `grep -n 'ns.rankIndex\|ns.rankFamilies' Core.lua`
     shows both tables declared at file scope.
   - Reading the function shows the empty-owner early-out **before** any call to `ns:ResolveRankFamily`.
   - Reading the function shows `wipe(ns.rankIndex)` present and **no** `wipe(` applied to any table stored
     in `ns.rankFamilies`.
   - Reading the insert loop shows both guards on the same insert: the `ns.db.trackedBuffs[id]` nil test
     and the `ns.rankIndex[id]` nil test.
   - `grep -n 'table.sort' Core.lua` shows a sort inside `ns:RebuildRankIndex`.

## Risks

- **`GetBaseSpell`/`GetOverrideSpell` may contribute nothing on Forever.** The research records the probes
  as never run. That is why the spellbook name scan exists and why it is step 3 rather than a fallback —
  if both APIs return nothing useful, the family is still correct, because siblings are found by name.
- **A name-matched scan can over-match.** Two genuinely different spells sharing a name would merge into
  one family. Accepted: the user opted into "cover all ranks" for that spell, the failure mode is a timer
  starting on a spell the user did not intend, and the vanilla convention is that same-name spellbook
  entries *are* the same spell at different ranks.
- **`SPELLS_CHANGED` fires several times during login.** Each fire is a full rebuild. Bounded by the
  early-out (zero cost when nothing is covered) and by a vanilla spellbook's size; it is an event-driven
  path, never per frame. Do not add debounce machinery for it.
- **`C_SpellBook` may be absent or shaped differently on the Forever build.** Guarded by capability, so a
  client lacking it degrades to base/override-only resolution and a silent single-ID family, not a load
  error. That degradation is exactly the locked "capability checks, not client-identity checks" decision.
