# Phase 37 — Plan 03: The Redesigned Add Dialog

**Created:** 2026-09-21
**Requirements:** ADD-01, ADD-02, ADD-03

## Approach

This is a redesign of a working flow, not a new one. `CreateAddDialog` in `CDMTab.lua` already has the
frame, the backdrop, the two edit boxes, the error label and the Add/Cancel buttons. Three controls go in
between, and the Add handler grows a fourth argument. **Everything else stays as it is.**

**Scope fence, stated so an executor does not wander.** The user reserved the detailed add-panel layout for
discussion when this phase arrived — *"we will discuss the new add popup frame we will have"* — and
`37-CONTEXT.md` records it as a deferred idea. The three controls below are the contract. Do **not**
restyle the dialog, do not reposition the existing widgets relative to each other, do not add a spell-name
preview, an icon preview, a search box, or a container-kind warning. If a layout question comes up that is
not answered here, leave the existing behaviour and note it; it is a question for the user, not a decision
for the executor.

**Control 1 — type (`ADD-01`): a mutually exclusive `UICheckButtonTemplate` pair, "Buff" and "Cooldown".**
Copy the idiom verbatim from `CreateContainerDialog` in this same file (the Icons/Bars pair, Phase 36):
each `OnClick` sets itself checked and the other unchecked, and re-checks itself if clicked while already
checked, so the pair can never both be off. That comment in `CreateContainerDialog` also records *why* it
is not a dropdown — a modern dropdown template is a Midnight-only asset. "Buff" is checked on open.

**Control 2 — container (`ADD-02`): a button that opens `MenuUtil.CreateContextMenu`.** A checkbox pair
does not scale to four base containers plus an unbounded number of user containers. `MenuUtil` is the right
answer and is already proven on both flavours by the right-click menus at the top of this file
(`Move to <container>` / `Add to <container>`), which build their option list by iterating `ns.CONTAINERS`.
Do the same here.

- The menu is built **inside the click handler**, so it is rebuilt every time it opens and a container
  created since the dialog was first constructed appears without any refresh plumbing.
- The list is **"Not Displayed" first, then one option per `ns.CONTAINERS` def in registry order**, using
  `def.title` as the label and `def.key` as the value. Nothing is hardcoded; user containers are in
  `ns.CONTAINERS` since Phase 36 and so are in the list for free.
- Do **not** build it from `SECTION_DEFS`. That list also contains `"suggested"`, which is a catalog, not a
  container — offering it would write a tracker into a section that nothing renders.
- The current choice lives on `dialog.selectedSection`, defaults to `"hidden"`, and is echoed in the
  button's text. **The default is Not Displayed, and that is load-bearing:** the locked v0.2.0 decision says
  new trackers land in Not Displayed, and the container choice supersedes it only when the user actually
  picks. An unchosen container must never fall through to a visible container.

**Control 3 — cover all ranks (`ADD-03`): created only when `ns.CLIENT_HAS_SPELL_RANKS` is true.**
Plan 01 owns the flavour check; this plan reads the resulting boolean and nothing else. The requirement is
precise and the implementation must be too: on retail the widget is **not created at all** — not created
and hidden, not created and disabled. So the `CreateFrame` call sits inside the `if`, `rankCheck` is nil on
retail, and every later reference to it is nil-guarded. On Forever it is checked when the dialog opens.

**Height without a second flavour branch.** The dialog is currently a fixed `220x170` and now needs to be
taller on Forever than on retail. Do **not** write two literal heights behind an `if` — that reads as a
second flavour branch even though it is fed by the first. Instead carry a local `y` offset cursor that each
control advances as it is anchored, let the rank checkbox advance it only when it exists, and call
`dialog:SetSize(240, math.abs(y) + 46)` once after the last control. One code path, two outcomes, driven by
what was created.

**One reset path.** The `addSquare` click handler currently clears the two edit boxes and the error label
itself. With three more controls to reset, that belongs in the dialog. Expose `dialog.ResetFields` from
`CreateAddDialog` and have the click handler call it, so a future control is reset in one place instead of
two.

**What this plan does not do.** It does not render a cooldown tracker — Phase 38 (`CD-01`…`CD-06`) owns
that, and Plan 02 deliberately keeps cooldown entries out of both the cast path and preview. **A cooldown
tracker created through this dialog will appear in the CDM tab section you chose and will show nothing in
the world. That is correct for Phase 37.** The chat confirmation from `ns:AddTrackedBuff` naming the type is
how you observe that the choice was recorded.

  two sides — present on Forever, absent on retail — and only the Forever side is observable now. Retail
  validation is the milestone's second-to-last phase (Phase 44); until then the retail half rests on reading
  the code: the `CreateFrame` for `rankCheck` is inside the `if`, so on a client where
  `ns.CLIENT_HAS_SPELL_RANKS` is false the widget does not exist. Record `ADD-03` as **half-verified,
  retail side deferred to Phase 44** in the phase verification, not as passed.

  same call is already shipping in this file on a path both flavours run. If it fails, it fails visibly at
  the checkpoint rather than silently.

  that; if the checkpoint shows overlap, adjust the `+46` constant, not the layout structure.
- **Layout is deliberately unfinished.** The user reserved add-panel design for discussion. Expect a
  follow-up pass; do not pre-empt it by redesigning here.
