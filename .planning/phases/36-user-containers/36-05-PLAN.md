# Phase 36 — Plan 05: Per-Container Items Per Row

**Created:** 2026-09-21
**Requirements:** CONT-06

## Approach

**Why this plan exists.** `CONT-06` enumerates the per-container settings as *scale, padding,
orientation, **items per row**, bar width*, and the phase's success criterion 3 requires that changing
items-per-row on one container leaves every other container visually unchanged. No such setting exists
anywhere in the addon today: Phase 35 made the existing setting set per-container, and
`RenderIconContainer` lays out a single unbounded row or column with no wrap. That criterion is
therefore unverifiable until the setting exists, so it is built here rather than quietly dropped.

**Scope: icon-kind containers only**, alongside Orientation and Icon Direction, which are already
icon-only. Blizzard's own bar viewers are a single column by design and `RenderBarContainer` lays out
one column with no wrapping; adding a second bar column would be a new layout mode nobody asked for.
The bar-kind branch is untouched.

**Default is `12` — a deliberately conservative addon-level default, NOT the CDM's value.** Blizzard's
factory `IconLimit` presets differ per viewer: in `EditModePresetLayouts.lua`'s `EDIT_MODE_MODERN_SYSTEM_MAP`,
Essential is **12**, Utility is **7** and BuffIcon is **1**. The stride-12 reading in
`.planning/research/TEST-PLAN-CDM-INJECTION-AND-COOLDOWNS.md` was measured on a live account whose Utility
viewer had been changed from its default, so it must not be generalised. Twelve is chosen because it is
the *highest* of the three factory defaults, which makes it the value least likely to wrap anything
unexpectedly. Do not describe it as "matching the CDM" anywhere in code or comment.

A user who wants their viewer's real value pulls it with **Copy Blizzard CDM Config** (Task 3b reads
`S.IconLimit`), which is the honest way to mirror Blizzard rather than guessing a single number.

**The layout stays allocation-free.** `RenderIconContainer` runs inside `ns:UpdateDisplay`, every 0.05s,
once per container, on a registry that Phase 36 lets grow without bound. Wrapping is pure scalar
arithmetic on the existing loop index — two integer divisions per icon, no table, no closure.

**Terminology, so the maths reads unambiguously.** "Major axis" is the direction items flow along
(X when Orientation is Horizontal, Y when Vertical); "minor axis" is the direction the grid wraps into.
`itemsPerRow` is the count along the major axis. For a slot index `i` (1-based):
`major = (i - 1) % perRow` and `minor = math.floor((i - 1) / perRow)`.

## Tasks

1. **`Core.lua` — the `itemsPerRow` default and backfill.**

   defaults constructor and the per-field backfill branch beside it).

   In the defaults constructor, add `itemsPerRow = 12` under the **non-bar** side — mirroring how
   `barWidth` and `displayMode` are added only under `if def.kind == "bar" then`. In the backfill
   branch, add `if def.kind ~= "bar" and cs.itemsPerRow == nil then cs.itemsPerRow = 12 end`, in the
   same shape as the existing `hideWhenInactive` / `showTimer` / `opacity` backfills. Idempotent, not
   version-gated, no `schemaVersion` bump, `BuffEngine.lua` untouched — the same rule the rest of this
   registry pass follows.

   Add a one-line comment stating that 12 is a conservative addon default — the highest of Blizzard's
   three factory `IconLimit` presets (Essential 12, Utility 7, BuffIcon 1) — chosen so the wrap is opt-in.
   Do NOT write that it "matches the CDM"; that is only true of Essential.

   *Acceptance:*
   - `grep -c 'itemsPerRow' Core.lua` returns `3` (the default, and the two halves of the backfill
     condition on one line count as one hit — confirm by reading that both the constructor and the
     backfill are present).
   - `sed -n '/^function ns.EnsureContainerSettings/,/^end$/p' Core.lua | grep -c 'itemsPerRow'` equals

2. **`Display.lua` — cache the setting and wrap the icon grid.**
   *Read first:* `Display.lua` `RefreshContainerSettings` (the icon-kind `else` branch setting
   `orientationSetting` and `iconDirection`), and `RenderIconContainer` in full (the `step`/`orientation`
   /`direction` block, the four `SetPoint` branches, and the container-sizing block at the end).

   a. In `RefreshContainerSettings`'s icon branch, add
      `dst.itemsPerRow = math.max(1, src.itemsPerRow or 12)`. The `math.max(1, ...)` floor is load-bearing:
      a zero or negative value would make the modulo arithmetic below divide by zero.

   b. In `RenderIconContainer`, after `local direction = settings.iconDirection`, add
      `local perRow = settings.itemsPerRow`. Inside the slot loop, replace the single
      `local offset = (slotIndex - 1) * step` with the two-axis form:
      `local major = ((slotIndex - 1) % perRow) * step` and
      `local minor = math.floor((slotIndex - 1) / perRow) * step`.
      Rewrite the four anchor branches so the major offset runs along the flow axis and the minor offset
      runs perpendicular to it, keeping each branch's existing anchor point:
      - Horizontal / Right — `TOPLEFT` to container `TOPLEFT`, `(major, -minor)`
      - Horizontal / Left — `TOPRIGHT` to container `TOPRIGHT`, `(-major, -minor)`
      - Vertical / Down — `TOPLEFT` to container `TOPLEFT`, `(minor, -major)`
      - Vertical / Up — `BOTTOMLEFT` to container `BOTTOMLEFT`, `(minor, major)`
      Every wrap direction is *downward* for horizontal flow and *rightward* for vertical flow, matching
      `GridLayoutFrame`'s `layoutFramesGoingRight = true` / `layoutFramesGoingUp = false` defaults that
      `BuildTBTSection` already uses for the CDM tab's own grids.

   c. Rewrite the container-sizing block at the end of `RenderIconContainer`. With
      `local n = #slots`, `local majorCount = math.min(n, perRow)` and
      `local minorCount = math.ceil(n / perRow)`, compute
      `majorSize = majorCount * BUFF_ICON_SIZE + (majorCount - 1) * iconPadding` and the same for
      `minorSize` from `minorCount`. Then, for orientation `0`, `container:SetSize(math.max(1, majorSize), math.max(1, minorSize))`;
      for orientation `1`, `container:SetSize(math.max(1, minorSize), math.max(1, majorSize))`.
      Leave the `visibleCount == 0` branch exactly as it is — an empty icon container keeps one
      icon of size so it stays clickable in Edit Mode.

   *Acceptance:*
   - `grep -c 'dst.itemsPerRow' Display.lua` returns `1`, and it is inside `RefreshContainerSettings`'s
     icon branch (the same branch that sets `dst.orientationSetting`).
   - `sed -n '/^local function RenderIconContainer/,/^end$/p' Display.lua | grep -c 'perRow'` is at
     least `5`.
   - `sed -n '/^local function RenderIconContainer/,/^end$/p' Display.lua | grep -c '(slotIndex - 1) \* step'`
     returns `0` — the single-axis offset is gone.
   - `sed -n '/^local function RenderBarContainer/,$p' Display.lua | grep -c '{}'` returns `0` — still
     no empty-table constructor at or below the render functions.
   - `sed -n '/^local function RenderIconContainer/,/^end$/p' Display.lua | grep -c 'function('`
     returns `0` — no closure is allocated per tick.
   - `grep -n 'math.ceil(n / perRow)' Display.lua` matches.

## Risks

- **`perRow` of zero.** Guarded twice: `math.max(1, ...)` when the snapshot is built, and a slider whose
  minimum is `1`. A modulo by zero in a 20-times-a-second render loop is the failure this prevents.
- **An upgraded database relayouts on login.** Unlikely rather than impossible: the backfill writes `12`,
  and `math.min(n, perRow)` collapses to `n` for any container holding fewer than twelve trackers, which
  reduces the sizing maths to exactly the pre-change formula. A container holding twelve or more WOULD
  wrap where it previously ran on in one line. Nobody can rule that out statically — it depends on a
  user's SavedVariables — so state it as a bounded risk, not an impossibility. Twelve being the highest
  of Blizzard's three factory presets is what keeps the exposure small.
- **Vertical wrap direction.** Vertical flow wraps *rightward* (minor offset on `+x` from a LEFT-anchored
  point) in both Up and Down directions. That matches `GridLayoutFrame`'s
  `layoutFramesGoingRight = true` default, which the CDM tab's own section grids already use, so the
  behaviour is consistent with what the user sees one panel away.
- **Bar containers gain nothing here.** Deliberate and stated in Approach, so it is not re-opened as an
  oversight: CDM bar viewers are single-column by design, and `CONT-06`'s bar-specific setting
  (`barWidth`) is already per-container from Phase 35.
