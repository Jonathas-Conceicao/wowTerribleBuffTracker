# Phase 36 — Plan 03: Post-Load Container Frames and Teardown

**Created:** 2026-09-21
**Requirements:** CONT-04, CONT-05, CONT-06

## Approach

`ns:InitEditModeFrames` creates every container frame exactly once, at `PLAYER_ENTERING_WORLD`, inside
one loop over `ns.CONTAINERS`. Phase 36 lets a container come into existence **after** that loop has
run — including while Edit Mode is open, with overlays showing and a drag possibly in flight. This is
the part of the phase most likely to produce an in-game Lua error, so it is planned as its own extract
step followed by its own lifecycle step.

**Extract before adding.** Four loops in this file already do per-container work with identical bodies:
position application (`ApplyEditModePositions`), handle showing (`ns:ShowEditModeHandles`), drag wiring
(`ns:OnEditModeEnter` and the sidebar checkbox's `OnClick`), and frame construction
(`ns:InitEditModeFrames`). Task 1 extracts each body into a per-def function and rewrites the loops to
call it. This is `CLAUDE.md`'s "unify repeated behaviour **the milestone itself introduces**" applied
before the duplication is introduced a fifth time — `ns.CreateContainerFrames` needs all four bodies,
and copying them would be the fifth copy.

**Placement matters, because these are file-local functions with a fixed definition order:**

| new function | defined immediately before | why there |
|---|---|---|
| `ApplyContainerPosition(def)` | `ApplyEditModePositions` (top of file) | used by that function and by `ns.CreateContainerFrames` at the bottom |
| `ShowContainerHandle(def)` | `ns:ShowEditModeHandles` | same |
| `WireContainerDrag(def)` | `ns:OnEditModeEnter` | must sit **after** `WireSelectableDrag` (currently line ~545), which it calls |
| `ns.CreateContainerFrames(def)` / `ns.DestroyContainerFrames(key)` | `ns:InitEditModeFrames` (bottom of file) | needs all three helpers above plus the two overlay constructors |

**The no-op contract.** `ns.CreateContainerFrames` and `ns.DestroyContainerFrames` are called from
Plan 01's hook dispatch, which runs during `ADDON_LOADED` for rehydrated containers — before
`ns:InitEditModeFrames` has created `ns.containers`. Both therefore return immediately when
`ns.containers` is nil. That is not a defensive afterthought: it is how rehydrated user containers get
their frames, because `ns:InitEditModeFrames` loops the *whole* registry at
`PLAYER_ENTERING_WORLD` and by then the user entries are already appended.

**Teardown is hide-and-orphan, not destroy.** WoW frames cannot be destroyed. A deleted container's
frame is deselected, unwired, hidden, cleared of points, unparented, and dropped from the three `ns`
tables. Its global name (`TBTContainer_userN`) stays bound to the orphan forever — harmless, and it can
never collide, because Plan 01's `nextContainerId` never decrements so no `frameName` is ever reused.
The `OnSizeChanged` hooks the two overlay constructors install cannot be removed either; an orphaned,
hidden frame never resizes, so they never fire again.

**Per-container settings for a user container (CONT-06).** `ns:ShowSettingsPopup` is already fully
registry-driven: it reads `ns.CONTAINER_BY_KEY[containerKey].title` and branches on `.kind`, and every
control writes `ns.db.containerSettings[activeContainerKey][settingKey]` then calls
`ns.RefreshContainerSettings()` and `ns:UpdateDisplay()`. It needs exactly one change: the "Copy
Blizzard CDM Config" button resolves `_G[def.cdmViewerGlobal]`, and a user container has no
`cdmViewerGlobal`, so the button must be hidden for those containers rather than offering an action
that can only print a failure.

## Risks

- **Clearing the wrong selection on teardown.** `ns:DeselectContainer` nils the file-local
  `selectedContainer` unconditionally, so calling it blindly for a deleted key would clear a *different*
  container's selection state and strand its overlay. Task 2b pins the guarded form
  (`if selectedContainer == key then ns:ClearSelection() end`), which is readable because
  `ns.DestroyContainerFrames` is defined in the same file below the `local selectedContainer`
  declaration.
- **A drag in flight on the deleted container.** `container:StopMovingOrSizing()` is called before the
  frame is hidden, and the overlay's `OnMouseUp` is cleared afterwards, so no handler can fire against
  an orphan.
- **`ns:SaveEditModePositions` on Edit Mode exit after a delete.** It loops `ns.CONTAINERS`, and Plan 01
  unregisters the def before teardown, so the deleted key is simply absent. Its stale
  `ns.db.editModePositions[key]` is removed by Plan 01's delete path.
