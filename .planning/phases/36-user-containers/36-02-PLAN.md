# Phase 36 — Plan 02: Per-Container Runtime Table Lifecycle

**Created:** 2026-09-21
**Requirements:** CONT-04, CONT-06

## Approach

`Display.lua` already holds four tables keyed by container key — `pools`, `timersByContainer`,
`cachedSettings` and `ns.containerTooltipsShown`. Phase 35 built the first two in a **file-scope loop
over `ns.CONTAINERS`**, which runs at Lua load time, before `ADDON_LOADED` and therefore before Plan 01
rehydrates user containers. That loop is the whole problem this plan solves.

**The fix is a single allocation site, not a second one.** The file-scope loop is rewritten to call a
new `ns.AllocateContainerRuntime(def)`, and Plan 01's `ns:AttachContainerRuntime` calls the same
function for every user container at rehydration and at runtime creation. There is then exactly one
line in the file that constructs a pool table and exactly one that constructs a timer list, and neither
is reachable from the render path.

`ns:UpdateDisplay` runs every 0.05s and loops the registry, and Phase 36 lets that registry grow without
bound. The allocation rule from Phase 35 therefore tightens rather than relaxes: **no table constructor
may appear in `ns:UpdateDisplay`, `RenderBarContainer` or `RenderIconContainer`.** This plan adds none,
and the acceptance criteria assert that by inspection of the file below `RenderBarContainer`.

**Settings isolation (CONT-06) is already correctly shaped and must stay that way.**
`RefreshContainerSettings` creates `cachedSettings[def.key]` lazily with its own `dst = {}` per key and
reuses it forever after — the render path never allocates and no two containers ever point at one
table. `ns.AllocateContainerRuntime` calls `RefreshContainerSettings()` so a newly created container has
its snapshot before the next tick; `RefreshContainerSettings` already nil-guards `ns.db`, so calling it
from the file-scope loop (where `ns.db` does not exist yet) is a no-op, not an error.

**Release is explicit, because nothing else would ever drop these keys.**
`RefreshContainerSettings` only ever *adds* keys, so `cachedSettings` would otherwise retain a deleted
container's snapshot forever. WoW frames cannot be destroyed, so pooled frames are hidden and unparented
rather than freed; they are then unreachable and the pool table itself is dropped.

**Two nil-safety points, both free:**
- `ns:InitDisplay` resolves `_G[def.cdmViewerGlobal]`. A user container has no `cdmViewerGlobal`, so the
  lookup must be guarded on the field existing rather than relying on a nil table index.
- `ns:UpdateDisplay`'s "no frame or no settings" fallback branch indexes `pools[def.key]` and walks it.
  Plan 01 orders deletion so that a def is unregistered before its pool is released, which makes a nil
  pool unreachable — the guard is defence in depth against a future reordering, and costs one `if`.

## Tasks

1. **`Display.lua` — `ns.AllocateContainerRuntime` and `ns.ReleaseContainerRuntime`.**
   *Read first:* `Display.lua` lines 1–95 (the per-container table block, the file-scope registry loop,
   `RefreshContainerSettings`) and lines 715–749 (`ns:UpdateDisplay`); `Core.lua`'s
   `ns:AttachContainerRuntime` / `ns:DetachContainerRuntime` from Plan 01 to confirm the call
   signatures (`(def)` and `(key)` respectively).

   a. Define `function ns.AllocateContainerRuntime(def)` immediately **after** `RefreshContainerSettings`
      and its `ns.RefreshContainerSettings = RefreshContainerSettings` export (it calls that function),
      and **before** the pool getters. Body:
      `pools[def.key] = pools[def.key] or {}`,
      `timersByContainer[def.key] = timersByContainer[def.key] or {}`,
      then `RefreshContainerSettings()`.
      Idempotent by construction, so calling it twice for the same key is harmless.

   b. Replace the file-scope
      `for _, def in ipairs(ns.CONTAINERS) do pools[def.key] = {} ... end` loop with a loop whose body
      is a single `ns.AllocateContainerRuntime(def)` call, and move that loop **below** the new
      function definition. Update the comment above the per-container table block to say that
      `ns.AllocateContainerRuntime` is now the only allocation site and that the registry grows at
      runtime in this phase.

   c. Define `function ns.ReleaseContainerRuntime(key)` directly after (a). Body:
      - `local pool = pools[key]`; if it exists, `for i = 1, #pool do pool[i]:Hide(); pool[i]:SetParent(nil) end`;
      - `pools[key] = nil`, `timersByContainer[key] = nil`, `cachedSettings[key] = nil`,
        `ns.containerTooltipsShown[key] = nil`.
      Add a comment noting that WoW frames cannot be destroyed, so the pooled frames are hidden and
      unparented and then become unreachable with the pool table.

   *Acceptance:*
   - `grep -c 'pools\[[^]]*\] = {}' Display.lua` returns `0`; `grep -c 'pools\[def.key\] or {}' Display.lua`
     returns `1`.
   - `grep -c 'timersByContainer\[def.key\] or {}' Display.lua` returns `1`.
   - `grep -n 'function ns.AllocateContainerRuntime' Display.lua` and
     `grep -n 'function ns.ReleaseContainerRuntime' Display.lua` both match.
   - `grep -n 'ns.AllocateContainerRuntime(def)' Display.lua` matches inside the file-scope loop, and
     its line number is **greater** than the line number of `function ns.AllocateContainerRuntime`.
   - `grep -n 'cachedSettings\[key\] = nil' Display.lua` and
     `grep -n 'ns.containerTooltipsShown\[key\] = nil' Display.lua` both match inside
     `ns.ReleaseContainerRuntime`.
   - `sed -n '/^local function RenderBarContainer/,$p' Display.lua | grep -c '{}'` returns `0` — no
     empty-table constructor exists anywhere at or below the render functions. (This gate passes on the
     current file; it must still pass after the edit.)

2. **`Display.lua` — nil-safety for a registry that no longer implies a CDM viewer or a live pool.**
   *Read first:* `Display.lua` `ns:InitDisplay` (lines 383–422) and `ns:UpdateDisplay` (lines 715–749).

   a. In `ns:InitDisplay`'s viewer-resolution loop, guard the global lookup on the field existing:
      resolve `viewer` only `if def.cdmViewerGlobal then`. Add a one-line comment saying a user
      container mirrors no Blizzard viewer, so a nil `cdmViewerGlobal` is normal and not a failure.
      Do **not** change the `if not next(ns.cdmViewers) then ... return end` bail — four base containers
      always supply viewers on a client that has the CDM, which is the addon's stated hard requirement.

   b. In `ns:UpdateDisplay`'s "no container or no settings" fallback branch, bind
      `local pool = pools[def.key]` and wrap the hide loop in `if pool then`. No table constructor, no
      new allocation — one branch.

   *Acceptance:*

   - `grep -c 'timersByContainer\[timer.section\] or timersByContainer.bars' Display.lua` still returns

## Risks

- **`ns.AllocateContainerRuntime` called before `ns.db` exists.** It calls `RefreshContainerSettings`,
  which already returns early when `ns.db` or `ns.db.containerSettings` is nil. That is exactly the
  file-scope-load case, and it is a no-op, not an error — `ns:InitDisplay` calls
  `RefreshContainerSettings()` again once the database is up.
- **A deleted container's pooled frames were parented to a frame Plan 03 also unparents.** Both are
  safe: `SetParent(nil)` on an already-orphaned frame is legal, and the ordering in
  `ns:DetachContainerRuntime` runs frame teardown before runtime release either way.
- **`ns.containerTooltipsShown` is written from the render path.** It is only ever assigned an existing
  key's boolean (`ns.containerTooltipsShown[def.key] = settings.tooltipsShown`), never a table, so it
  adds no allocation and releasing the key is sufficient.
