# Phase 35 — Plan 04: Per-Container Rendering

**Created:** 2026-09-21
**Requirements:** CONT-01, CONT-02

## Approach

`UpdateDisplay` is today one function containing two hardcoded render blocks reading two hardcoded
settings caches and two hardcoded pools. Four containers turn each of those pairs into a key-indexed
table and each block into a function called once per container.

**The shape after this plan:**

| today | after |
|---|---|
| `cachedBarSettings`, `cachedIconSettings` | `cachedSettings[key]` |
| `barPool`, `iconPool` | `pools[key]` |
| `barTimers`, `iconTimers` | `timersByContainer[key]` |
| `ns.barTooltipsShown`, `ns.iconTooltipsShown` | `ns.containerTooltipsShown[key]` |
| inline bar block, inline icon block | `RenderBarContainer(def, ...)`, `RenderIconContainer(def, ...)` |

**Hot-path discipline is non-negotiable here.** `UpdateDisplay` runs every 0.05s. Every one of those
tables is created once at load — keyed by container, never rebuilt — and its contents are `wipe()`d per
cycle, matching the file's existing convention. Nothing in `UpdateDisplay` or in either render function
may construct a table. The scratch tables (`slots`, `activeByKey`) stay single module-level tables shared
across containers: renders run sequentially and never interleave, so one `wipe()` at the top of each
render is correct and costs no allocation.

**Grouping rule:** a timer goes to `timersByContainer[timer.section]` when `timer.section` names a
registered container, and to `timersByContainer.bars` otherwise. The fallback reproduces today's
`if section == "buffs" then icons else bars` behaviour exactly for any stale or missing section value.

**`EXAMPLE_BAR_SLOT` applies to bar-kind containers only.** Do not add an icon equivalent —
`35-CONTEXT.md` defers it. Empty icon containers keep their `SetSize(40, 40)` empty case, which is what
makes them clickable in Edit Mode.

**This plan also closes out Plan 02's temporary bridge.** `ns.barContainer` and `ns.iconContainer` are
deleted here, in both files.

## Risks

- **`UpdateDisplay` is the addon's hottest path.** The extraction adds one loop over four entries and two
  function calls per tick, replacing two inline blocks. The fixed cost is the loop; the per-container cost
  is what it already was. Any table constructor introduced inside `UpdateDisplay` or either render
  function turns that into four allocations every 0.05s — Task 2's last acceptance criterion exists to
  catch exactly that.
- **The icon block's early `return`s were returns from `UpdateDisplay`.** Converting them to returns from
  `RenderIconContainer` is the point of the extraction, but a missed one would silently stop the remaining
  containers from rendering. Read every `return` in the extracted body.
- **An upgraded user's `essential`/`utility` settings come from Plan 01's `Core.lua` seeding, not from a
  migration.** If `cachedSettings[key]` is nil the container is skipped rather than erroring, so a
  seeding failure shows up as a container that never renders rather than as a Lua error. Step 5 of the
  in-game pass is what detects it.
