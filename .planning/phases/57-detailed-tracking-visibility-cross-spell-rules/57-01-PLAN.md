Design choices recorded here (Claude's discretion per 57-CONTEXT):
- Saved key (written by Plan 04): `entry.endOnCast` = a plain array of positive numeric spell IDs, or nil. One key for both kinds; the dialog label differs ("Ends when you cast:" on buffs, "Resets when you cast:" on cooldowns).
- **Skip rule (per 57-CONTEXT "Never end the key this same cast is about to start"):** the loop skips any key equal to the key this cast resolves to on the cooldown side (`cdKey`) or on the buff side (`ns.buffKeyBySpell[spellID]`, else `ns.rankIndex[spellID]`). "Skip" was chosen over "end then start" because it never touches a key the cast is restarting anyway, so it costs nothing and cannot leave a half-reset cooldown. A key resolved by the buff lookup but then rejected by the buff side (hidden section) is skipped too; that tracker is hidden, so the difference is not visible.
- **Redraw rule:** `ns:ApplyEndOnCast` calls `ns:UpdateDisplay()` itself whenever it removed a buff timer (a buff end must show at once even when the cast returns no proc), and calls `ns:MarkCooldownsDirty()` once when it reset a cooldown. A cast that both ends one tracker and starts another therefore redraws twice; that case is rare, and correctness beats one redundant redraw.
- The lifecycle loop lives in BuffEngine.lua (`ns:ApplyEndOnCast`), like `ns:EndTimer`; OnTrigger does the one lookup and calls it only on a hit.
- **Trigger expansion cost (checker decision):** retail expands each trigger ID to the array `{ triggerID, base, override }` (the two guarded RelatedSpellID lookups, nil results skipped) and never calls ns:ResolveRankFamily, so a retail rebuild does no spellbook scan. Forever calls ns:ResolveRankFamily once per trigger ID and caches the result in `ns.endRuleFamilies[triggerID]` (`false` for a nil result, so a miss is cached too). The cache is wiped only when the spellbook actually changes: in the SPELLS_CHANGED branch when NOT `InCombatLockdown()` (in combat the old families stay valid, since a Forever rank cannot be learned mid-fight, and the next out-of-combat SPELLS_CHANGED refreshes them), and at PLAYER_ENTERING_WORLD (the first moment the spellbook is populated, so ADDON_LOADED's incomplete families never outlive the first world entry). Each wipe sits before that branch's `ns:RebuildRankIndex()`, so the rebuild it triggers recomputes.

Hazards: Lua file-local upvalue order (hit 5 times) -- every new helper is an `ns` method, never a file-local.
