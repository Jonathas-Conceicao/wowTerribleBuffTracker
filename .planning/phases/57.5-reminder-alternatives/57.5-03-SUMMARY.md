## Performance and cleanup review

The review covers the phase diff against base 1314742.

**Hot paths**
- **UserSpellProviderMixin:OnTrigger.**
  - A miss costs one `ns.alternativeKeysBySpell[spellID]` lookup.
  - A hit costs a numeric loop over the prebuilt array, then one `ns:UpdateDisplay()` when any reminder started.
  - No constructor (gated).
- **ns:StartReminderFromCast.**
  - `skipRedraw` suppresses the per-reminder redraw.
  - `ns:QueueCastAuraRecheck()` is still called per start, but it coalesces: one pending flag, one C_Timer per burst.
  - No constructor.
- **ns:FillUserBuffProc.** One extra table lookup (`ns.satisfiedByWatch[ownerKey]`). No constructor.
- **ns:RefreshAuraStates.**
  - Two `wipe()` calls per call.
  - Every watched ID is read at most once per call through `ReadWatchedAura`.
  - No constructor, and it names no aura reader directly (gated).
- **Read count, five blessing reminders on a Forever paladin at level 60.** Rank-family sizes, estimated from the Classic spellbook with only known ranks counted:

  | Blessing | Ranks |
  |----------|-------|
  | Kings | 1 |
  | Might | 7 |
  | Wisdom | 6 |
  | Salvation | 1 |
  | Light | 3 |

  - Each reminder's combined list is the union of all five families, about 18 IDs.
  - Without the memo that would be 5 x 18 = 90 reads per UNIT_AURA.
  - With the memo it is at most 18 distinct reads per call, plus 1 for Righteous Fury if placed. This is the same bound as before the phase, when each reminder read only its own family.
- **Unchanged.** `ns:ScanActiveTimersForCancellation`, `ns:VisibilityGate`, `ns:GetActiveTimers` and the Display render loops. The last three build no table (gated).

**Rebuild cost**
- `ns:CastRuleFamily` is called only from `ns:RebuildDetailedRuleIndex` and `ns:RebuildVisibilityWatch` (gated: never from Providers.lua, BuffEngine.lua or Display.lua).
  - Forever: served from the `ns.endRuleFamilies` cache, so there is one spellbook scan per ID per spellbook change.
  - Retail: allocates a 1-3 element array per alternative per rebuild.
- `ns:RebuildVisibilityWatch` allocates one combined list per reminder with alternatives, plus the new outer `satisfied` table.
- `ns:ApplyMetaReminderDef` writes `alternatives` only on a reference difference. After a /reload that is once per blessing entry, because the saved copy is replaced by the table's array. After that it writes nothing.

**Dirty checks**
- A blessing cast starts up to five reminders with one redraw from the alternatives side. The directly resolved user and built-in reminders keep their own redraw, as before.

**Dead code and stale comments**
- The ApplyEndOnCast reminder branch and the `startingReminderKey` parameter are gone (gated).
- "Ends when you cast" no longer describes reminders anywhere. It remains only as the buff label and in the v11 and RALT-01 comments that describe the change.
- The "reminder is buff-like, so its cast rule is indexed" comment is gone.
- No code reads a reminder's endOnCast. The only readers left are the v9 and v11 migrations, `ns:ApplyMetaReminderDef` (clears it) and the buff/cooldown index condition, which excludes reminders.
- No unused locals were left by the moves. `RelatedSpellID` is still read, by `ns:CastRuleFamily`. The dialog's old inline bodies were replaced by the shared locals.
- The `ns.auraState` writer list no longer names ApplyEndOnCast.
- **Found and fixed (ab88a8d):**
  - `ns:VisibilityGate`'s comment still listed "a cast rule" as a way a reminder's aura is marked gone.
  - The `ns:RebuildDetailedRuleIndex` walk comment did not name the alternatives.
  - Two CDMTab.lua comment lines left over-long by 57.5-01 were rewrapped.

**Duplication the phase introduced**
- There is one family expansion (`ns:CastRuleFamily`), one list row (the CDMTab.lua shared locals) and one reminder start (`ns:StartReminderFromCast`). `IndexFamily` serves both indexes.
- Code that predates the milestone was not refactored.

**Upvalue order**
- Each new file-local is declared above its first reader:

  | File-local | Declared above |
  |------------|----------------|
  | IndexFamily | ns:RebuildDetailedRuleIndex |
  | ListContains | ns:RebuildVisibilityWatch |
  | refreshAuraMemo, refreshReadableMemo, ReadWatchedAura | ns:RefreshAuraStates |
  | MetaReminderGroup | its call, after the rows |
  | BuildSpellListField, SetSpellListText, UpdateSpellListIcons, ReadSpellList, ValidateSpellList | TRACKER_FIELDS |

- `RelatedSpellID` (Core.lua ~867) sits above `ns:CastRuleFamily`.
- Everything read across files is on `ns`: `ns.alternativeKeysBySpell`, `ns.satisfiedByWatch`, `ns:CastRuleFamily`, `ns:StartReminderFromCast`.

**Semantics spot-check (CONTEXT RALT-01): a Kings reminder with Might's aura present and the Kings timer not running**
1. **Watch list.** `ns.visibilityWatch["metaReminder:20217"]` is Kings' rank family followed by the Might, Wisdom, Salvation and Light families.
2. **State.** On the next `ns:RefreshAuraStates`, the Might ID reads readable and present, so `present = true` and the state becomes true. The reminder hides, because `ns:VisibilityGate` needs the state to be false.
3. **Timer.** Might is the only present aura, so `seenAura` is Might's aura. Its readable expiry makes `ns:FillUserBuffProc` start a Kings timer, with `aliveBuffs = ns.satisfiedByWatch[key]` (the combined list), and its expiry is set to Might's. The timer follows Might.
4. **A Might cast on another player.**
   - OnTrigger starts Might's own reminder directly, then the alternatives side starts Kings, Wisdom, Salvation and Light (each with `castAt`, state true, one redraw). The re-check is queued.
   - About 0.6 s later, `RunCastAuraRecheck` calls `ns:RefreshAuraStates`.
   - If a blessing of yours is still readably on you (the Might from step 1), `present` is true and the reminders stay hidden. The timer syncs only when the expiry drifts by more than 0.5 s.
   - If none of the set is on you, every ID reads absent, the grace has passed, the timer ends and the state becomes false, so the reminders show.
   - While the auras are unreadable, nothing changes (DTRK-06).
