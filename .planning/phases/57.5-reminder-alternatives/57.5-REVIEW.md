## Summary

The core RALT-01..03 behaviour is correct, and I found no blocker:
- The reminder watches the combined set.
- A cast of an alternative starts every listing reminder, with one redraw.
- The post-cast re-check ends a timer that an alternative cast on someone else started.
- Unreadable reads hold.
- The blessing group, Righteous Fury and the Sanctuary orphan behave as specified.
- Buff "Ends when you cast" is untouched.
- v11 is gated and idempotent.
- The dialog stores nil when a field is empty.

`node scripts/migrate-dryrun.js --selftest` gives 12/12 PASS. The aura-read gate passes. stylua is clean, and all four Lua files are CRLF with no CRCR.

Four robustness defects remain. Each can show a reminder that is satisfied, or hide one that is not:
- **WR-01.** A present alternative with no readable expiry is ignored by the expiry sync.
- **WR-02.** A running timer keeps a stale `aliveBuffs` after its alternatives are edited.
- **WR-03.** An opted-out user reminder stays hidden for its full duration after an alternative is cast on someone else. This contradicts CONTEXT.
- **WR-04.** On retail, an alternative's override family can invalidate the state in combat.

Verified with no finding:
- Upvalue order. IndexFamily, ListContains, ReadWatchedAura and the memo tables, MetaReminderGroup, and the five CDMTab list locals are each declared above their first reader, and RelatedSpellID is at Core.lua:867.
- The memo is wiped per call and allocates nothing on the hot path.
- `ns.alternativeKeysBySpell` and `ns.satisfiedByWatch` are initialised tables, so they are never indexed as nil.
- The skip of `reminderKey`/`metaReminderKey` in the alternatives loop.
- The ApplyEndOnCast reminder branch removal. No reminder can reach `ns.endKeysBySpell`.
- Lua v11 gating: `ver < 10` defers, and `>= 11` is a no-op.
- The v10 literal pin.
- A built-in never opens the dialog, so user input cannot reach a metaReminder's alternatives.
- A hidden (own `visible()`) field is neither read nor validated, so a reminder never writes `endOnCast` and a buff never writes `alternatives` (CDMTab.lua:2737-2743).

## Warnings

### WR-01: A present alternative with no readable expiry loses the sync to a shorter one, so the reminder shows while satisfied

**File:** `BuffEngine.lua:1792-1808` (selection), `BuffEngine.lua:954-958` (lazy expiry), `BuffEngine.lua:1844-1873` (sync)

**Issue:** In the selection loop, a present aura whose expiry is unreadable (a permanent aura with duration 0, or a secret expiry) is always replaced by any later present aura that has a readable expiry. The timer then follows the shorter, readable one. Example: reminder X lists Y as an alternative, and Y is a permanent aura.
1. With X and Y both present, the timer syncs to X's expiry.
2. When X runs out, `UNIT_AURA` fires. `RefreshAuraStates` sees Y present, but Y has no readable expiry, so no sync happens and the proc keeps X's expiry.
3. `ns:GetActiveTimers` then lazily expires the proc and writes `ns.auraState[key] = false`. The reminder shows while Y still satisfies it.
4. Nothing re-reads until the next unrelated aura event, which can be minutes away out of combat.

Before this phase, a watch list was one spell's rank family, so this mix could not occur. Alternatives make it a normal configuration: a user can list any buff, and "latest expiry" is only well-defined when every present aura's expiry is readable.

**Fix:** Treat "present with no readable expiry" as outlasting any readable expiry. In that case, do not sync and do not start a timer from the shorter aura:
```lua
local bestExpiry, openEnded = nil, false
for j = 1, #list do
    local aura, readable = ReadWatchedAura(list[j])
    if not readable then
        allReadable = false
    elseif aura then
        present = true
        local _, expirationTime = ns:ReadableAuraExpiry(aura, now)
        if expirationTime == nil then
            openEnded = true
        elseif bestExpiry == nil or expirationTime > bestExpiry then
            seenAura, bestExpiry = aura, expirationTime
        end
    end
end
if openEnded then
    seenAura = nil -- the sync below then leaves timing alone; the state is still true
end
```
Also end or mark indefinite a running proc when `openEnded`, so the lazy expiry cannot flip the state. Alternatively, have the reminder branch of the lazy expiry in `ns:GetActiveTimers` call `ns:QueueCastAuraRecheck()` (one flag, no allocation), so a readable re-read confirms the absence before the next redraw.

### WR-02: A running timer keeps its pre-edit `aliveBuffs`, so the cancellation scan shows the reminder while an alternative is present

**File:** `Providers.lua:122-125`, `BuffEngine.lua:1605-1630`, `Core.lua:1666/1692`

**Issue:** `proc.aliveBuffs` is captured when the timer starts. When the user edits a reminder and adds alternatives while its timer runs, the rebuild publishes a new `ns.satisfiedByWatch[key]`, but the live proc still holds the old own-family list. The failure sequence:
1. The own buff is lost while an alternative is present.
2. On the same `UNIT_AURA`, `RefreshAuraStates` reads the combined set as present and keeps the state true.
3. `ScanActiveTimersForCancellation` then runs, reads the stale own-only `aliveBuffs` as absent, deletes the timer and writes `ns.auraState[key] = false` (BuffEngine.lua:1628-1630).
4. The reminder shows although it is satisfied, until the next aura event.

The two readers disagree only because the proc was not updated. The same thing happens after any rebuild that changes a reminder's combined list mid-timer, for example a new rank learned out of combat.

**Fix:** At the end of `ns:RebuildVisibilityWatch`, repoint every live reminder proc at its current list. This is rebuild-time, so the cost is fine:
```lua
for key, proc in pairs(ns.activeTimers) do
    local entry = tracked[key]
    if entry and ns:IsReminderEntry(entry) and proc.aliveBuffs ~= nil then
        proc.aliveBuffs = satisfied[key] or proc.aliveBuffs
    end
end
```
An alternative fix: have the scan skip reminder keys entirely, since `RefreshAuraStates` already owns reminder aura loss, and the scan runs right after it on every `UNIT_AURA` and in the re-check.

### WR-03: Casting an alternative on someone else hides an opted-out user reminder for its whole typed duration

**File:** `BuffEngine.lua:1831` (`keepsTimer`), `Providers.lua:356-372`

**Issue:** CONTEXT (RALT-01) requires: "Casting an alternative on another player must not keep your own reminder hidden once a readable read says none of the set is on you." For a user reminder with "End when the aura is lost" unticked (`keepOnAuraLoss`), this does not hold:
1. The alternatives side starts the reminder's timer.
2. The post-cast re-check reads the whole set as absent, but `keepsTimer` is true because `ns:CancelsOnAuraLoss(entry)` is false, so both the timer and the true state hold.
3. The proc also carries no `aliveBuffs`, so the scan skips it.
4. The reminder stays hidden for the typed duration. For a 60-minute buff, that is an hour of a missing buff not being reminded.

The same gap existed for the reminder's own spell (57.4 CR-01 accepted it). Alternatives multiply it: every listed spell, cast on anyone, now hides every reminder that lists it.

**Fix:** The opt-out means "don't end on a loss I observed", not "trust a cast I never confirmed". In `RefreshAuraStates`, let the first post-grace readable absence of a cast-started timer end it, whatever the opt-out:
```lua
local unconfirmedCast = proc ~= nil and proc.castAt ~= nil and proc.syncedAt == nil
local keepsTimer = present == false and proc ~= nil and not unconfirmedCast
    and (suppressCancel or not ns:CancelsOnAuraLoss(entry))
```
Clear `proc.castAt` (or set a `confirmed` flag) at the first readable present read, so the opt-out applies from then on. If the user prefers to keep the 57.4 behaviour, record that as an accepted divergence from the CONTEXT sentence above.

### WR-04: On retail, alternatives make the reminder state depend on override answers read during an in-combat rebuild

**File:** `Core.lua:1498-1507` (retail `ns:CastRuleFamily`), `Core.lua:1655-1687` (content compare), `Core.lua:2151-2155` (SPELLS_CHANGED)

**Issue:** On retail, `ns:CastRuleFamily` builds `{ id, base, override }` fresh on every rebuild, with no cache. `SPELLS_CHANGED` calls `ns:RebuildRankIndex` in combat too. If `C_Spell.GetOverrideSpell` answers differently mid-fight, the combined list's content changes and `RebuildVisibilityWatch` writes `ns.auraState[key] = nil`, which hides the reminder. Two ways this happens:
- A talent or proc override changes.
- The answer turns secret, so `RelatedSpellID` returns nil and the family shrinks.

While auras are secret in combat, `RefreshAuraStates` returns early, so a reminder that was correctly showing a missing buff disappears for the rest of the fight. Before this phase, a retail reminder (never rank-covering) watched its single aura ID (`list == nil`), which cannot vary. The alternatives' families are the new source of variance.

**Fix:** Cache the retail family per ID the same way Forever does. Retail can use `ns.endRuleFamilies` too, which is already wiped only out of combat, so a mid-fight answer never enters the list:
```lua
function ns:CastRuleFamily(triggerID)
    if type(triggerID) ~= "number" or triggerID <= 0 then return nil end
    local family = ns.endRuleFamilies[triggerID]
    if family == nil then
        if ns.CLIENT_HAS_SPELL_RANKS then
            family = ns:ResolveRankFamily(triggerID) or false
        else
            family = { triggerID }
            -- base/override as today
        end
        ns.endRuleFamilies[triggerID] = family
    end
    return family or nil
end
```
Update the "Never read on retail" comment on `ns.endRuleFamilies` (Core.lua:1133) to match.

## Info

### IN-01: "Hold while unreadable" now spans the whole set, so one always-unreadable alternative can stop the reminder ever showing

**File:** `BuffEngine.lua:1793-1811`, `BuffEngine.lua:1610-1618`

**Issue:** Absence is proven only when every ID in the combined list reads readable (correct per DTRK-06). If any one alternative's aura is per-spell secret whenever the check runs, the reminder can never turn false. This bites in two cases:
- The state is nil after a rebuild invalidation.
- The reminder has no timer, such as a no-duration row.

In both cases the reminder stays hidden with no user-visible cause. This is by design, but alternatives now let a user-typed ID from an unrelated spell cause it.

**Fix:** Document the risk in the dialog tooltip or in RALT-01. Optionally, prove absence from the readable subset when the unreadable IDs are only alternatives. That would be a user decision, because it relaxes DTRK-06.

### IN-02: The Lua and JS v11 mirrors diverge on malformed (hand-edited) tables

**File:** `BuffEngine.lua:712-736`, `scripts/migrate-dryrun.js:515-531`

**Issue:** The mirrors disagree in three ways, all on data that SavedVariables never writes itself:
1. A hash-only `endOnCast` table is dropped by Lua (`#rule == 0`) but moved by JS (`size > 0`).
2. The Lua merge walks `1..#rule`, while JS walks every value.
3. JS `alternatives.set(alternatives.size + 1, id)` overwrites an existing key when the Map is sparse, where Lua's `#list + 1` appends at the border.

Separately, the move path adopts the rule table unfiltered, while the merge path filters out non-positive and non-numeric IDs. The runtime does tolerate junk (`ns:CastRuleFamily` rejects it).

**Fix:** Make JS test `rule.has(1)` rather than `size > 0`, and append at the first free integer key. Alternatively, record these as intentional non-goals in the reconciliation table in 57.5-01-SUMMARY.

### IN-03: The saved `alternatives` array of a built-in reminder is the Providers.lua def's own table

**File:** `Providers.lua:1637-1639`

**Issue:** `entry.alternatives = def.alternatives` aliases the load-time def array into SavedVariables. Nothing mutates it today:
- The v11 merge path (BuffEngine.lua:715-733) appends in place, but it runs only when a metaReminder still has `endOnCast`, which ApplyMetaReminderDef clears in the same rebuild.
- The dialog never opens for built-ins.

A future in-place writer would silently change the table for every reminder in the group.

**Fix:** Add a "never mutate in place" note next to `MetaReminderGroup`. Alternatively, make the v11 merge build a fresh list instead of appending.

### IN-04: Two comment lines added by the phase exceed the 120-column stylua width

**Issue:** stylua does not wrap comments. 57.5-03 reports "two CDMTab.lua comment lines ... rewrapped", but these two lines are still over-long.

**WR-01.** The fix combines two parts.
- In `ns:RefreshAuraStates`, a present watched aura with no readable expiry sets `openEnded`. The state stays true, but `seenAura` is cleared, so no timer is started or synced from a shorter aura.
- The reminder branch of the lazy expiry in `ns:GetActiveTimers` now calls `ns:QueueCastAuraRecheck()`. That is one flag and one coalesced C_Timer, with no allocation. If the set is still present, the re-read hides the reminder again. A cast-started timer can still end naturally while an open-ended alternative is up, so the reminder can flash for up to about 0.6 s before the re-check hides it. UAT 16 records this.

**WR-02.** At the end of `ns:RebuildVisibilityWatch`, every live reminder proc that carries `aliveBuffs` is repointed. The new target is `satisfied[key] or watch[key] or ns:AcquireAliveBuffs(key, visibilityAuraID[key])`, the same choice and order `ns:FillUserBuffProc` makes. This also covers alternatives being removed. It runs at rebuild time only.

**WR-03.** A cast-started timer counts as unconfirmed while it still has `proc.castAt`. The first readable present read in `ns:RefreshAuraStates` clears `castAt`. The opt-out (`keepOnAuraLoss`) now keeps only a confirmed timer, so the first readable absence past the grace ends an unconfirmed one. `suppressCancel` still ends nothing.
- A side effect: once a timer is confirmed, the scan's cast grace no longer applies to it. A real loss inside 0.5 s of the cast then ends it.
- **Reminder-only. Buff trackers do not share it.** This is not the same shared path. A buff tracker's aura loss goes through `ns:ScanActiveTimersForCancellation`, and an opted-out buff proc carries no `aliveBuffs`, so nothing ever reads its presence and it could never be confirmed. A buff's opt-out is also how a spell whose aura is not on the player gets tracked. Ending those timers on the first absence would break that.
- Remaining edge, unchanged from 57.4: suppose you recast an opted-out reminder's buff on someone else while your own copy still has a few seconds left. The re-check reads your copy as present and confirms the timer, so the typed timer then governs.

**WR-04.** `ns:CastRuleFamily` now caches the retail `{ id, base, override }` family in `ns.endRuleFamilies`, exactly like Forever. That cache is wiped only out of combat, at SPELLS_CHANGED and in the load refresh, and at world entry.
- The signature stays `ns:CastRuleFamily(triggerID)`, because the 57.5-02 plan gate pins it and requires both rebuild call sites to use it. So the cache is shared by the alternatives and the retail cast-rule index.
- Side effect on retail only: a buff or cooldown "Ends/Resets when you cast" rule now keeps its out-of-combat override until combat ends. Before, an in-combat SPELLS_CHANGED would pick up a new override. This matches Forever and also protects cast rules from a secret override answer mid-fight.

**IN-01.** Skipped. "Hold while unreadable" across the whole set is DTRK-06 by design. Revisit if a user hits it.

**IN-02.** Both mirrors now filter the same way on both paths, through one helper each (`AppendAlternativeID` in Lua, `appendAlternativeID` in JS).
- A rule is read as its ipairs sequence: positive numbers only, first occurrence only.
- **Move path:** the SAME table is compacted in place to exactly the valid IDs, and every other key is dropped.
- **Merge path:** IDs are appended after the existing list's ipairs border, never over a sparse key.
- A rule with no valid ID is dropped.
- **Selftest:** case K runs a new malformed sub-case, `caseKMalformed` with Fixture H, covering hash-only, junk and duplicates, a hole, a sparse merge target, and all-junk. It is a sub-case rather than a new `runCase` because the 57.5 plan gates pin `SELFTEST PASS (12 cases)`. Against HEAD's JS mirror, the sub-case fails on all five entries.

**IN-03.** `ns:ApplyMetaReminderDef` gives the entry its own copy (`CopyIDList`) only when the entry's list differs by content (`SameIDList`). A saved copy that already matches is kept, so a normal rebuild allocates nothing. The def array is never handed out.
