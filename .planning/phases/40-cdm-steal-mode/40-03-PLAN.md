# Phase 40 — Plan 03: Hide, Restore and the Toggle

**Created:** 2026-09-21
**Requirements:** STEAL-01, STEAL-02, STEAL-06, STEAL-07, STEAL-08

## Approach

This is the only plan in the phase that touches a Blizzard frame at all, and it touches exactly three
C widget methods on four named globals. Everything below is written so that the `STEAL-08` code-level
audit is a single-file read.

**The complete inventory of CDM interaction after this plan — one row per operation.**

| Step | Operation | Class |
|---|---|---|
| `_G[def.cdmViewerGlobal]` | global table lookup | **read**, no frame method |
| `viewer:IsShown()` | C widget method, no Blizzard Lua runs | **read** |
| `viewer:Hide()` | C widget method, sets shown state | **write** — the only write in the phase |
| `viewer:Show()` | C widget method, restore path only | **write** — the only other write |
| `C_CooldownViewer.Get*` (Plan 01) | namespace API | **call**, no frame |

Nothing else. No CDM mixin method is called — not `IsActive`, not `ShouldBeShown`, not `GetItemCount`,
not `GetSettingValue`. No field is written on a CDM frame. No frame is parented into one.
`C_CooldownViewer.SetLayoutData` is never called. The research record is unambiguous about why: *"they do
not merely fail, they leave the frame tainted afterwards"*
(`.planning/research/TEST-PLAN-CDM-INJECTION-AND-COOLDOWNS.md`, "Calling Blizzard's CDM mixin methods from
addon code is UNSAFE"), and the taint is sticky until `/reload`.

`EditModeFrames.lua`'s pre-existing "Copy Blizzard CDM Config" button calls `viewer:GetSettingValue(...)`.
That is v0.3.0 code, user-initiated and out of combat, and it is explicitly **not** extended here. This
plan adds no mixin call anywhere and does not modify `EditModeFrames.lua`.

**The hide, and when it is allowed to run.**

`CooldownViewerMixin:UpdateShownState` (`Blizzard_CooldownViewer/CooldownViewer.lua:1953-1965`) calls
`self:SetShown(self:ShouldBeShown())` and early-returns only when the two already agree. So a viewer we
hid will be re-shown by Blizzard whenever that function runs and `ShouldBeShown()` is true. Reading the
source, it runs on: `PLAYER_IN_COMBAT_CHANGED`, `PLAYER_LEVEL_CHANGED`, `VARIABLES_LOADED`, a
`cooldownViewerEnabled` CVar change, the `CooldownViewerSettings.OnShow` / `.OnHide` callbacks, and
`SetIsEditing` (Edit Mode enter and exit). The hide must therefore be **re-asserted**, and the addon-side
triggers that correspond to those are the named list below.

`ShouldBeShown()` (`:1888-1920`) returns **true unconditionally** while `IsEditing()` is true or while
`CooldownViewerSettings:IsVisible()` is true. Fighting that would mean writing to a CDM frame repeatedly
during the Edit-Mode code path that reached `RefreshTotemData` in every taint failure recorded — the
single worst place to write. So the hide is **suspended**, not re-asserted, for the duration of an Edit
Mode session and for the duration of a CDM settings window session, and re-asserted when each ends. This
also keeps Blizzard's containers movable and configurable in Edit Mode, which is the user's own framing
of steal mode: *"the user still moves and configs the blizzard cdm directly."* Zero writes happen while
either is open.

**Three gates, in this order, on every apply:**

1. **Suspended?** — `editModeOpen or cdmSettingsOpen` → set `pendingApply = true` and return. No write.
2. **In combat?** — `InCombatLockdown()` → set `pendingApply = true` and return. No write. Mandated twice
   over: `:Hide()` on a protected frame is blocked in combat, and the milestone rule from the research is
   *"all writes to CDM frames are out-of-combat-only, full stop."*
3. **On a Blizzard call stack?** — never apply inline from an event handler or an `EventRegistry`
   callback. Every trigger calls `ns:QueueStealVisibility()`, which sets a flag and schedules one
   `C_Timer.After(0, ...)`, so the write always lands on a fresh execution frame. This is the same
   hygiene the research's `pure` injection variant used for its writes.

**The re-assert triggers, named.** `StealMode.lua` registers its own frame for
`PLAYER_ENTERING_WORLD`, `PLAYER_REGEN_ENABLED`, `PLAYER_LEVEL_CHANGED`, `VARIABLES_LOADED`, `CVAR_UPDATE` and
`EDIT_MODE_LAYOUTS_UPDATED`, and its own `EventRegistry` callbacks for `EditMode.Enter` (suspend),
`EditMode.Exit` (resume + queue), `CooldownViewerSettings.OnShow` (suspend) and
`CooldownViewerSettings.OnHide` (resume + queue). `PLAYER_REGEN_ENABLED` is both a trigger and the flush
point for anything the combat gate deferred.

**Prior visibility is captured on the first apply of a steal-mode session, not on the toggle click.**
`STEAL-07` needs the state each viewer had *before* TBT hid it. `ns.stealPriorShown` is runtime-only and
starts empty; the first apply after steal mode becomes active reads `viewer:IsShown()` into it and only
then hides. That single rule covers both entry paths correctly — the checkbox click, and a login where
the database already says on — and it is naturally correct in the checkbox case because the checkbox
lives *inside* the CDM settings window, so the apply is suspended until that window closes and
`IsShown()` is read after Blizzard has settled its own state. Turning steal mode off restores from
`ns.stealPriorShown` and then wipes it, so the next switch-on re-captures.

**What this cannot do, and why it is not a planning gap.** Blizzard re-shows the viewers on combat
*start* (`PLAYER_IN_COMBAT_CHANGED` → `UpdateShownState`), and TBT cannot hide them again until combat
ends because writing to a CDM frame in combat is exactly the action that taints. The hide is re-asserted
at `PLAYER_REGEN_ENABLED`. This is the direct, unavoidable consequence of the two risks the user
explicitly accepted when choosing plain `:Hide()` over driving Blizzard's Edit Mode visibility setting.
It is recorded in **Risks** with the workaround available to the user, not worked around here.

## Notes carried in from plan review

- **`PLAYER_LEVEL_CHANGED`, not `PLAYER_LEVEL_UP`.** Blizzard’s `CooldownViewerMixin:OnEvent` re-asserts
  `UpdateShownState()` on `PLAYER_IN_COMBAT_CHANGED` and **`PLAYER_LEVEL_CHANGED`**
  (`CooldownViewer.lua:1764-1765`). An earlier draft registered `PLAYER_LEVEL_UP`, which fires only on a
  real level-up — so level-sync or template scaling would re-show a viewer with nothing to re-hide it
  until an unrelated trigger fired. The acceptance grep passed anyway, because it matched the wrong name.
- **`VARIABLES_LOADED` added** — another of Blizzard’s own `UpdateShownState` callers
  (`CooldownViewer.lua:1755-1757`). `PLAYER_ENTERING_WORLD` covers nearly the same moment, but an
  unlisted caller is an unlisted caller.
- **`pendingApply` needs a reader or must be deleted.** As drafted both early-return gates write it and
  nothing reads it. Correctness is actually carried by the explicit re-trigger events
  (`PLAYER_REGEN_ENABLED`, `EditMode.Exit`, `CooldownViewerSettings.OnHide`), which each call
  `ns:QueueStealVisibility()` again. Give it a real consumer or drop it — do not ship dead state that
  implies a retry mechanism that does not exist.
## Risks

- **Blizzard re-shows the viewers on combat start and TBT cannot hide them until combat ends.**
  `CooldownViewerMixin:OnEvent` handles `PLAYER_IN_COMBAT_CHANGED` by calling `UpdateShownState`, and the
  combat gate forbids the counter-write. Directly downstream of the two risks the user accepted when
  choosing plain `:Hide()`. The re-assert at `PLAYER_REGEN_ENABLED` bounds the window to the duration of
  one combat. The user-side workaround, if the flicker is unacceptable, is to set each CDM viewer's own
  visibility to Hidden in Blizzard's Edit Mode — which is precisely the mechanism the locked decision
  rejected, so revisiting it is a user decision and not a defect to fix here.
- **Blizzard's viewers are visible during an Edit Mode session and while the CDM settings window is
  open.** Deliberate: `ShouldBeShown()` returns true unconditionally in both states
  (`CooldownViewer.lua:1888-1920`), so re-asserting would be a losing write loop inside the exact code
  path that produced every recorded taint failure. Both are configuration surfaces where seeing
  Blizzard's own containers is useful. If the user wants them hidden there too, that is a follow-up
  decision with a measurable taint cost attached.
- **`:Hide()` may still taint the viewer's shown state.** Unproven either way — the five measured
  injection variants all *parented a frame into* the viewer, which is a strictly heavier action, and the
  research's stated mechanism ("being a child at all is the problem") does not apply to a bare `Hide`.
  Step 5 of the in-game checklist is the decisive test, and it is written to start from a clean
  `/reload` for exactly that reason. If it fails, the fallback is the rejected Edit-Mode-visibility
  mechanism, and that requires a user decision.
- **`EDIT_MODE_LAYOUTS_UPDATED` may fire while `editModeOpen` is true.** Harmless: the suspension gate
  turns the apply into a `pendingApply = true` and the `EditMode.Exit` callback flushes it.
- **`CVAR_UPDATE` fires often.** The apply is idempotent and cheap — four global lookups and, at most,
  four `Hide()` calls on frames that are already hidden — and the single-flight queue coalesces bursts
  into one apply per frame. No table is created on that path.
