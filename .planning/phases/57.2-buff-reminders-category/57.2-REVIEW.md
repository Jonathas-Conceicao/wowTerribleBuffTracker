## Warnings

### WR-01: A change in restriction state with no combat edge and no aura event is not handled

**File:** `BuffEngine.lua:1626`, `BuffEngine.lua:1690-1700`, `Core.lua:1497-1514`
**Issue:** Reminder state changes only on UNIT_AURA, PLAYER_REGEN_DISABLED/ENABLED, PLAYER_ENTERING_WORLD and a rank rebuild. `C_Secrets.ShouldAurasBeSecret()` can flip with none of these firing. This happens with a Mythic+ key: restrictions switch on at key start before any pull, and switch off at key completion out of combat.
- **Restriction ends out of combat.** Every reminder was cleared to nil while restricted, and no refresh happens when the restriction lifts. A buff that really is missing stays hidden until some unrelated aura changes. This breaks REM-03's rule that a missing buff shows again once it can be read.
- **Restriction starts out of combat.** A reminder that is showing keeps showing until the next UNIT_AURA. CONTEXT says it must hide "whenever the read is unreadable". In practice the effect is small: any change to the buff fires UNIT_AURA, which then clears it.

Blizzard documents `ADDON_RESTRICTION_STATE_CHANGED` (RestrictedActionsDocumentation.lua). It fires before a restriction becomes active and after it is deactivated, which is exactly the edge that is missing.
**Fix:** Register it through the existing guarded `TryRegisterEvent` path. Forever may not have the event. Then re-read on it:
```lua
elseif event == "ADDON_RESTRICTION_STATE_CHANGED" then
	-- Fired before a restriction activates and after it deactivates: re-evaluate
	-- (RefreshAuraStates clears when still restricted, re-reads when not).
	ns:RefreshAuraStates()
```
If the event is missing on a client, the current behaviour stays as it is, so this change carries no risk there.

### WR-02: A full-update UNIT_AURA skips the reminder re-read, so a reminder can hold a stale state

**File:** `BuffEngine.lua:1703-1719`
**Issue:** The ZONE-02 `isFullUpdate` early return comes before `ns:RefreshAuraStates()`. Phase 57's "the state holds" rationale does not fit reminders:
- `RefreshAuraStates` does not read the event payload. It makes live `GetPlayerAuraBySpellID` reads, each gated on readability, so a full update does not make its reads any less real.
- A reminder showing "missing" whose buff arrives in a full-update batch keeps showing although the buff is up. That is the stale "missing" state REM-03 forbids.
- A buff lost in a full update, for example from an out-of-combat death or a phasing or vehicle transition, leaves the reminder hidden.

In-combat deaths are covered by the PLAYER_REGEN_ENABLED re-read. Out-of-combat full updates are not.
**Fix:** Refresh the reminder cache before the full-update return, and keep suppressing only the cancellation scan, which is what ZONE-02 was about:
```lua
local isFullUpdate = updateInfo and updateInfo.isFullUpdate
if not issecretvalue(isFullUpdate) and isFullUpdate then
	-- Live, readability-gated reads: unaffected by the payload being a full list.
	ns:RefreshAuraStates()
	...
	return
end
```
If you want the loading-screen transient avoided too, the minimum safe version is `ns:ClearReminderStates()` in that branch. Hiding is always safe, and PLAYER_ENTERING_WORLD re-reads anyway.

### Warnings

#### 05-WR-01: Cast race. A readable "absent" read between the cast and the aura landing ends the new timer and shows the reminder

**File:** `BuffEngine.lua:1696-1708` (RefreshAuraStates), `BuffEngine.lua:1541-1547` (ScanActiveTimersForCancellation), `Providers.lua:238-250`
**Issue:** The race is real. `OnTrigger` starts the reminder timer and writes `auraState = true`. If any UNIT_AURA reaches the player before the buff itself is applied (for example a consumed proc, a resource aura, or a cast-time spell whose aura lands with the spell's travel), that event does the following:

1. `RefreshAuraStates` reads the watched ID as readably absent.
2. `CancelsOnAuraLoss` is true by default, so it deletes the timer and writes `false`.
3. `ScanActiveTimersForCancellation` would do the same through `aliveBuffs`.

The reminder draws until the next UNIT_AURA brings the aura. Buffs have the identical race in the scan, with no grace at all, and there the buff timer is lost for good. So "mirror the buff" means both paths need the same fix. A fix in only one path does not work, because the scan also writes `auraState = false` for a reminder key.

**Fix:** Add one shared grace, keyed on the cast time rather than `startedAt`, because the expiry sync rewrites `startedAt`:

```lua
-- Core.lua, on ns (not a file local: upvalue-order trap)
ns.CAST_AURA_GRACE = 0.5
-- Providers.lua ns:FillUserBuffProc, after the fields are set
proc.castAt = now
-- BuffEngine.lua RefreshAuraStates sync-start path, after FillUserBuffProc
proc.castAt = nil -- a read-started timer is not a cast
-- RefreshAuraStates, right after the read, before keepsTimer
local proc = ns.activeTimers[key]
if present == false and proc and proc.castAt and now - proc.castAt < ns.CAST_AURA_GRACE then
	present = nil -- treated as unknown: the state and the timer hold
end
-- ScanActiveTimersForCancellation: hoist `local now = GetTime()` above the loop, then
if allReadable and not anyPresent and not (timer.castAt and now - timer.castAt < ns.CAST_AURA_GRACE) then
```

The cost is one subtraction and one compare per live proc per aura event, with no allocation. If the aura never lands, the timer runs its full duration, which is the opt-out behaviour. That is acceptable, because the aura landing normally raises its own UNIT_AURA after the grace. Applying the fix to the buff scan touches pre-milestone code, so it needs the user's approval under PROJECT.md's no-refactor rule. It is a behaviour fix, not a refactor.

#### 05-WR-02: A full-update UNIT_AURA ends a reminder timer, but a buff timer survives it

**File:** `BuffEngine.lua:1766` together with `1696-1708`, and `1772-1778`
**Issue:** 57.2 WR-02 moved `RefreshAuraStates` above the ZONE-02 `isFullUpdate` return. At that point it only wrote state. Since this plan it also deletes the running timer on a readable-absent read. ZONE-02 exists because a full-update batch (zone boundary, loading screen) can transiently read an aura as absent, and it suppresses the buff cancellation scan for that reason. A buff timer survives the batch. A reminder timer is cancelled, its state goes `false`, and it flashes, contrary to "cancel exactly like a buff". The same applies to the `RefreshAuraStates` call at `PLAYER_ENTERING_WORLD` after a zone-in loading screen.
**Fix:** Read `isFullUpdate` before the refresh and pass it in. On a full update, a readable-absent read may still write state for a reminder with no timer, which keeps WR-02's purpose. It must not end a running timer:

```lua
local isFullUpdate = updateInfo and updateInfo.isFullUpdate
local full = not issecretvalue(isFullUpdate) and isFullUpdate == true
ns:RefreshAuraStates(full)
-- in RefreshAuraStates(suppressCancel):
local keepsTimer = present == false and proc ~= nil and (suppressCancel or not ns:CancelsOnAuraLoss(entry))
```

#### 05-WR-03: A cast after the aura event overwrites a synced expiry with the typed duration

**File:** `Providers.lua:245`, `BuffEngine.lua:1711-1729`
**Issue:** When UNIT_AURA arrives before UNIT_SPELLCAST_SUCCEEDED, the sequence is:

1. `RefreshAuraStates` starts or syncs the timer to the aura's real `expirationTime`.
2. The cast arrives and `FillUserBuffProc` wipes the same pooled proc and sets `expiresAt = now + entry.duration`.
3. Nothing resyncs until the next readable aura event. Out of combat, that can be a long time.

If the typed duration is shorter than the aura, the lazy expiry in `GetActiveTimers` writes `false`, and the reminder shows while the buff is still up. This breaks the stated rule that a readable present aura with a readable expiry syncs the timer. It also runs the other way round: a longer typed duration hides a reminder after the buff is gone, until the next aura event.

**Fix:** Stamp the sync and let a cast within the same moment keep it:

```lua
-- RefreshAuraStates, both sync branches:
proc.syncedAt = now
-- OnTrigger reminder side:
local running = ns.activeTimers[reminderKey]
if not (running and running.syncedAt and GetTime() - running.syncedAt < ns.CAST_AURA_GRACE) then
	ns.activeTimers[reminderKey] = ns:FillUserBuffProc(reminderKey, reminderEntry, GetTime())
end
ns.auraState[reminderKey] = true
```

This needs no aura read in Providers.lua, so the aura-read gate's allowlist is untouched. `FillUserBuffProc`'s `AcquireProc` wipe clears `syncedAt` on a real refill.

#### 05-WR-04: The expiry sync overrides "End when the aura is lost" being off

**File:** `BuffEngine.lua:1711-1720`
**Issue:** `keepsTimer` makes an opted-out reminder's typed timer govern after aura loss, which is the buff rule. The sync then moves `expiresAt` to the aura's expiry, above the 0.5s threshold, whenever the aura is readable. With duration 30, opt-out on, and a 10s aura, the timer is cut to 10s on the first aura event. `keepsTimer` then preserves a timer that already ends when the aura ends, so the reminder shows at 10s instead of 30s. On an opted-out tracker, the sync cancels the opt-out.
**Fix:** Either skip the correction for opted-out trackers, or only ever extend. Extending covers a refresh by another player, and a shrink is what an aura loss would have done:

```lua
if proc ~= nil then
	local optedOut = not ns:CancelsOnAuraLoss(entry)
	if (optedOut and expirationTime > proc.expiresAt + 0.5)
		or (not optedOut and math.abs(proc.expiresAt - expirationTime) > 0.5) then
```

Ask the user which of the two they want. The plan's rule says "syncs" without any exception for opted-out trackers.

#### 05-WR-05: Reminders with no duration never hide on cast and never get a timer, and the user's existing reminders are all in this state

**File:** `Providers.lua:238-250`, `BuffEngine.lua:1721`, `BuffEngine.lua:639-648`
**Issue:** v10 was changed in place. Any database that already ran the earlier v10 build is at `schemaVersion = 10`, and that includes the developer's own play database. For every reminder in it, `duration`, `keepOnAuraLoss` and `endOnCast` were deleted, and the new migration never runs again. The deleted cast rules are unrecoverable. For those reminders:

- The cast does not write `auraState = true`. In combat, where every read is secret, the reminder stays drawn after the player casts the buff until combat ends.
- The sync never starts a timer (`type(entry.duration) == "number"` at 1721), even though the aura supplies its own duration there, and `entry.duration` is not used on that path at all.

**Fix:**

1. The cast is evidence the buff is up regardless of the timer. Move `ns.auraState[reminderKey] = true` plus a redraw out of the duration condition, still gated on `section ~= "hidden"`.
2. Drop the `entry.duration` requirement from the sync-start path. Make `FillUserBuffProc` tolerate nil (`proc.expiresAt = now + (entry.duration or 0)`), because both fields are overwritten immediately afterwards.
3. Print a one-time chat line at login naming reminders without a duration, so the user knows to re-enter the duration and "Ends when you cast:" rules.

#### Fixed

- **05-WR-01** (`8935d73`, Core.lua, Providers.lua, BuffEngine.lua): `ns.CAST_AURA_GRACE = 0.5` lives on `ns` in Core.lua. `ns:FillUserBuffProc` stamps `proc.castAt`, so every cast-started buff and reminder proc carries it. Within the grace, a readable absence counts as unknown in both `ns:RefreshAuraStates` (present becomes nil, so the timer and the cast's `true` state hold) and `ns:ScanActiveTimersForCancellation` (`now` hoisted above the loop). The buff side is included by orchestrator decision: it is a bug fix, not a refactor. A read-started reminder timer clears `castAt`. Cost: one subtraction and one compare per live proc per aura event, no allocation.
- **05-WR-02** (`066ce48`, BuffEngine.lua, Core.lua): `ns:OnUnitAura` reads `isFullUpdate` (still secret-gated) before the refresh and passes it as `ns:RefreshAuraStates(suppressCancel)`. `keepsTimer` then also holds on `suppressCancel`, so a full update ends no running reminder timer and leaves its state alone, while a reminder with no timer still takes the read (57.2 WR-02's purpose). `PLAYER_ENTERING_WORLD` passes `true` as well. The OnTrigger reminder side leaves a timer synced within `ns.CAST_AURA_GRACE` alone instead of refilling it, and still marks the reminder present. A real refill's `AcquireProc` wipe clears `syncedAt`. There is no aura read in Providers.lua, so the gate allowlist is untouched.
- **05-WR-04** (`a7623d7`, BuffEngine.lua): the review's extend-only option. With "End when the aura is lost" off, the sync corrects only when the aura's expiry is more than 0.5s later; shortening remains for a tracker that ends on aura loss.
